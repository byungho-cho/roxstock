# 1. v0.5 변경 이력

v0.4는 보존하며 다음 내용을 v0.5에 추가·명확화했습니다.

1. `compound_growth_plans` 1 : N `compound_growth_goals`의 컬럼, FK와 애플리케이션 제약을 확정했습니다.
2. 거래·배당·예수금 내역의 **최초 등록만 예수금 반영** 원칙을 생성·수정·삭제별로 명시했습니다.
3. `cash_transactions.balance_after`는 최초 등록 직후의 잔액 스냅샷이며 과거 행 수정 시 다시 계산하지 않는 것으로 확정했습니다.
4. 매수 Lot, 단일 Lot 매도, 연결 삭제, 보유현황 계산식을 구현 단위로 정리했습니다.
5. 사용자 입력 거래일은 날짜만 저장하고 실제 등록 시각은 `created_at`으로 분리했습니다.
6. 스냅샷과 수익률에서 확정 계산식과 추가 결정이 필요한 계산식을 구분했습니다.
7. Figma 커버·펼침 화면의 명칭, 이동, 입력·빈 상태와 설계 불일치를 기록했습니다.
8. 실제 Prisma의 복리목표 단일 구조를 계획·목표 1:N 구조로 현행화했습니다.

# 2. 개발 우선순위

| 순위 | 기능 | 구현 완료 조건 |
|---:|---|---|
| 1 | 매수 Lot | 매수 1건이 독립 Lot으로 저장되고 잔여수량을 계산할 수 있음 |
| 2 | 단일 Lot 매도 | 매도 1건이 선택한 Lot 1건만 참조하며 초과매도가 차단됨 |

| 5 | 스냅샷·분석 | 현재 상태를 일별 UPSERT하고 확정 계산식만 제공함 |

# 3. 확정 업무 규칙

## 3.1 매수 Lot

- `buy_trades` 한 행은 독립된 매수 Lot 한 건입니다.
- 한 종목을 같은 날 같은 단가로 여러 번 매수해도 각각 별도 Lot으로 저장할 수 있습니다.
- 사용자 입력은 거래일, 종목, 수량, 단가, 메모입니다.
- 거래일은 날짜만 저장하고 실제 등록·수정 시각은 `created_at`, `updated_at`으로 관리합니다.
- 매수금액은 `매수수량 × 매수단가`로 조회 시 계산하며 저장하지 않습니다.

```text
Lot 잔여수량 = 매수수량 - 연결된 매도수량 합계
Lot 잔여매입금액 = Lot 잔여수량 × 매수단가
```

수량과 단가는 0보다 커야 합니다.

## 3.2 단일 Lot 매도

- `sell_trades.buy_trade_id`는 반드시 하나의 `buy_trades.id`를 참조합니다.
- 한 매수 Lot은 여러 건으로 분할매도할 수 있습니다.
- 한 매도는 여러 매수 Lot을 묶을 수 없습니다.
- 여러 Lot 선택과 일괄매도 UI는 제공하지 않습니다.
- 보유현황의 Lot 카드 또는 행에서 매도를 선택하면 해당 Lot 매도 화면으로 이동합니다.
- 기본 매도수량은 해당 Lot 잔여수량, 기본 매도단가는 현재가이며 사용자가 변경할 수 있습니다.
- 등록 트랜잭션 안에서 누적 매도수량을 다시 확인해 동시 초과매도를 차단합니다.

```text
실현손익 = 매도수량 × (매도단가 - 연결된 Lot 매수단가)
```

실현손익에는 `fee_tax_amount`를 넣지 않으며 거래비용은 별도 합계로 보여줍니다.

## 3.3 거래 수정과 삭제

- 거래 수정은 거래 행만 변경하며 현재 예수금을 다시 반영하지 않습니다.
- 연결 매도가 없는 매수는 확인 후 단건 삭제합니다.
- 연결 매도가 있는 매수를 삭제하면 연결 매도 건수를 확인창에 표시합니다.
- 사용자가 확인하면 연결 매도를 먼저 삭제하고 매수를 삭제합니다.
- 연결 매도 삭제와 매수 삭제는 하나의 DB 트랜잭션으로 처리합니다.
- FK는 `ON DELETE RESTRICT`를 유지하고 서비스가 삭제 순서를 제어합니다.
- 매도만 삭제할 때도 현재 예수금과 과거 스냅샷은 변경하지 않습니다.
- 일괄삭제 UI와 소프트 삭제는 1차 범위에 포함하지 않습니다.

## 3.4 예수금

`accounts.cash_balance`는 거래원장을 재합산한 값이 아니라 증권계좌에서 확인한 **현재 실제 예수금**입니다.

| 사건 | 최초 등록 | 수정 | 삭제 |
|---|---|---|---|
| 매수 | 매수금액과 비용 차감 | 자동 반영 안 함 | 자동 복원 안 함 |
| 매도 | 매도금액에서 비용을 뺀 금액 가산 | 자동 반영 안 함 | 자동 복원 안 함 |
| 입금·출금 | 유형에 따라 가감 | 자동 반영 안 함 | 자동 복원 안 함 |
| 배당 | 세후 배당금 가산 | 자동 반영 안 함 | 자동 복원 안 함 |

최초 등록 시 계산은 다음과 같습니다.

```text
BUY        = 이전 예수금 - 매수금액 - 수수료·세금
SELL       = 이전 예수금 + 매도금액 - 수수료·세금
DEPOSIT    = 이전 예수금 + 입금액
WITHDRAWAL = 이전 예수금 - 출금액
DIVIDEND   = 이전 예수금 + 세후 배당금
```

- 수수료와 세금은 `cash_transactions.fee_tax_amount` 한 컬럼에 합산합니다.
- 거래·배당 테이블과 `cash_transactions` 사이에 FK를 두지 않습니다.
- 매수·매도·배당 생성과 예수금 변경·예수금 내역 생성은 한 DB 트랜잭션으로 처리합니다.
- 계좌 행을 잠그고 현재 잔액을 읽은 뒤 `balance_after`와 `cash_balance`를 갱신해 동시 등록 충돌을 막습니다.
- `balance_after`는 **그 내역이 최초 등록된 직후의 잔액 스냅샷**입니다.
- 과거 예수금 내역을 수정해도 해당 행과 이후 행의 `balance_after`를 다시 계산하지 않습니다.
- 예수금 내역을 삭제해도 현재 잔액과 다른 행의 `balance_after`를 변경하지 않습니다.
- 실제 계좌와 차이가 있으면 사용자가 `accounts.cash_balance`를 직접 수정하며 별도 보정 이력을 저장하지 않습니다.

월별·연도별 거래비용은 `fee_tax_amount`를 기간 합산해 조회합니다. 스키마 v0.2의 “비용 수정 시 변경 전후 차액을 현재 예수금에 반영” 규칙은 폐기합니다.

## 3.5 배당

- `dividends.gross_amount`에 세전 배당금, `net_amount`에 세후 배당금을 저장합니다.
- 배당 최초 등록 시 세후 배당금만 현재 예수금에 1회 반영합니다.
- 연도별 실수령 배당금은 해당 연도 `net_amount` 합계입니다.
- 배당 수정·삭제는 현재 예수금을 자동 변경하지 않습니다.

## 3.6 보유현황

보유현황은 저장 테이블 없이 매수 Lot과 연결 매도를 이용한 조회 모델로 계산합니다.

```text
종목 보유수량 = 종목별 Lot 잔여수량 합계
종목 잔여매입금액 = Σ(Lot 잔여수량 × Lot 매수단가)
종목 평균단가 = 종목 잔여매입금액 ÷ 종목 보유수량
종목 평가금액 = 종목 보유수량 × 현재가
종목 평가손익 = Σ[Lot 잔여수량 × (현재가 - Lot 매수단가)]
총 평가자산 = 전체 종목 평가금액 + 현재 예수금
예수금 비중 = 현재 예수금 ÷ 총 평가자산 × 100
```

- 종목 평균단가는 화면 참고값일 뿐 매도 연결과 실현손익 원가로 사용하지 않습니다.
- 종목 보유수량이 0이 되면 `watchlist_items.list_type`을 `WATCHLIST`로 바꿉니다.
- 매수 후 보유수량이 생기면 `HOLDING`으로 바꿉니다.
- 한 종목은 `WATCHLIST`, `HOLDING`, `RECOMMENDED` 중 하나에만 속합니다.

## 3.7 스냅샷

- `daily_account_snapshots`는 계좌·날짜별 한 행입니다.
- `daily_position_snapshots`는 계좌·종목·날짜별 한 행이며 1차에서 선택 구현입니다.
- 같은 날짜의 행을 약 1시간마다 UPSERT합니다.
- 한국 시간 23시 실행을 당일 마지막 예정 갱신으로 사용합니다.
- `is_final` 컬럼은 두지 않고 마지막 성공 UPSERT 값을 당일 값으로 사용합니다.
- 필수 현재가가 없으면 0원으로 스냅샷을 만들지 않습니다.
- 거래·예수금의 수정·삭제로 과거 스냅샷을 소급 변경하지 않습니다.
- 휴장일 생성 여부는 아직 결정하지 않았습니다.

## 3.8 수익과 수익률

확정 계산식은 다음과 같습니다.

```text
Lot 실현손익 = 매도수량 × (매도단가 - Lot 매수단가)
종목 실현손익 = 종목에 연결된 Lot 실현손익 합계
종목 매수총액 = 해당 종목 매수수량 × 매수단가 합계
손익률 = 실현손익 ÷ 매수총액 × 100
배당률 = 누적 세후 배당금 ÷ 매수총액 × 100
총계 = 실현손익 + 누적 세후 배당금
총계율 = 총계 ÷ 매수총액 × 100
```

매수총액이 0이면 비율은 `-`로 표시합니다. 기간 성과의 기본 수익률 분모와 입출금 가중 방식은 아직 결정하지 않았으므로 1차 구현에서 임의 공식을 추가하지 않습니다.

# 4. 복리계획 1 구조

## 4.1 관계

```text
accounts 1 ── N compound_growth_plans 1 ── N compound_growth_goals
```

- 1차·2차·3차처럼 기간이 다른 단위는 복리계획입니다.
- 같은 계획의 안정형·기준형·공격형처럼 목표율이 다른 단위는 복리목표입니다.
- 화면은 일반적으로 3개 목표를 먼저 표시하지만 저장 개수 제한은 없습니다.

## 4.2 계획

`compound_growth_plans`는 다음 공통값을 가집니다.

- 계좌, 계획명, 시작일, 종료일
- 시작자산, 연간 추가 투자금
- 활성 여부, 표시순서, 메모
- 생성·수정시각

계좌 안에서 계획명은 중복할 수 없습니다. 종료일은 시작일보다 빠를 수 없고 시작자산과 연간 추가금은 0 이상이어야 합니다.

## 4.3 목표

`compound_growth_goals`는 다음 값을 가집니다.

- 계획 FK, 목표명, 연 목표수익률
- 표시색상 키, 기본 목표 여부, 표시 여부, 표시순서, 메모
- 생성·수정시각

계획 안에서 목표명은 중복할 수 없습니다. 목표수익률은 0 이상이어야 합니다. 목표가 존재하는 계획은 기본 목표를 정확히 하나 가져야 하며, 이 조건은 서비스 트랜잭션으로 검증합니다. 계획 삭제는 FK `RESTRICT`를 유지하고 목표를 먼저 삭제한 뒤 계획을 삭제합니다.

## 4.4 계산

연간 추가 투자금은 첫해부터 매년 연초에 더한 후 수익률을 적용합니다.

```text
첫해 목표자산 = (시작자산 + 연간추가금) × (1 + 목표수익률)
다음 해 목표자산 = (직전 목표자산 + 연간추가금) × (1 + 목표수익률)
```

Figma의 “각 연도 말에 반영” 및 “추가금은 연말 반영” 문구와 예시 금액은 구현 기준으로 사용하지 않습니다.

## 5.2 반응형과 탐색

| 구간 | 화면 기준 | 일정 |
|---|---|---|
| 커버 0~599px | 단일 열·카드·세로 스크롤, 가로 표 금지 | 1차 개발 |
| 펼침·태블릿 600~1199px | 2열 Master–Detail, 집중 입력은 전체 폭 | 1차 개발 |
| PC 1200px 이상 | 좌측 사이드바·전체 데이터 테이블 | 1차 개발 완료 후 상세 설계 |

관심·보유·추천 탭과 기간 탐색은 데이터 범위 안에서 양방향 순환 스와이프를 사용합니다. 세로 목록을 스크롤하는 동안에는 가로 스와이프를 실행하지 않습니다.

## 5.3 입력과 빈 상태

- 공통 입력은 Figma 002의 Default·Focus·Filled·Error·Required·Disabled·Readonly·Loading 상태를 따릅니다.
- 필수값, 숫자 범위, Lot 잔여수량은 저장 전에 검증하고 첫 오류 필드로 포커스를 이동합니다.
- 매수·매도 수정 화면의 거래 후 예수금은 참고값이며 저장으로 예수금을 변경하지 않습니다.
- 복리계획 없음: `등록된 복리계획이 없습니다.`와 `첫 계획 추가`를 표시합니다.
- 계획에 목표 없음: `복리목표를 추가해 주세요.`와 `목표 추가`를 표시합니다.
- 투자손익 없음: `투자손익 내역이 없습니다.`를 표시합니다.
- 종목 검색 결과 없음과 통신 오류를 서로 다른 상태로 표시합니다.
- 수집 실패 시 마지막 정상 가격과 실패 상태를 함께 표시하며 수기 수정 진입점을 제공합니다.

## 5.4 Figma 수정 필요 항목

# 7. 정합성 점검 결과

## 7.1 이번에 해소한 불일치

| 항목 | 기존 상태 | v0.5 기준 |
|---|---|---|
| 복리 구조 | Prisma가 목표 단일 테이블 | 계획 1:N 목표로 변경 |
| 계획 공통값 | 목표 행마다 기간·금액 중복 | 계획 테이블로 이동 |
| 거래일 | Prisma `bought_at`, `sold_at` 시각 | 사용자 입력 `trade_date` 날짜 |
| 예수금 비용 수정 | 스키마 v0.2는 차액 반영 | 어떤 수정·삭제도 자동 미반영 |
| `balance_after` | 표시 의미 미정 | 최초 등록 직후 스냅샷, 불변 |
| 연결 매수 삭제 | 문서만 설명 | 확인 후 매도→매수 트랜잭션 삭제 |
| Figma 복리 추가금 | 연말 반영 문구 | 연초 반영을 구현 기준으로 확정 |

## 7.2 확정 규칙

- 매수 1건 = Lot 1건, 매도 1건 = Lot 1건 참조
- 매수 1건에 여러 분할매도 허용, 여러 Lot 일괄매도 금지
- 연결 매수 삭제 시 확인 후 연결 매도까지 단일 트랜잭션 삭제
- 최초 등록만 예수금 반영, 수정·삭제는 예수금·과거 스냅샷 미반영
- 현재 예수금은 사용자가 직접 실제 계좌와 맞출 수 있음
- 보유현황과 평균단가는 Lot 잔여수량으로 조회 계산
- 스냅샷은 일자별 UPSERT, 23시 마지막 예정 실행, final 컬럼 없음
- 복리계획 1:N 복리목표, 첫해부터 연초 추가금 반영
- PC 상세 화면은 1차 커버·펼침 개발 후 진행

## 7.3 아직 결정이 필요한 항목

1. 기존 `compound_growth_goals` 데이터를 새 계획·목표로 이관하는 규칙
2. 같은 계좌의 복리계획 기간 중복 허용 여부
3. 휴장일 계좌·종목 스냅샷 생성 여부
4. `daily_position_snapshots`의 1차 실제 구현 여부
5. 기간 성과 수익률의 분모와 기간 중 입출금 가중 방식
6. Figma 001 화면흐름도 작성과 Figma 충돌 문구 수정 일정
7. 가치분석의 RIM W 계산에 필요한 상세 재무 컬럼과 원천 데이터 확정

# 8. 구현 안전장치

- Prisma로 표현하기 어려운 양수·범위·기본 목표 1개 조건은 API 검증과 테스트로 보장합니다.
- Lot 잔여수량 확인, 매도 저장과 최초 예수금 반영은 각각 DB 트랜잭션 안에서 처리합니다.
- 예수금 최초 반영은 계좌 행 잠금 또는 동등한 동시성 제어를 사용합니다.
- Decimal 계산은 JavaScript `number`로 변환하지 않고 Prisma Decimal 또는 정밀 계산 유틸을 사용합니다.
- 기존 초기 마이그레이션을 수정하지 않고 별도 마이그레이션으로 변경합니다.
- 데이터 이관 규칙이 결정되기 전에는 운영 DB에 복리 구조 마이그레이션을 적용하지 않습니다.
