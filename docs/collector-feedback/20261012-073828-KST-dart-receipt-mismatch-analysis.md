### A. 비12월 결산의 사업연도/보고기간 연결

GRT API 반환20250304000174는 목록의 **반기보고서 (2024.12)**, 접수일2025-03-04, 정정 표시 없음이다. 선택20240229002271은 **반기보고서 (2023.12)**이며 역시 정정 표시 없음이다. 이 차이는 정정공시 관계가 아니라 서로 다른 보고기간의 원보고서 선택이다.

배포 mapper는 `(YYYY.MM)` 파싱 → 표시연도가 task.fiscalYear인 사업보고서의 결산월 선택(없으면12월) → Q1/Q2/Q3에 결산일에서9/6/3개월 차감 → 일치 제목에서 최신 선택을 한다. 한편 재무 API에는 task.fiscalYear를 그대로 bsns_year로 보낸다. GRT에서 이 두 기준이 서로 어긋나는 것을 실제 API 비교로 확인했다. 공식 문서는 사업연도 인자를 정의하지만 비12월 결산의 모든 전환 규칙을 설명하지 않으므로, **GRT 결과를 모든 종목에 대한 일괄 year-1 보정 규칙으로 일반화하면 안 된다.**

GRT에는17개 분기/반기 실패(2017~2025)가 존재하고 이 대표 사례와 일관된 패턴을 보인다. 나머지16개를 이번에 외부 API로 재검증하지 않았으므로 같은 원인의 영향 후보로 남긴다. 다른 비12월 결산 기업·결산월 변경·과거 보고서 없는 경우도 공통 mapper의 검증 대상이다.

추가 코드 위험: `endOfFiscalPeriod`가 연간12월/Q1 3월/Q2 6월/Q3 9월로 고정되어 비12월 결산의 periodEndDate가 실제 기간과 다를 수 있다. 코드상 위험은 확인했으나 기존 전체 데이터의 오기재 규모를 집계/수정하지 않았다.

### B. 첨부정정과 재무 API의 접수번호 계약

CJ 목록에는 같은2024.12 연간의 원공시 **20250317000953**(2025-03-17, rm=정연)과 **[첨부정정]20250317001020**(같은 날짜, rm=연)이 함께 있다. 반환 번호는 목록의 원공시와 정확히 같다. 현재 코드는 철회만 제외하고 기재정정/첨부정정/첨부추가를 구분하지 않으며 날짜 내 큰 접수번호를 최신으로 선택한다. 그 결과 첨부정정이 선택된다.

공식 공시검색 문서는 N이 정정 전후 전체 공시를 포함하고, 첨부정정은 첨부서류 변경, 기재정정은 본문 변경을 뜻한다고 설명한다. [공시검색 계약](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019001). 같은 기업·제목 기간·정정 표시로 원/첨부정정 관계가 확인된다. 다만 공시뷰어는 이번 도구에서 접근 실패하여 정정표 원문과 첨부 재무자료의 실제 변경 내용까지 검증하지 못했다. **재무 수치가 동일하다고 단정하지 않는다.**

전체 재무제표 API 입력은 corp_code/bsns_year/reprt_code/fs_div이며 rcept_no를 받지 않는다. 반환 rcept_no가 있다는 사실은 임의로 고른 최신 첨부정정과 일치한다는 계약이 아니다. 현재 절대 동일성 전제는 이 사례에서 API 선택 기준과 맞지 않는다. [단일회사 전체 재무제표 계약](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS003&apiId=2019020).

접수번호 검증 자체를 없애거나 불일치 자료를 선택 공시의 번호로 강제 저장하면 잘못된 출처/기간을 저장할 수 있다. 명시적 접수번호의 자료가 필요하다면 접수번호 입력을 지원하는 [XBRL 원문 API](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS002&apiId=2019019)를 통한 별도 검증 방안을 검토할 수 있지만 이번에는 호출하지 않았다.

## 4. 재현 방법·사용량·증거

운영 키는 기존 backend 프로세스 환경에서 읽기 전용 요청에만 사용했고 출력하지 않았다. 수집 함수/캐시 함수는 호출하지 않았다(현재 수집기의 불일치 처리는 운영 캐시 삭제까지 하므로 진단에 사용하지 않음). 진단 요청은 DB 사용량 카운터도 변경하지 않고 별도 기록했다.

- 실제 DART 호출 **8회 = list.json 3회 + fnlttSinglAcntAll.json 5회**. 최소 간격2초, timeout20초, 최대12회 제한; 키/한도 오류 시 중단. 결과8회 모두000, 한도 오류 없음. 공식 문서/접근 실패 공시뷰어의 일반 웹 조회는 인증키 API 호출이 아니다.
- 10-12 앱 일일 카운터5,065(마지막 갱신05:59:59 KST), 진단8회 별도. 앱 BACKFILL 한도10,000, 일반한도3,000. 따라서 확인된 앱+진단 호출은5,073이나 동일 키의 다른 서비스 사용량을 포함한 DART 계정 전체 수치는 미확인이다. 공식020 설명은 일반20,000 이상이지만 키별 제한이 다를 수 있으므로 이를 실제 보장 한도로 간주하지 않았다.
- [dart-responses.json](20261012-073828-KST-dart-receipt-mismatch-analysis-evidence/dart-responses.json): 키 제외 요청 조건, 요청 시각, HTTP/DART 상태, 목록의 공개 공시 식별값, 재무 응답의 기업/사업연도/코드/접수번호만 보관. 재무 금액/전체 URL/헤더/원문 오류는 제외.
- **격리 fixture 재현**: 실제 배포 JS mapper를 임시 경로로 읽어 복사하고 위 목록 응답을 입력. DB 접근0, 네트워크0. 기존 strict receipt 비교 조건을 재현하여 두 실패와 세 비교/성공 결과 **5개 assertion 통과**. 이는 mapper와 비교 규칙의 재현이며 전체 수집·DB 저장 통합 재현은 아니다.
- 실행: 증거 디렉터리에서 `node replay.mjs`. [fixture-replay.json](20261012-073828-KST-dart-receipt-mismatch-analysis-evidence/fixture-replay.json)에 시각과 결과; 배포 JS 사본은 분석 fixture 용도이며 운영 소스 수정이 아니다. GRT 연도 비교는2024 mapper 선택값과2023 API 응답을 비교한다.

## 5. PROCESS_RESTARTED와 프로세스 종료 구분

| 근거 | KST 시각/상태 | 판단 |
| --- | --- | --- |
| 실행#4506 | 시작10-11 20:26:16.240, 정리 표시20:42:19.428 | 다음 실행#4508 생성 직전 미완료 RUNNING 정리 |
| 실행#4508 | 시작10-11 20:42:19.485, 정리 표시10-12 03:06:24.562 | 다음 실행#4780 생성 직전 미완료 RUNNING 정리 |
| 현재 배포 커밋 | 10-11 22:15:19 | #4508 진행 중 배포 변경 시점 후보 |
| 현재 DART 컨테이너 | 생성10-11 22:20:43.573, 시작22:20:55.077 | 현 이미지로 재생성된 사실; 이전 프로세스 종료 원인은 미확인 |
| 07:35 재확인 | running/healthy, restartCount0, unless-stopped, OOMKilled=false, 현재 ExitCode0 | 현재 컨테이너에서 비정상 재시작 근거 없음; 이전 컨테이너의 종료코드/메모리 문제를 배제하지 않음 |

repository.createRun은 남은 RUNNING을 PROCESS_RESTARTED/FAILED로 바꾸면서 **정리 시각을 finishedAt에 기록**한다. PROCESSING 작업도 재개 단계에서 PENDING/PROCESS_RESTARTED로 바꾼다. 종료 로그/이벤트를 확인해서 부여한 코드가 아니다. 따라서 위20:42와03:06은 실제 종료 시각으로 사용하지 않는다.

현재 컨테이너 로그와 보존 Docker events에서 당시 이전 컨테이너의 die/kill/oom/배포 주체 기록을 복구하지 못했다. 이미지 재생성과 배포 커밋의 근접성으로 #4508은 배포 중단 가능성이 있지만 **정상 배포 재시작 확정/비정상 종료 확정은 둘 다 미확인**이다. #4506도 종료 원인 미확인이다. 카운터0은 중간 성공이 없었다는 증거가 아니며 종료 전 실적 정산이 안 됐을 가능성이 있다.

RECEIPT_MISMATCH는 작업별 catch에서 FAILED/재시도 또는 REVIEW_REQUIRED로 기록한 뒤 다음 작업을 진행한다. 실제 최신 실행은97건을 겪고06시까지3,377건 성공으로 끝났다. worker tick catch도 로그 후 지속하므로 **해당 오류가 직접 process.exit를 호출하는 경로는 없다.** 초기 `await tick()` 후에 SIGTERM/SIGINT handler를 등록하는 구조는 초기 긴 수집 중 배포 종료를 충분히 정리하지 못할 위험이 있지만, 과거 종료 원인으로 확정하지 않았다.

추가 필요한 종료 근거: 배포 실행 ID/대상SHA/컨테이너 교체 시각, 이전 컨테이너 ID·StartedAt/FinishedAt·exitCode·OOMKilled, 지속 보존 die/kill/oom 이벤트, 안전한 종료사유/신호/최종runId·stage 로그. 불일치와의 상관관계는 같은 시각의 실제 종료 기록이 확보된 후 판단한다.

**개발 순서:** 보고기간과 DART 요청 사업연도 계약을 먼저 정의하고, 원/정정 공시와 재무 출처 연결을 검증 가능하게 만든다. 그 다음 안전한 구조화 진단 필드를 추가하고 제한된 대표 작업으로 검증한다. 접수번호 검증 해제·불일치 강제 저장·미완료 작업 삭제·전량 재수집은 해결안으로 채택하지 않는다. 기존 SUCCESS와 미완료 작업을 보존하고 변경 대상만 별도 검토한다.

수정 배포 후 검증 제안(이번에는 미실행): 격리 fixture/저장 통합 검증 후 별도 승인된 소수 대표 작업을 확인하고 최소2회 정상 야간 창(최소48시간)을 관측한다. 신규 RECEIPT_MISMATCH/원래 원인별 REVIEW_REQUIRED 수, 성공/실패/NO_FILING, 누락·중복, 기존 정상자료/작업 보존, API 사용량을 기준시각과 같은조건으로 비교한다. DART 컨테이너의 restartCount 증분과 배포에 의한 컨테이너 교체를 별도로 기록한다. 대표 사례의 미완료 해소와 잘못된 출처 차단을 모두 확인하고, 전체 실패가0이 될 것으로 약속하지 않는다. 재수집 정책/기존 작업 상태 변경은 별도 작업에서 결정한다.
