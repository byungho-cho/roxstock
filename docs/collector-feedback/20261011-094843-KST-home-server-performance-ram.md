# 18차 성능 개선 근거: 홈 첫 로딩 서버 진단과 RAM 증설 판단

작성: 2026-10-11 09:48:43 KST. 운영 읽기 전용 진단. 전달 대상: 개발 담당. 소통 PR [#137](https://github.com/byungho-cho/roxstock/pull/137).

## 결론과 확실성

- **확인:** 백엔드 직접 호출에서도 초 단위 지연이 발생한다. 외부 DNS/TCP/TLS나 431KB 전송만으로 설명할 수 없다. API 측정과 겹치는 구간에 실제 swap-in/swap-out 및 높은 I/O wait가 지속된다. RAM 압박에 따른 페이지 교체가 주요 병목 후보이며, 단순히 스왑 사용량만으로 판단한 결론이 아니다.
- **권고:** RAM 증설을 권고한다. 1GB 추가는 단계적 완화책으로 타당하나 충분성·최종 응답시간은 보장할 수 없다. 현재 backend+DB의 스왑만 약 1.3GiB이고 호스트 전체는 약 2GiB다. 이 전부가 활성 working set이라는 뜻도 아니므로 스왑 크기를 그대로 필요 RAM으로 환산하지 않는다. 증설 후 활성 페이지·수집 최대 사용량과 API 재측정으로 추가 용량 여부를 판단한다.
- **확인:** 홈 여러 API가 독립적으로 전체 매수 Lot/매도 이력을 읽고 계산한다. 최근 매수는 최초 5건 표시를 위해 완료 Lot까지 전량 받아 정렬한다. 조회·계산·직렬화 축소는 18차 코드 개선 우선 항목이다.
- **추정:** 메모리 페이지 교체, 디스크 대기, 가상화 CPU steal이 공통 지연에 함께 기여한다. 각각의 기여도와 시작 원인은 미확인이다. 메모리 누수·GC·특정 쿼리가 원인이라고 확정하지 않는다.
- **미확인:** 수집이 전혀 없는 평상시 대조군, 개별 SQL/풀 대기 시간, 이벤트 루프 지연·GC, 증설 후 효과. 수집을 중단하지 않았으며 자연 실행 중 관찰했다.

## API 측정 방법과 결과

기본 활성 계좌를 응답 내부에서 선택, 자산추이 기간 2026-09-11~2026-10-11, `view=trend`, 최근 매수 `remainingOnly=false`. 각 경로/모드/API 3회(총 90개 최종 GET). 개별은 순차, 홈 모드는 계좌 목록 완료 후 나머지 4개 동시 시작; 라운드 사이 1초 간격. 새로운 curl 프로세스마다 연결하므로 브라우저 HTTP/2 연결 재사용을 재현하지 않는다. timeout 45초, HTTP 상태도 검증했다.

- 직접: 호스트에서 backend Docker IP:3300 HTTP.
- 내부 프록시: 공개 호스트명과 정상 TLS 검증을 유지하고 `--resolve`로 localhost:443 접속.
- 공개 HTTPS: 운영 서버의 DNS와 공개 호스트명으로 접속. 모바일/외부 망 지연은 포함하지 않는다. 실제 원격 이용자와 네트워크 경로가 다르다.
- 최초 내부 HTTP는 HTTPS 308 redirect라 API 결과에서 제외했다. 별도 보조 측정은 최근 매수를 `remainingOnly=true`로 요청하여 25,799B였으므로 홈 결과로 사용하지 않았다. 요청 조건 오류를 숨기지 않고 최종 431KB 조건으로 다시 측정했다. 보조 측정은 API 60개 유효 200, redirect 30개 및 계좌 선택 GET을 포함하며 최종 90개와 구분한다. 스트레스 테스트는 수행하지 않았다.

아래 모든 시간은 초. 각 셀은 **중앙값 / 최소 / 최대**, n=3. TCP/TLS는 DNS/연결 완료 누적값에서 차감한 단계 시간. TTFB는 요청 시작부터 첫 바이트까지여서 서버 순수 처리시간과 다르다. 전송은 total−TTFB이며 백엔드 직렬화는 TTFB에도 포함될 수 있다.

### API 우선순위와 해석

**간헐성:** 직접 홈 병렬 최대8.451s, 내부 프록시 개별 대시보드 최대14.612s였다. 이후 공개 HTTPS 개별 호출은 전체0.055~0.369s였다. 요청 순서/워밍/동시 활동이 다르므로 프록시보다 공개 경로가 빠르다는 인과 결론을 내리지 않는다. 지속 지연 대신 긴 tail과 큰 변동성이 확인됐다.

최종 공개 HTTPS 개별 중앙값 순위: 대시보드 0.255s > 최근 매수(전체 Lot) 0.238s > 목표가 도래 0.145s > 1개월 자산추이 0.122s > 계좌 목록 0.115s. n=3의 해당 시간대 순위이며 고정된 서비스 병목 순위로 일반화하지 않는다. 경로를 순차 측정했으므로 서로 다른 경로의 중앙값을 빼서 프록시 비용으로 해석하지 않는다.

- 최근 매수: 전량 Lot·관계 데이터 로딩, 모든 Lot 평가·Decimal 계산·매도 이력 매핑 후 응답 생성. UI는 전량 정렬 후 최초 5건 표시. 가장 명확한 제거 가능 낭비다.
- 대시보드: loadPortfolio 전량 조회·계산 후 스냅샷/입출금 추가 조회. 오늘 자산추이도 loadPortfolio를 호출하여 동시 중복 계산한다.
- 자산추이: trend 분기로 원장/목표 계산은 이미 생략되지만 오늘 live closing을 위해 여전히 전체 포트폴리오 조회. 18차에서는 기존 최적화에 중복 제안하지 않는다.
- 목표가 도래: 응답이 작은 경우도 모든 매수/매도/가격을 읽어 평가한다. 작은 본문이 작은 DB 작업을 의미하지 않는다.
- 계좌 목록: 전체 Lot는 읽지 않으며 계좌와 최신 현금 거래만 조회한다. 이것까지 느린 공통 원인은 paging/I/O wait, 이벤트 루프 또는 DB/스케줄 대기를 의심해야 한다. 하나의 큰 최근 매수 응답 전송만으로 설명되지 않는다.

사용자 제공 오전 외부 n=3 중앙값 계좌 6.36s, 대시보드 6.86s, 추이 7.00s, 목표가 6.35s, 최근 매수 7.52s(5.65~14.57s 전체 범위)는 별도 배경 자료다. 정확한 샘플 시각/배포/세부 단계가 없어 이번 결과와 개선 전후 수치로 직접 비교하지 않는다.

## DB·백엔드 근거와 미확인

- DB 관찰: 연결 17→16, running 1(진단 SELECT 포함), 나머지 sleep 16→15. 집계된 최대 sleep 2,480→2,677초는 장기 실행 쿼리가 아니라 유휴 연결이다. 순간 관찰에 장기 활성 쿼리·현재 row lock wait 없음. 모든 측정 순간에 경합이 없었다는 뜻은 아니다.
- row lock 누적 시간 471→520ms, slow query 누적 23→25. 서버 가동 이후 카운터이며 증가분을 특정 API에 귀속할 수 없다. slow_query_log OFF, long_query_time 10s, performance_schema OFF라 기존 로그만으로 SQL별 지연 분리 불가. 전역 설정 변경하지 않았다.
- InnoDB buffer pool 128MiB, max_connections 151. 읽기 요청 누적 244,735,320→245,082,508(+347,188), buffer pool physical reads 23,196→23,197(+1). 이 제한된 구간에는 buffer miss로 발생한 DB 파일 읽기 폭증보다 OS swap/page-in이 중요한 후보다. 누적 hit ratio를 지금 지연 증거로 사용하지 않는다.
- backend DATABASE_URL의 pool query parameters 없음. Prisma 기본 pool 사용; 실측 queue/active pool metric 없음. 메모리 부족 환경에서 무조건 pool/max_connections를 키우면 메모리 수요와 동시 쿼리를 늘릴 수 있다.
- 기존 Fastify 로그(최종 재측정 전 20분, 다른 GET/health 제외 API 이름별 집계) 처리시간(ms): 계좌 n21 중앙값203.77/최소19.05/최대6793.06, 대시보드 n18 2481.78/169.92/14544.78, 추이 n18 1077.26/87.61/8921.50, 목표가 n18 435.97/91.68/7532.88, buy-lots n18 1634.00/155.77/15331.21. 조건이 다른 보조 호출이 섞여 있어 최종 API 비교 표로 쓰지 않는다. 서버 자체 처리 구간에 긴 지연이 있음을 뒷받침한다.
- Fastify responseTime은 handler/DB 대기/계산/직렬화 등을 합친 값이며 SQL 시간이나 pool wait를 개별로 제공하지 않는다. 이벤트 루프/GC 계측은 기존 코드에서 확인되지 않았다. 운영 Node에 inspector/GC tracing을 켜거나 임시 hook을 삽입하지 않았다. Decimal/날짜 평가의 동기 반복은 확인했지만 실제 CPU 프로파일은 미확인이다.

## 18차 개발 담당 전달안

1. **최근 매수 전용 경량 조회**: buyDate/boughtAt/id 안정 정렬을 서버에 구현, 최초 최근 5건과 필요한 필드만 제공하고 더보기는 기간/커서로 확장한다. 완료 Lot 표시, 최근 5건·월 확장 규칙, 날짜/KST, 같은 날짜 tie-break, 평가손익/수익률의 기존 의미를 유지한다. 매도 전체 배열·memo 등 홈 미사용 필드는 제외하고 필요한 합계를 사용한다. 단순 remainingOnly=true 변경은 완료 Lot를 제거하므로 기능 보존 대안이 아니다.
2. **포트폴리오 중복 계산 완화**: 동일 계좌의 dashboard/trend/targets에서 공통 데이터 로딩을 요청 병합 또는 짧은 캐시로 재사용. 계좌·가격 시각·매매/현금 변경 시 무효화와 사용자 데이터 격리를 명시한다. 통합 홈 요약 응답도 선택지지만 섹션별 오류 독립성과 갱신 정책을 보존해야 한다.
3. **조회 필드/범위 축소**: 종목·매도 이력 select, 필요한 잔여 수량/평가 집계, live closing 재사용. 전량 Lot를 읽은 뒤 필터하는 패턴을 줄인다. 계산 정확성을 보존하는 기준 테스트로 확인한다.
4. **현금 최신 거래 인덱스 검토**: 대표 EXPLAIN 이후 실제 Prisma SQL의 ORDER BY와 LIMIT를 확인하여 (account_id,created_at,id) 추가의 비용/효과를 격리 환경에서 검증. 코드 개선과 DB migration을 구분하여 별도 승인/배포한다.
5. **realtime 안정성**: heartbeat가 timer와 collector loop에서 겹칠 가능성, 1020 처리·동시 upsert·락 소유권/만료·재시도/backoff를 검토. 미처리 오류 종료와 자동 restart 반복을 막는 코드 수정안을 준비하되 수집 중단은 하지 않는다.
6. **관측성 후속 PR**: 민감정보 없는 route별 handler/DB acquisition/query/계산/직렬화 timing, 이벤트 루프 delay와 GC 요약, pool active/wait 계측을 코드 변경으로 제안. raw SQL parameter·계좌·요청 URL은 기록하지 않는다. 운영 global log 활성화는 별도 검토 대상이다.

이번 진단에는 코드/인덱스/설정 수정이 없다. 위 항목은 개발 담당이 구현할 제안이다.

## RAM 추가 효과·서버 변경 판단

- 현재 실메모리 압박에 따른 swap I/O가 관찰됐으므로 **RAM 추가 권고**. 기대효과는 자주 쓰는 backend/DB 페이지를 RAM에 유지하여 page-in과 디스크 대기를 줄이는 것이다. 예상 개선율이나 응답시간은 추정하지 않는다.
- **+1GB의 충분성 미확인**: 총 OS 인식 RAM은 단순 계산 약1.75GiB 수준이 될 수 있으나 실제 제공/예약량은 적용 후 확인한다. 현재 총 swap 약2GiB를 모두 활성 수요로 보지도, 1GB면 전부 해결된다고 보지도 않는다. 단계적 증설 후 working set·swap-in/out·수집 최대 부하를 다시 관찰한다. 지속 paging이면 추가 용량 또는 메모리 사용 개선 검토.
- 당장 CPU 증설·디스크 용량 확대를 먼저 할 근거는 약하다. 높은 steal과 가상 디스크 지연은 공급자에 별도 확인한다. **RAM 증설과 전량 조회 축소를 함께 우선**, 그 뒤 남는 쿼리·CPU·디스크 병목에 맞춰 변경한다.
- DB buffer pool은128MiB. RAM 추가 후 우선 그대로 두고 재측정한다. 현재 physical read 증가가1인 구간만 보고 pool 확대를 먼저 하지 않는다. 실제 DB working set·connection당 메모리와 다른 프로세스 예산을 반영해 필요할 때 조정한다.
- backend/DB/수집기는 hard memory limit 없음; 추가 RAM을 이용하는 데 제한 확대가 필수는 아니다. 프록시128MiB/frontend96MiB 한도는 호스트 RAM이 늘어도 그대로 유지된다. Node V8 기본 heap 한도가 RAM 인식 변화로 달라질 수 있으므로 실제 heap 수요를 확인하고 서비스별 예산을 정한다. 무조건 최대치를 늘리지 않는다. 프로세스별 pool도 예산에 맞춰 검토한다.
- [카페24 공식 가상서버 상품 안내](https://hosting.cafe24.com/?controller=new_product_page&page=virtual)에 RAM 추가 옵션이 있으나 현재 계약 상품·실제 주문 가능 옵션·청구금액·재부팅 필요성·중단 시간은 관리화면/고객지원에서 확인해야 한다. 이번 진단에서 신청하지 않았다. 상품 안내만으로 운영 계약에 적용되는 조건을 확정하지 않는다.

### 증설을 선택할 경우의 적용/복구 점검안 (미실행)

공급자에게 hot-add 가능 여부와 정지/재부팅 요구, 예상 창을 확인한다. 중단 시간은 아직 산정 불가; 호스트 재시작이 필요하면 종료+증설+부팅+DB recovery+healthy 및 검증 완료까지 서비스 중단으로 잡는다. 장중/예약 수집·배포 시간을 피한 점검 창과 롤백 경로를 별도 승인한다.

사전에는 복구 가능한 백업의 최신 시각·검증 상태, 볼륨/compose/실행 이미지, DB 정상 종료 절차, 수집 락·작업 진행 상태를 확인한다. 기존 백업이 있다는 사실만으로 최신 복구 가능성을 보장하지 않는다.

확인된 Docker 서비스 `enabled/active`, 모든 관찰 컨테이너 `restart=unless-stopped`. 이것은 부팅 복구 기대를 뒷받침하지만 수동 stopped 컨테이너, 부팅 순서·DB recovery·외부 공급자 연결 정상까지 보장하지 않는다.

재시작 후 점검 순서: OS RAM·swap·디스크 마운트 → Docker daemon enabled/active → DB volume/healthy/SELECT1 및 기존 데이터 확인 → backend healthy/DB 연결 → collector/DART/realtime 정상 heartbeat·lock 한 소유자·재시작 증가 없음 → proxy TLS 및 frontend → 5개 API 200·정상 크기/기능 → 자연 예약 수집 1회 정상 완료·중복 작업 없음. 시작 의존성과 healthcheck만으로 자동 복구를 가정하지 않는다. 실패 시 원문 비밀 없이 상태·오류 코드를 기록하고 합의한 복구 절차를 수행한다.

## 개선 전후 재측정 계획

동일 배포·계좌·기간·파라미터·클라이언트 조건으로 경로별 개별 및 홈(계좌→4병렬) 각3회. 변경 전/후 커밋·UTC/KST 시작/종료 시각·응답 크기·상태·단계 시간을 남긴다. 보조 측정과 최종 측정, 서버 공개 주소와 외부 모바일 측정을 구분한다.

수집을 중단하지 않고 자연 idle 구간/VALUATION·DART·장중 realtime 구간을 각각 잡아 동시 vmstat/iostat와 프로세스 RSS/swap·container CPU/RAM·DB running/row lock·풀/쿼리/이벤트루프 지표를 확보한다. 첫 vmstat/iostat 누적 평균 제외, 시각을 붙인 1초 샘플로 요청 구간에 매칭한다. 이번 vmstat는 연속 구간 관찰로 상관을 확인했으나 각 요청별 시각 매칭을 자동화하지 못했다.

성공 판단은 중앙값뿐 아니라 최대값/변동성·계좌 지연과 home 병렬 완료 지연, 지속 swap-in/out 및 I/O wait 감소, 정상 수집 유지로 한다. 단3회로 p95/p99를 발표하지 않는다. 재부팅 직후 cache warming 효과를 증설 효과와 혼동하지 않도록 안정화 후 동일 조건으로 다시 측정한다. 실제 모바일 앱은 별도로 계좌 요청 시작→필요 섹션 표시까지 trace하여 네트워크/서버/렌더링을 분리한다.
