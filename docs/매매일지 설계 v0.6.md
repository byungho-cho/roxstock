**버전:** v0.6  
**부제:** 계좌 관리·초기 진입·기본 계좌 규칙 현행화

# 1. 설계 결론

- 매수와 매도는 `buy_trades`, `sell_trades`로 분리합니다.
- 한 매수는 하나의 독립된 Lot이며 여러 매도를 가질 수 있습니다.
- 한 매도는 반드시 하나의 매수 Lot만 참조합니다.
- 여러 매수 Lot을 한 번에 매도하는 기능은 제공하지 않습니다.
- 보유현황은 조회 시 계산하며 `positions` 테이블을 저장하지 않습니다.
- 예수금은 `accounts.cash_balance`에 현재 실제 금액을 유지합니다.
- 거래·배당·예수금 변동은 최초 등록 때만 현재 예수금에 자동 반영합니다.
- 거래·배당·예수금 내역 수정·삭제 시 현재 예수금을 다시 계산하지 않습니다.
- 현재가, 일별 스냅샷, 가치투자 정보와 복리계획별 여러 하위 목표를 관리합니다.
- Figma는 화면 표현 기준이고, 계산·데이터 충돌 시 이 설계서의 업무 규칙을 우선합니다.

# 4. 매수·매도

## 4.1 매수 Lot

`buy_trades` 한 행이 매수 Lot 한 건입니다. 현재 보유수량과 종목 전체 평균단가는 조회 시 계산할 수 있지만, 평균단가는 매도 연결이나 실현손익 원가로 사용하지 않습니다.

## 4.2 매도

`sell_trades.buy_trade_id`는 한 `buy_trades.id`만 참조합니다. 잔여수량보다 많은 매도는 허용하지 않습니다.

```text
잔여수량 = 매수수량 - 연결된 매도수량 합계
실현손익 = 매도수량 × (매도단가 - 연결된 매수단가)
```

실현손익, 잔여수량과 총거래금액은 저장하지 않고 조회 시 계산합니다.

## 4.3 수정과 삭제

- 거래 수정은 매수·매도 기록만 변경하고 현재 예수금을 다시 반영하지 않습니다.
- 연결된 매도가 없는 매수는 바로 삭제할 수 있습니다.
- 연결된 매도가 있는 매수는 연결 매도 건수를 포함한 확인창을 표시합니다.
- 사용자가 확인하면 연결 매도를 먼저 삭제하고 매수를 삭제합니다.
- 연결 매도와 매수 삭제는 하나의 DB 트랜잭션으로 처리합니다.
- DB FK는 `ON DELETE RESTRICT`로 유지합니다.
- 일괄삭제 UI와 소프트 삭제는 제공하지 않습니다.
- 거래 삭제로 예수금과 과거 스냅샷을 자동 변경하지 않습니다.

# 5. 예수금과 거래비용

## 5.1 현재 예수금

`accounts.cash_balance`는 현재 증권계좌에서 확인한 실제 예수금입니다. 사용자는 이 값을 직접 수정할 수 있고 보정 이력은 따로 저장하지 않습니다.

## 5.2 예수금 변동

`cash_transactions.transaction_type`은 다음 값을 사용합니다.

```text
BUY, SELL, DEPOSIT, WITHDRAWAL, DIVIDEND
```

| 유형 | 최초 등록 시 현재 예수금 계산 |
|---|---|
| BUY | 이전 예수금 - 매수금액 - 수수료·세금 |
| SELL | 이전 예수금 + 매도금액 - 수수료·세금 |
| DEPOSIT | 이전 예수금 + 입금액 |
| WITHDRAWAL | 이전 예수금 - 출금액 |
| DIVIDEND | 이전 예수금 + 세후 배당금 |

수수료와 세금은 `fee_tax_amount` 하나로 통합합니다. 거래·배당 테이블과 예수금 내역 사이에는 FK를 두지 않습니다.

거래·배당·예수금 변동 내역은 최초 등록할 때만 현재 예수금에 반영합니다. 이후 수정·삭제 시에는 비용 차액을 포함하여 현재 예수금을 자동 변경하지 않습니다. 실제 잔액과 차이가 있으면 사용자가 `accounts.cash_balance`를 직접 수정합니다.

```text
월별 비용 = 해당 월 fee_tax_amount 합계
연도별 비용 = 해당 연도 fee_tax_amount 합계
```

## 5.3 예수금 화면

- 현재 예수금과 마지막 갱신시각을 표시합니다.
- 월간·연간 정보를 하나의 통합 기간 카드에서 전환합니다.
- 최초 진입은 현재 월의 월간 상태입니다.
- 월간과 연간의 마지막 조회 기간을 각각 보존합니다.
- 월간은 출금·입금·배당을, 연간은 연간 합계를 표시합니다.
- 기간은 좌우 버튼과 스와이프로 순환 탐색합니다.
- 최근 변경은 `구분 | 날짜 | 금액` 3열로 최신 10개를 표시합니다.
- `이전 1개월 불러오기`로 과거 내역을 추가합니다.
- 데이터가 없는 기간도 같은 구조의 빈 상태로 표시합니다.
- Figma 삭제 확인창의 “삭제하면 예수금에서 제외” 문구는 사용하지 않습니다.
- 수정·삭제 화면에는 현재 예수금이 자동 변경되지 않는다는 안내를 표시합니다.

# 6. 배당

`dividends`에는 세전 `gross_amount`와 세후 `net_amount`를 함께 저장합니다.

```text
배당소득세 = gross_amount - net_amount
연도별 실수령 배당금 = 해당 연도 net_amount 합계
```

배당 최초 등록과 세후 금액의 예수금 증가는 한 DB 트랜잭션으로 처리합니다. 이후 배당 수정·삭제는 현재 예수금을 자동 변경하지 않습니다.

# 7. 종목목록과 가치투자

## 7.1 통합 목록

`watchlist_items.list_type`은 `WATCHLIST`, `HOLDING`, `RECOMMENDED` 중 하나입니다. `security_id`에 UNIQUE를 적용하여 한 종목이 여러 탭에 중복되지 않게 합니다.

- 매수 후 잔여수량이 생기면 `HOLDING`으로 변경합니다.
- 전량 매도하면 `WATCHLIST`로 변경합니다.
- 전체 목록을 한 번 조회하고 React에서 `list_type`으로 필터링합니다.
- 관심·보유·추천 탭은 양방향 무한 순환합니다.

## 7.2 보유종목

- 보유수량·매수단가·매입금액·현재가·평가금액·평가손익·수집상태를 표시합니다.
- 종목 상세는 `요약 | 보유 현황 | 거래내역` 탭을 제공합니다.
- 보유 현황은 Lot별 보유일, 잔여수량, 매수금액, 예상 평가와 목표수익률별 단가·총액을 표시합니다.
- 거래내역은 매수와 연결 매도를 한 묶음으로 표시합니다.
- 매수 후 평균단가는 종목 전체 참고값으로만 표시합니다.

## 7.3 관심·추천과 가치분석

- 관심·추천 목록은 현재가, 등락, PER, PBR, ROE, W 값과 메모를 표시합니다.
- 가치분석은 RIM 기준 W별 적정주가와 상승여력을 제공합니다.
- 재무지표는 연간·분기 전환과 수익성·안정성·성장성 항목을 제공합니다.
- 직접 수정 화면에서는 자동 계산 지표와 계산 기초 데이터를 함께 보여줍니다.

# 8. 현재가와 수집

## 8.1 수집 계층

`market_prices`는 종목별 최신 가격 한 행만 유지합니다. 전체 종목의 종가 보정과 사용자가 실제로 보는 선택 종목의 장중 시세를 서로 다른 작업으로 분리합니다.

| 작업 | 대상 | 기본 일정·주기 | 결과 |
|---|---|---|---|
| 종목 마스터 | KOSPI·KOSDAQ 전체 활성 종목 | 매일 07:00 | `securities` UPSERT |
| 장중 실시간 시세 | `HOLDING + WATCHLIST + RECOMMENDED` 합집합, 최대 100종목 | 평일 프리 08:00~08:50, 정규 09:00~15:30, 애프터 15:40~20:00, 60초 | 메모리 캐시 갱신 및 SSE 전송 |
| 실시간 DB 반영 | 위 장중 실시간 대상 | 60초 | `market_prices` UPSERT |
| 장 마감 시세 | 전체 활성 종목 | 매일 20:00, 1회 | `market_prices` 최종 UPSERT |
| 계좌 스냅샷 | 전체 계좌 | 매일 23:00, 1회 | `daily_account_snapshots` UPSERT |

모든 시각은 `Asia/Seoul` 기준입니다. 장중 실시간 수집의 기본 간격은 60초이며 환경변수로 최소 5초까지 조정할 수 있습니다. 공식 호출 한도가 보장되지 않은 외부 원천의 부하와 개인용 화면의 실시간성 요구를 함께 고려해 운영 기본값은 60초로 유지합니다.

NXT 프리마켓 종료 후 정규장 시작 전인 08:50~09:00과, KRX 종가 형성 후 NXT 애프터마켓 시작 전인 15:30~15:40에는 수집을 멈춥니다. NXT 거래 대상이 아닌 종목은 프리·애프터 세션에서 기존 마지막 정상 KRX 가격을 유지하며 0원이나 빈 값으로 덮어쓰지 않습니다.

## 8.2 실행 프로세스

- Fastify API, 일일 배치 수집기, 장중 실시간 수집기는 각각 독립 프로세스와 Docker Compose 서비스로 실행합니다.
- 장중 실시간 수집기의 장애·재시작은 API 서버와 일일 배치 수집기를 중단시키지 않습니다.
- 공통 Prisma 연결, 가격 타입, 공급자 인터페이스와 로깅은 기존 백엔드 코드를 공유합니다.
- 장중 대상은 `watchlist_items`의 세 분류를 합쳐 만들고 `security_id` 기준으로 중복 제거합니다.
- 보유·관심·추천 분류가 변경되면 다음 대상 갱신 회차에 자동 반영합니다.
- 보유종목은 실제 잔여수량이 있는 거래 데이터를 기준으로 유지하며 사용자가 임의로 분류를 변경하지 않습니다.

## 8.3 실시간 전달과 저장

1. 실시간 수집기가 선택 종목 시세를 60초 간격으로 수집합니다.
2. 유효한 가격을 수집기 프로세스 메모리 캐시에 즉시 반영합니다.
3. 수집기는 Bearer 토큰으로 보호된 내부 `POST /internal/realtime-prices`를 호출하여 API 프로세스 캐시로 전달합니다.
4. API는 SSE(Server-Sent Events)로 연결된 React 화면에 변경 가격을 전송합니다.
5. 프론트엔드는 SSE 메시지를 받으면 해당 종목만 갱신합니다.
6. SSE 연결이 끊기면 최신 가격 REST API를 10초 간격으로 조회하는 폴백을 사용합니다.
7. DB 쓰기 부하는 줄이기 위해 수집기 캐시의 최신 정상 가격을 기본 60초마다 `market_prices`에 UPSERT합니다.
8. API 전달 실패와 관계없이 DB 저장은 계속하며, 20시 전체 종목 수집 결과가 당일 최종 마감 가격을 보정합니다.

SSE는 서버에서 브라우저로의 단방향 가격 전달에 적합하며 React에서는 하나의 연결을 공유합니다. 화면·탭별로 별도 외부 시세 요청을 생성하지 않습니다.

## 8.4 외부 원천과 호출 제어

1차 가격 원천은 네이버 금융 브라우저용 polling JSON 응답을 사용합니다. 공식 공개 API가 아니므로 응답 형식과 접근 정책이 바뀔 수 있으며 공급자 코드는 인터페이스 뒤에 격리합니다.

- 종목코드는 `securities.symbol`의 6자리 코드를 사용하고 `A005930` 형식은 `005930`으로 정규화합니다.
- 프리·애프터마켓에서는 `overMarketPriceInfo.overMarketStatus=OPEN`이고 세션이 `PRE_MARKET` 또는 `AFTER_MARKET`일 때 `overPrice`와 해당 `localTradedAt`을 사용합니다.
- 정규장에서는 기본 현재가와 거래시각을 사용합니다. API의 `marketStatus`는 NXT 세션일 때 `NXT_PRE_MARKET` 또는 `NXT_AFTER_MARKET`으로 전달합니다.
- 동시 요청 수는 기본 5개로 제한하고 전체 회차가 끝나기 전에 다음 회차를 겹쳐 실행하지 않습니다.
- 공급자가 다중 종목 응답을 안정적으로 제공하는 것이 확인되면 배치 단위 호출로 교체할 수 있습니다.
- 인증이 필요한 원천을 추가할 때 키는 환경변수로만 관리하고 Git에는 저장하지 않습니다.
- 원천별 응답 변환은 공급자 모듈에서 처리하여 수집·저장 로직과 분리합니다.

## 8.5 정합성·실패 처리

- 가격이 0, 빈 값, 비정상 숫자이면 저장하거나 전송하지 않습니다.
- 수집 실패 시 마지막 정상 가격을 캐시와 DB에 유지합니다.
- 사용자가 수동 수정한 가격은 다음 정상 자동 수집 성공 시 갱신합니다.
- 공급자 응답의 거래시각 `providerTimestamp`가 현재 저장값보다 오래되면 덮어쓰지 않습니다.
- 휴장일, 장 운영상태 종료, 거래시각 미갱신은 성공과 구분하여 `STALE` 또는 `SKIPPED`로 기록합니다.
- 개별 종목 실패는 다른 종목의 수집을 중단시키지 않습니다.
- 동일 실시간 회차의 중복 실행은 프로세스 락으로 차단하고, 여러 인스턴스 운영 시 DB 락을 함께 사용합니다.
- 실행 시작·종료, 대상 수, 성공·실패·STALE 수, 종목별 실패 사유를 구조화 로그에 남깁니다.
- 수집상태는 영구 가격 데이터보다 최신 수집 실행 결과와 응답 상태로 우선 제공합니다.

# 9. 스냅샷

## 9.1 계좌 스냅샷

`daily_account_snapshots`는 `cash_balance`, `stock_value`, `total_asset_value`를 저장합니다. `account_id + snapshot_date`를 UNIQUE로 둡니다.

## 9.2 종목 스냅샷

`daily_position_snapshots`는 종목별 수량, 매입금액, 현재가, 평가금액과 미실현손익을 저장합니다. 종목별 스냅샷은 선택 구현입니다.

## 9.3 실행 규칙

- 현재 운영 기본값은 한국 시간 23시 1회 실행이며 같은 계좌·날짜를 UPSERT합니다.
- 향후 장중 자산 추이가 필요하면 1시간 간격 갱신을 선택적으로 활성화할 수 있습니다.
- 한국 시간 23시 실행을 당일 마지막 예정 갱신으로 사용합니다.
- `is_final`은 두지 않습니다.
- 시세가 없으면 잘못된 0원 스냅샷을 만들지 않습니다.
- 거래나 예수금 변경으로 과거 날짜 스냅샷을 수정하지 않습니다.

# 10. 복리계획과 복리목표

Figma 최종 통합 구조인 `복리계획 1 : 복리목표 N`을 사용합니다. 1차·2차·3차처럼 기간이 다른 차수는 계획이고, 같은 기간의 안정형·기준형·공격형은 하위 목표입니다.

## 10.1 복리계획

`compound_growth_plans`는 계좌, 계획명, 시작일, 종료일, 시작자산, 연간 추가 투자금, 표시순서와 상태를 저장합니다.

## 10.2 하위 목표

`compound_growth_goals`는 `plan_id`, 목표명, 연 목표수익률, 표시색상, 기본 목표 여부, 표시 여부와 표시순서를 저장합니다.

- 계획을 만들면 기준형 목표 한 개를 자동 생성합니다.
- 계획 목록의 올해 목표·최종 목표·진행률은 기본 목표 기준입니다.
- 기본 목표 변경은 확인창을 거칩니다.
- 시작연도 선택 시 5년 범위를 제안하지만 시작·종료연도를 수정할 수 있습니다.
- 같은 연도를 선택한 1년 계획도 허용합니다.
- 화면에는 일반적으로 목표 3개를 우선 표시하지만 저장 개수에는 제한이 없습니다.

## 10.3 계산 기준

연간 추가 투자금은 첫해부터 연초에 기초자산에 더한 뒤 해당 연도의 목표수익률을 적용합니다.

```text
첫해 목표자산
= (시작자산 + 연간추가금) × (1 + 목표수익률)

다음 해 목표자산
= (직전 목표자산 + 연간추가금) × (1 + 목표수익률)
```

Figma에 표시된 연말 추가 방식의 예시 금액과 안내문은 구현 기준으로 사용하지 않습니다. 화면 예시 데이터는 위 공식에 맞춰 교체합니다.

# 12. 화면별 설계

## 12.1 홈과 평가자산

- 화면 제목은 `대시보드`, 하단 메뉴명은 `홈`입니다.
- 평가자산·오늘손익은 적색, 주식평가액은 연두색, 예수금은 노란색을 사용합니다.
- 평가자산·예수금·오늘손익·자산추이 카드는 각각 관련 상세 화면으로 이동합니다.
- 보유종목 제목은 목록으로, 개별 행은 해당 종목 상세로 이동합니다.
- 평가자산 화면은 `매입금액 | 평가손익 | 주식평가액`과 전일 대비를 제공합니다.
- 자산구성은 주식·예수금 금액과 비율을 표시합니다.
- 종목별 비중 카드는 `순위형 ↔ 누적형`으로 전환합니다.

## 12.2 매매일지와 일별손익

- 매매일지 기본 화면은 월간 달력입니다.
- 날짜별 매수·매도 건수와 선택 날짜의 거래 요약을 표시합니다.
- 월 이동은 버튼과 스와이프를 지원하고 최초 데이터 월과 현재 월 사이를 순환합니다.
- 일별손익은 전체손익, 평가손익, 실현손익, 종목별 기여도와 거래 현황을 표시합니다.
- 오늘 날짜에서는 다음 날짜 이동을 막고 과거 날짜에서는 `오늘` 바로가기를 제공합니다.
- 날짜 선택 영역은 세로 스크롤 시 상단에 고정합니다.

## 12.3 자산분석과 투자손익

- 자산추이는 `1개월 | 3개월 | 6개월 | 1년 | 전체`를 제공합니다.
- 기간 성과는 시작자산, 입금, 출금, 순입출금, 평가손익, 실현손익, 배당, 비용, 투자손익과 수익률을 제공합니다.
- 투자금 화면은 일별 평가금액과 투자금 추이를 함께 표시합니다.
- 투자손익은 연도별·종목별 전환을 제공합니다.
- 연도 상세에서는 종목별·월별 손익을 조회합니다.
- 종목 상세에서는 매수총액, 매도총액, 매매손익, 배당포함 총손익과 연도·월별 내역을 제공합니다.
- 연도 이동은 올해와 최초 데이터 연도가 이어지는 순환형 탐색을 지원합니다.

## 12.4 거래등록

- 매수는 거래일자, 수량, 단가와 메모를 입력하고 매수금액과 예상 거래 후 예수금을 표시합니다.
- 매도는 선택한 매수 Lot을 고정 표시하고 잔여수량 이내에서 수량과 단가를 입력합니다.
- 예상 실현손익은 선택한 Lot의 매수단가로 계산합니다.
- 거래 후 예수금은 최초 등록 시 예상값입니다.
- 수정 화면의 예수금은 참고값이며 저장 시 현재 예수금을 다시 반영하지 않습니다.
- 여러 Lot을 선택하거나 한 번에 매도하는 UI는 제공하지 않습니다.

## 12.5 더보기와 설정

- 더보기에는 평가자산, 예수금, 일별손익, 자산분석, 투자금, 투자손익, 복리계획, 가치분석, 재무지표, 시세수집과 설정 진입점을 제공합니다.
- 계좌 관리는 목록·추가·변경 공통 폼을 제공하며 현재 계좌 선택과 기본 계좌 지정 규칙은 19장을 따릅니다. 현재 실제 예수금은 별도 기능으로 직접 수정합니다.
- 현재가 수기 수정값은 다음 자동수집 성공 시 덮어씁니다.
- 테마는 다크·라이트·시스템을 제공하며 기본값은 다크입니다.

## 13.1 반응형 기준

커버 메뉴는 `종목목록 | 매매일지 | 홈 | 자산분석 | 더보기`입니다. 태블릿 확장 메뉴는 종목목록·매매일지·평가자산·예수금·홈·자산분석·재무제표·시세수집·더보기입니다. 거래등록은 메뉴가 아니라 공통 상단 `+` 액션입니다.

## 13.2 스와이프와 스크롤

- 동일 레벨의 탭·기간 화면은 좌우 스와이프를 지원합니다.
- 마지막 다음에 첫 화면, 첫 화면 이전에 마지막 화면이 이어지는 무한 순환을 지원합니다.
- 탭 클릭과 스와이프 선택 상태를 동기화합니다.
- 화면별 세로 스크롤 위치를 유지합니다.
- 입력폼·버튼·차트와 OS 뒤로가기 영역은 스와이프 대상에서 제외합니다.
- 세로 스크롤이 화면 높이의 40% 이상이면 하단 메뉴 위 우측에 최상단 이동 버튼을 표시합니다.
- 최하단에는 버튼과 마지막 항목이 겹치지 않도록 104px 이상의 안전 여백을 둡니다.

## 13.3 색상과 금액 단위

| 상태 | 색상 | 표시 |
|---|---|---|
| 상승·수익·입금·매도 | 밝은 적색 | `+`와 수익률 병기 |
| 하락·손실·출금·매수 | 밝은 청색 | `-`와 수익률 병기 |
| 보합 | 흰색 | `0` 또는 `0.0%` 병기 |
| 선택 메뉴 | 밝은 앰버 | 아이콘과 텍스트 강조 |

- 성공 녹색과 상승 적색은 다른 의미 토큰으로 관리합니다.
- 보유종목 수집상태는 정상=녹색, 일부 실패=노랑, 실패=적색입니다.
- 차트 금액은 10,000원 미만은 원, 이상은 만원 단위를 사용합니다.
- 1억원 이상도 억 단위로 바꾸지 않고 만원 단위를 유지합니다.

## 13.4 공통 상태와 입력

- 모든 화면은 기본, 선택, 비활성, 로딩, 빈 상태, 수집 실패, 입력 오류와 저장 성공 상태를 고려합니다.
- 입력 화면은 Figma 002 입력폼 표준을 재사용합니다.

# 14. 자산과 손익 계산

```text
Lot 평가금액 = 잔여수량 × 현재가
Lot 평가손익 = 잔여수량 × (현재가 - 매수단가)
주식 평가금액 = 모든 보유 Lot 평가금액 합계
총 평가자산 = 주식 평가금액 + 현재 예수금
현금 비중 = 현재 예수금 ÷ 총 평가자산 × 100
기간 투자손익 = 평가손익 + 실현손익 + 배당수익 - 수수료·세금
현재 총자산 = 기간 시작자산 + 순입출금 + 기간 투자손익
```

일별손익·기간성과·투자손익은 기존 거래·배당·예수금·스냅샷에서 계산하는 조회모델로 제공하며 별도 집계 테이블은 두지 않습니다.

# 19. 계좌 관리 설계 (v0.6)

## 19.1 확정 정책과 적용 범위

- **계좌번호는 신규 생성 시 필수**입니다. 계좌명은 중복을 허용하므로 계좌 식별과 중복 방지를 위해 증권사+번호를 사용합니다. 기존 계좌 중 번호가 없는 행은 이관 대상이며, 번호 보완 전에는 기존 데이터 조회가 가능하되 계좌 변경 시 번호를 입력하도록 안내합니다. NULL 행을 임의의 번호로 채우지 않습니다.
- **삭제는 물리 삭제가 아닌 비활성화**(`is_active=false`)입니다. Lot, 거래, 예수금, 배당, 스냅샷, 복리계획의 계좌 FK와 감사 가능한 내역을 보존합니다. 비활성화된 계좌는 일반 선택 목록과 계좌 의존 API에서 제외하며, 같은 증권사·번호의 재등록은 막고 기존 계좌의 재활성화는 계좌 목록의 비활성 항목에서 계좌 변경 화면을 열고 재활성화 동작을 통해 처리합니다.
- 활성 계좌가 하나라도 있으면 기본 계좌는 정확히 하나입니다. 기본 해제만 하는 요청은 거절하고 다른 계좌를 기본으로 지정합니다. 마지막 활성 계좌 비활성화는 허용하며 이때 기본 계좌는 없습니다. 계좌 재활성화로 첫 활성 계좌가 생기면 기본으로 자동 지정합니다.
- 기존 v0.5의 거래·예수금·Lot·스냅샷 계산 및 수정·삭제 규칙은 변경하지 않습니다.

## 19.2 목록·추가·변경 화면

| 화면 | 내용 | 행동 |
|---|---|---|
| 계좌 목록 | 활성 계좌 목록, 현재 선택 표시, 기본 계좌 표시 | 계좌 선택, 추가·변경 진입 |
| 계좌 추가 | 빈 공통 폼, 상단 뒤로가기·`계좌 추가` | `추가` 버튼 |
| 계좌 변경 | 기존 정보가 채워진 공통 폼, 상단 뒤로가기·`계좌 변경` | `변경` 버튼 |

공통 입력은 계좌명, 증권사명, 계좌번호(필수), 기본 계좌 사용 여부입니다. 첫 계좌에서는 기본 여부를 켠 상태로 고정합니다. 기존 유일한 활성 계좌에서도 기본 여부를 끌 수 없습니다. 기존 기본 계좌를 변경하면서 기본 여부만 해제하는 요청은 `409 DEFAULT_ACCOUNT_REQUIRED`로 거절합니다. 계좌 변경 화면의 비활성화와 비활성 계좌 재활성화는 각각 별도 확인을 거칩니다. 저장 버튼은 저장 중 중복 입력을 막습니다. Figma 002 입력폼 표준과 화면 레이아웃·스크롤 명세를 따릅니다.

## 19.3 계좌가 없는 초기 진입과 상태 구분

1. `GET /api/accounts` 응답을 받은 뒤 **활성 계좌**만 대상으로 선택 상태를 결정합니다. 목록 응답이 `[]`이거나 모두 비활성 계좌이면 계좌 의존 API를 호출하지 않습니다.
2. 조회 중에는 로딩, 조회 실패에는 오류 메시지와 재시도를 각각 표시합니다. 실패를 계좌 없음으로 오인하지 않습니다.
3. 활성 계좌가 없으면 `등록된 계좌가 없습니다.`와 `계좌 추가` 버튼을 표시합니다. 첫 계좌 생성 성공 시 서버에서 기본 계좌가 지정되고 해당 ID를 현재 선택한 뒤 대시보드를 조회합니다.
4. 계좌는 있으나 기본 계좌가 없는 기존 데이터에서는 활성 목록 첫 번째(표시 순서→ID 순)를 임시 선택하고 기본 지정 안내를 표시합니다. 서버는 데이터 정합성 복구를 별도로 수행합니다.
5. 마지막 활성 계좌 비활성화 성공 직후 현재 계좌 ID와 계좌별 캐시를 비우고 계좌 없음 화면으로 전환합니다.

## 19.4 정규화와 중복

- 계좌번호는 Unicode NFC 적용 후 앞뒤·중간의 모든 공백과 ASCII 하이픈(`-`)을 제거한 문자열을 정규화 값으로 보관합니다. 정규화 후 빈 값이면 `400 INVALID_INPUT`입니다. `1234-56-7890`, `1234567890`, `1234 56 7890`은 같습니다.
- 증권사명은 Unicode NFC, 앞뒤 공백 제거, 연속 공백 1칸 축약 후 표시값으로 보관합니다. 별도 `broker_key`는 동일 규칙과 영문 대소문자 접기를 적용한 비교값입니다. 국내 증권사 영문 대소문자 차이만으로 별개 계좌를 만들지 않습니다.
- `UNIQUE(broker_key, account_number_normalized)`는 비활성 계좌까지 포함합니다. 동일 계좌 변경 시 자신의 ID는 제외하고 검사하지만 최종 판정은 DB UNIQUE에 맡깁니다.
- 계좌명 중복은 허용합니다. 생성·변경의 중복은 모두 `409 ACCOUNT_ALREADY_EXISTS` / `이미 등록된 증권사와 계좌번호입니다.`로 통일합니다.
- 기존 데이터 이관 전에 동일 정규화 키 충돌을 보고하고 해결한 뒤 제약을 추가합니다. 프론트 사전 검사는 편의 기능이며 동시에 들어온 요청도 DB 제약이 최종 차단합니다.

## 19.5 기본 계좌와 계좌 선택

- 첫 활성 계좌 생성은 요청의 기본 여부와 관계없이 기본으로 지정합니다.
- 새 계좌를 기본으로 지정하면 기존 기본 표시를 해제하고 새 계좌를 지정합니다. 기본 계좌가 비활성화되면 남은 활성 계좌 중 `display_order, id` 오름차순 첫 계좌를 자동 지정합니다.
- 기본 변경·비활성화·재활성화는 각각 하나의 DB 트랜잭션으로 실행합니다. 동시 요청은 계좌 관리 작업을 직렬화하고 DB 유일 제약 및 충돌 재시도로 한 개의 기본 계좌만 유지합니다.
- 프론트 선택 우선순위: **사용자가 선택한 활성 계좌 → 서버 기본 활성 계좌 → 첫 활성 계좌**입니다. 사용자가 선택한 계좌 ID는 브라우저 저장소에 유지하되 서버가 비활성이라고 응답하면 버리고 다시 선택합니다.
- 대시보드·보유종목·매매일지·예수금·매수·매도·입금·출금·스냅샷·자산분석 모두 같은 선택 계좌 ID를 사용합니다. 계좌 전환 시 계좌별 React Query 키에 `accountId`를 포함하고 이전 계좌 데이터를 즉시 숨긴 뒤 새 계좌로 조회합니다. 등록·변경·비활성화 이후 계좌 목록과 관련 화면 캐시를 무효화합니다.
- 비활성 계좌를 지정한 계좌 의존 조회·거래 요청은 `404 ACCOUNT_NOT_FOUND`로 처리합니다.

## 19.6 계좌와 데이터 관계 및 이관

`accounts`는 `buy_trades`, `cash_transactions`, `dividends`, `daily_account_snapshots`, `daily_position_snapshots`, `compound_growth_plans`의 부모입니다. `sell_trades`는 참조하는 매수 Lot을 통해 계좌에 귀속됩니다. 기존 FK 제한을 유지하여 관련 데이터 삭제가 암묵적으로 전파되지 않게 합니다. 비활성화는 과거 내역과 스냅샷을 보존하며 신규 거래와 현재 선택을 중단합니다.

이관 순서: 기존 계좌번호 누락·정규화 중복 조사 → 사용자 보완·중복 해소 → `broker_key`, `account_number_normalized`, `is_default` 추가 및 백필 → UNIQUE/기본 유일 제약 적용 → 백엔드 변경 API 배포 → 프론트 계좌 선택·빈 상태 배포. 기존 기본값은 활성 목록 첫 계좌에 부여합니다. 이관 전 NULL 계좌번호가 남아 있으면 신규 생성의 필수 검증과 기존 조회는 분리하고, NOT NULL 제약은 보완 완료 후 적용합니다.

## 19.7 구현·검증 범위

계좌 API 요청·응답과 오류 표준은 `docs/api/계좌보유대시보드API.md` v0.2를 따릅니다. 폼과 빈 상태는 디자인 담당이 커버 400×640·펼침 816×616에 반영합니다. 백엔드·DB와 프론트엔드 작업은 계좌번호 이관 상태와 API 계약을 공유한 뒤 병행합니다. QA는 최초 생성, 번호 형식별 중복, 자기 자신 변경, 동시 생성, 기본 변경, 마지막 비활성화, 계좌 전환 후 이전 데이터 미노출을 검증합니다.

# 20. 테스트용 계좌 데이터 초기화 (v0.6 추가)

## 20.1 목적·제공 위치

개발과 API 연동 테스트 중 선택한 **계좌의 기록만** 다시 시작하기 위한 `더보기 > 설정 > 계좌 데이터 초기화` 기능입니다. 이는 테스트 서버에서만 제공하며 실사용 전 제거하거나 관리자 전용으로 전환합니다. 계좌 비활성화와 다른 동작입니다. 초기화 후에도 계좌 ID·계좌명·증권사·계좌번호·기본 여부·활성 여부는 그대로 유지합니다.

## 20.2 실제 Prisma 모델 기준 범위

| 데이터 | 관계 | 처리 |
|---|---|---|
| `sell_trades` | 해당 계좌 `buy_trades`를 통해 귀속 | 해당 Lot의 매도 행 삭제 |
| `buy_trades` | `account_id` | 해당 계좌 Lot 삭제, 보유수량은 조회 시 0 |
| `cash_transactions` | `account_id` | BUY·SELL·DEPOSIT·WITHDRAWAL·DIVIDEND 유형 전부 삭제 |
| `dividends` | `account_id` | 해당 계좌 행 삭제 |
| `daily_position_snapshots` | `account_id` | 현재·향후 저장된 해당 계좌 행 삭제 |
| `daily_account_snapshots` | `account_id` | 해당 계좌 행 삭제 |
| `compound_growth_goals`와 `compound_growth_plans` | 목표→해당 계좌 계획 | '해당 계좌의 사용자 데이터 모두 제거' 기준으로 목표를 먼저 지운 뒤 계획 삭제 |
| `accounts.cash_balance` | 해당 계좌 한 행 | 0으로 설정, 계좌 자체 및 기본 여부 보존 |
| 계좌별 향후 집계·캐시 | 계좌 ID 스코프 | 해당 계좌 키만 제거하고 계산값은 새 조회로 재생성 |
| `watchlist_items` | 현재는 `security_id`만 있고 `account_id` 없음 | **공통 목록이므로 보존**. 계좌별 관심·추천 연결 테이블을 추가하는 경우에만 그 계좌의 연결 행을 초기화 대상에 추가 |
| `securities`, `market_prices`, 재무·가치지표, 수집 기록·캐시 | 전체 공통 | 보존 |
| 다른 계좌의 모든 행 | 다른 `account_id` | 보존 |

현재 보유종목은 저장된 별도 `positions` 테이블이 아니라 잔여 매수 Lot에서 계산합니다. 별도 계좌별 종목 연결 테이블도 현재 없습니다. 따라서 매수 Lot과 매도 내역을 지우면 해당 계좌의 보유종목이 없어지며, 공통 관심·추천 목록은 남습니다.

## 20.3 완료 상태와 이후 데이터

초기화 성공 직후 해당 계좌의 거래·입출금·배당·보유종목·계좌별 복리계획·기존 일별 스냅샷은 비어 있고, 예수금은 0원입니다. 실현손익 및 주식평가액·총평가자산은 0원으로 표시할 수 있으나 값이 없는 기간 성과·수익률과 과거 차트는 `데이터 없음`으로 표시합니다. 가격 수집 결과는 공통 데이터이므로 계속 남습니다. 초기화 뒤 새로운 거래 또는 다음 스냅샷 작업이 실행되면 해당 날짜의 새로운 데이터는 다시 생성될 수 있습니다.

## 20.4 화면과 API 보호

- 설정 화면에는 현재 선택 계좌명과 지워지는 범위를 먼저 표시합니다. ‘초기화’ 첫 클릭에서 확인창을 열고, 계좌명을 직접 입력해 일치할 때만 최종 실행 버튼을 활성화합니다. 진행 중 중복 제출을 막습니다.
- 서버는 별도 테스트 환경 활성 플래그와 **서버에서 검증하는 관리자 접근 제한**이 함께 있을 때만 초기화 API를 허용합니다. 프론트 빌드 환경변수나 숨겨진 버튼만으로 접근을 제한하지 않습니다. 검증 수단이 마련되기 전에는 API를 비활성화합니다. 실사용으로 전환할 때 기본값은 비활성화입니다.
- 서버는 계좌 ID, 활성 계좌 여부, 확인 문자열, 권한을 검증합니다. 전체 `TRUNCATE`/무조건 `deleteMany()`는 금지합니다. 대상 계좌 ID로 모든 삭제를 제한하고, 매도→매수·목표→계획처럼 FK 자식부터 삭제합니다.
- 초기화와 예수금 0원 반영은 하나의 DB 트랜잭션으로 처리합니다. 같은 계좌에 대한 거래 쓰기·일별 스냅샷 생성과 초기화가 서로 끼어들지 않도록 계좌별 잠금 또는 동일한 직렬화 경로를 사용합니다. 실패하면 전부 롤백합니다.
- 성공 응답에는 계좌 ID, 삭제 건수, `cashBalance:"0"`을 제공하고 개인 정보·전체 거래 내역을 포함하지 않습니다. 프론트는 계좌별 캐시 및 해당 계좌의 화면 상태를 비운 뒤 계좌 목록·대시보드·보유종목·매매일지·예수금을 재조회합니다. 선택 계좌 ID와 기본 여부는 유지합니다.
- 초기화는 복원할 수 없습니다. 실제로 실행할 때의 접근 제한과 별개로 DB 백업 절차는 운영 담당이 점검합니다.

## 20.5 검증

테스트 계좌 A와 다른 계좌 B에 서로 다른 거래·배당·입출금·스냅샷·복리계획을 넣고 A만 초기화합니다. A의 자식 데이터·예수금만 지워지고, 계좌 자체·기본 여부·B의 모든 데이터·공통 종목·가격·관심·추천 목록이 보존되는지 확인합니다. 중간 삭제 실패 시 전체 롤백, 중복 요청, 다른 계좌의 동시 거래, 스냅샷 작업 경합, 접근 권한 거절, 캐시 갱신을 검증합니다.
