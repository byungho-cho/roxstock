# 수동 재무 갱신 대기·자동 보완 수집기 메모리 부족 운영 조사

팀장 검토용. 모든 시각은 **2026-10-17 KST**이며 날짜가 다른 경우 별도로 적었다. 운영 변경 없이 조사했다. 조사 종료 기준은 20:14경이다.

## 결론과 결정 요청

- 삼성전자 요청 10243의 대기는 **자동 보완 작업이 획득한 공용 실행 잠금이 프로세스 힙 부족 종료 후 남아 있었기 때문**으로 확인했다. 잠금 소유자, 실패 로그, 만료 직후 수동 처리 시작이 연결된다.
- 자동 보완기는 대상 유무를 알기 전에 잠금을 잡고, 큰 범위의 재무제표·가치지표를 메모리에 읽은 뒤 최대 10개를 선택한다. **대상이 없었다고 확인된 것은 아니다.** 대상 확정 전에 프로세스가 종료됐고 실행 이력 생성에도 도달하지 못한 정황이다.
- 직접 종료 원인은 Node/V8 힙 한도 도달이다. 전체 자료를 읽는 무제한 후보 탐색이 가장 유력한 원인 지점이다. 힙 덤프·프로파일이 없으므로 특정 객체의 점유량, 누수 여부, 어느 await에서 종료됐는지는 미확인이다.
- 개선 권고: 후보 탐색을 페이지·필드 단위로 제한하고, 탐색과 실행 잠금을 분리하며, 실행 직전 소량 재검증을 수행한다. 수동 작업 우선권과 잠금 소유자 생존 확인도 보완한다. 단순히 잠금을 뒤로 옮기거나 메모리만 늘리는 것으로 끝내지 않는다.
- 이 브랜치는 **조사 문서만** 포함한다. 재시작·잠금 삭제·요청 초기화·재수집·운영 코드 수정·배포는 수행하지 않았다. 로그의 재시작은 기존 정책에 따른 자동 재시작이다.

## 메모리 부족: 사실과 추정

### 확인 사실

- 운영 컨테이너 Node `v20.20.2`, `NODE_OPTIONS` 없음. 같은 컨테이너 안의 별도 Node 프로세스에서 조회한 기본 heap_size_limit은 **913MiB**다. 장애 프로세스의 힙 스냅샷을 취득한 것은 아니다.
- Docker 설정 `Memory=0`, `MemorySwap=0`: 컨테이너별 명시적 메모리 한도 없음. `OOMKilled=false`. 커널 OOM kill이 아니라 로그상 **V8 자체 힙 한도 초과 종료**다.
- 19:41:59 GC: 약 888.9MiB에서 수거 후 888.7MiB. GC가 거의 회수하지 못하는 상태에서 heap limit 오류 발생.
- 이후 **19:56:58.364** 자동 보완 잠금 획득 → **19:57:38.226** 동일 heap 오류, **20:12:33.596** 잠금 획득 → **20:13:13.610** 동일 오류가 반복됐다.
- 19:55경 서버 총 메모리 약 1777MiB, available 약 985MiB, swap 사용 약 933MiB, load average 0.41/0.55/1.09. 이는 조사 순간의 값으로 오류 직전 서버 전체 압박이나 CPU 부족을 증명하지 않는다.
- 20:14경 DB 집계: 재무제표 68,774행, 가치지표 18,614행. 2015~2026 비철회 재무제표의 account_sources + source_validation 문자열 합계 **125.34MiB**, 같은 연도 가치지표의 values + supplemental 합계 **2.23MiB**.
- 이 집계는 DB 전체 범위의 문자열 바이트 크기이며, 활성 종목 필터·distinct 이후 실제 반환 크기 또는 JS 힙 사용량과 같지 않다.

### 코드에서 확인한 메모리 증가 구조

`collector/src/independent-valuation-supplement.ts:runIndependentSupplement`:

1. 공용 잠금을 900초로 먼저 획득한다.
2. 우선종목 정보를 읽는다.
3. 2015~현재 연도 재무제표를 `findMany` + distinct + receiptDate/collectedAt 정렬 + security include로 읽는다. `take`/커서가 없고 재무제표 scalar 필드 전체(JSON 포함)를 읽는다.
4. 같은 연도의 가치지표를 `values`, `supplemental` 포함해 모두 읽는다.
5. JS Map/filter/sort로 후보를 만들고 **마지막에야 slice로 최대 10개**를 고른다. 당일 제한 200개 확인에 필요한 정보도 후보 전체 조회를 막지 않는다.
6. 그 뒤에 실행 행을 만들고 외부 자료를 조회한다. 수동 작업 양보도 batch 반복 내부에서만 검사한다.

대용량 JSON의 원문·파싱 객체, Prisma 결과, Decimal, 정렬·중간 배열 등이 같은 프로세스에서 함께 존재할 수 있다. **전체 후보 탐색의 메모리 폭증이 가장 유력**하나 현재 근거만으로 특정 객체/쿼리 한 곳을 최종 원인으로 단정하지 않는다. 전체 데이터 재조회나 OOM 재현, 힙 덤프 생성은 운영 안정성을 위해 실행하지 않았다.

### 권장 수정과 검증 기준 — 미구현

- 일일 한도 소진·대기 중 수동 요청을 대량 탐색 전에 확인한다.
- 후보 키와 필요한 최소 필드를 제한된 페이지로 읽는다. 이미 확정된 전체 테이블을 반복 로드하지 않도록 인덱스·조회 계획을 검토한다. 한 번에 10개만 실행한다는 제한과 탐색 메모리 제한을 별도로 둔다.
- 후보 탐색은 공용 **실행** 잠금 밖에서 수행하고, 획득 후 제한된 batch에 대해 대상·최신성·종목 식별·nextAttemptAt을 재검증한다. 동시 후보 선점 방지를 위한 원자적 claim/짧은 잠금이 필요하다.
- 강제 프로세스 종료에서 finally는 실행되지 않는다. 소유자 생존/heartbeat·진행 시각을 기록하고 임대 상실 시 저장을 막는 fencing을 함께 설계한다. 소유자가 확인되지 않은 잠금을 무조건 삭제하지 않는다.
- 실행 행을 후보 탐색 전에 만들거나 별도 탐색 상태를 기록해 ‘잠금 있음/실행 행 없음’을 추적 가능하게 한다.
- 큰 데이터 fixture에서 후보 수에 무관한 페이지 상한과 메모리 상한, 대상 0개 시 외부 호출 0, 동시 수동/자동 claim, 프로세스 중단 후 복구, 기존 자료 보존을 검증한다.
- Node 힙 상향은 서버 전체 여유·다른 서비스와 함께 검토할 임시 완화일 뿐이다. 이 1.7GiB 서버에서 무조건 상향하는 것은 권고하지 않는다.
