# 메일 운영 설정 위치 및 변경 경위 조사

조사일: 2026-10-21 UTC. 기준 운영 소스: `22001ac9c3da8f3dbb7ac492c511e492baf76e93`. 설정 변경·재시작·SMTP 인증 시도·시험 메일 발송은 수행하지 않았다. 비밀 값과 설정 원문은 보고서 및 Git에 포함하지 않았다.

## 결론

메일 설정은 삭제되어 유실된 상태가 아니라, 10월 20일 이메일 인증 기능 도입 과정에서 공용 `.env.production`에서 백엔드 전용 `.env.auth`로 분리된 상태다. 현재 실행 중인 백엔드의 PID 1 환경에도 요청한 8개 항목이 모두 비어 있지 않게 존재한다. `.env.production`만 검색하면 아무것도 출력되지 않는 것이 현재 구성과 일치한다.

분리 직전 비공개 사본과 비교하면 제거된 항목은 메일 8개뿐이며, 현재 `.env.auth`의 각 값은 그 사본과 모두 일치한다. 비메일 기존 변수는 이름과 값 모두 보존됐다. 따라서 현재 조사 범위에서 메일 설정 복구나 운영 재시작은 필요하지 않다. 현재 자격증명의 SMTP 유효성·수신 성공은 이번 조사에서 재검증하지 않았다.

## 시간대별 증거와 원인

1. 2026-10-20 07:33:57 UTC 기준 비공개 백업 `backups/roxstock-v0.2-20261020T073357Z/private-config.tar.gz`의 원본 `.env.production`에는 메일 8개가 아직 없었다. 그 사본의 기존 변수는 현재 파일에서 삭제·변경되지 않았다. 메일 항목 부재만으로 과거 정상 설정의 삭제라고 판단할 수 없다.
2. 비공개 `.deploy/auth-private-stage-20261020T121237Z/env.production.before`에는 메일 8개가 모두 비어 있지 않게 존재한다. 현재 파일과 비교하면 이 8개만 제거됐고 다른 기존 변수는 그대로다. 07:33 백업 이후 분리 전까지 메일이 원본에 추가되었던 것으로 판단되나, 최초 추가 시각 자체는 확정할 수 없다.
3. `.env.production` 수정 시각과 `.env.auth` 생성 시각은 모두 12:12:37 UTC다. 위 사전 사본의 메일 8개와 현재 `.env.auth`의 값이 모두 일치한다. 이 조합은 해당 시각의 파일 분리를 강하게 뒷받침한다. `.env.auth`의 12:31:14 추가 수정 내용은 별도 중간 사본이 없어 확정하지 않는다.
4. [인증 도입 커밋 4535d08](https://github.com/byungho-cho/roxstock/commit/4535d08cd50b075878617a3960fb5d995a249514)은 backend 전용 auth 파일을 Compose와 배포 복사 경로에 추가했다. [기존 인증 배포 보고서](./auth-v1.2.0-20261020.md)는 SMTP를 `.env.auth`에만 보관하고 collector 환경에서 제거한다고 명시한다. [PR #284](https://github.com/byungho-cho/roxstock/pull/284)로 운영 반영됐다.
5. 10월 20일 13:28 배포 이력의 직전 백엔드 컨테이너 사본에는 메일 8개가 없었다. 현재 컨테이너에는 모두 있다. 이전 보고서의 인증·메일 발송 기록과 사용자의 수신 확인은 이 조사에서 수행한 새 시험과 구분한다.
6. 10월 21일 Firebase 알림 작업은 `FCM_SERVICE_ACCOUNT_FILE`을 별도로 요구한다. 메일 설정은 현재도 분리 전 값 그대로 남아 있다. 이 작업이 메일 값을 유실시켰다는 증거는 없다.

원인은 공용 환경에서 메일 비밀을 제거하고 backend에만 주입하는 설정 분리다. Git에 기록된 코드 작성자 표시는 `byungho-cho`지만, 그것만으로 서버 파일을 직접 수정한 사람·에이전트를 특정할 수 없다. root 소유권과 파일 시각 역시 변경 주체를 증명하지 않는다. 사용자별 명령 감사 로그를 확보하지 못했으므로 직접 변경 주체는 미확인으로 둔다. 로그인 이력만으로 이 파일 변경을 귀속하지 않았다.

## 배포 스크립트 점검

실제 기준 SHA의 `scripts/deploy-production-component.sh` 61~65행은 서버 원본 `.env.production`과 `.env.auth`를 각각 `install -m 600`으로 배포 체크아웃에 복사한다. 예제 파일이나 일부 변수만으로 서버 원본을 덮어쓰는 동작은 이 경로에서 발견하지 못했다. 70~78행은 기존 실행 환경의 collector 내부 토큰이 필요한 경우 체크아웃 사본에만 보충한다. `scripts/deploy-investor-crawler.sh`도 공용 원본을 체크아웃으로 복사한다.

루트의 오래된 `scripts/deploy-backend.sh`는 `.env.production`만 사용하는 구성과 함께 남아 있다. 현재 실행 컨테이너의 Compose 경로와 다르므로, 이 오래된 경로로 수동 배포하면 auth 파일 주입이 빠질 가능성이 있다. 이번에 실행하거나 수정하지 않았다.

## 비공개 보존·복구 및 재발 방지

운영 변경 없이도 현재 두 설정 파일을 `/opt/roxstock/backups/mail-config-audit-20261021T071447Z/`에 보존했다. 디렉터리 `0700`, 사본과 `validation.json`은 `0600`. 사본별 SHA-256 및 원본과의 바이트 일치 결과를 해당 비공개 검증 기록에 저장했고 두 파일 모두 검증 통과했다. 이는 설정 파일 백업이며 새 DB 백업이나 DB 복원은 수행하지 않았다. 백업 내용·해시 원문은 Git에 올리지 않았다.

메일 8개는 분리 직전 사본에서 복구 가능하며 현재 auth 파일과 일치한다. 다만 자격증명이 아직 외부에서 유효한지는 별도 검증 대상이다. 유실이 생길 경우 현재 파일을 먼저 추가 보존한 뒤 필요한 키만 backend 전용 `.env.auth`에 복구하고, 중복 정의·빈 값·다른 설정 보존을 검사해야 한다. 공용 파일 전체 덮어쓰기나 메일 값을 collector 공용 환경으로 되돌리는 조치는 필요하지 않다.

후속 제안은 다음과 같다. 이번 조사에서는 적용하지 않았다.

- 배포 전 두 서버 원본의 존재·권한과 필수 메일 키의 비어 있지 않음을 값 출력 없이 검사한다. Compose 최종 backend 환경에도 같은 검사를 추가한다.
- 예제 파일 기반 재생성을 금지하고, 현재처럼 서버 비밀 원본을 보존·복사한다. 변경 시 비공개 스냅샷·체크섬·추가/삭제된 키 이름만 기록한다.
- 운영 문서에 `.env.production`은 공용 설정, `.env.auth`는 backend 전용이라는 위치와 우선순위를 명시한다. 오래된 수동 배포 경로는 현재 경로로 안내하거나 실행을 차단하는 별도 변경을 검토한다.
- Firebase와 별도 네이버 개발자 API의 과거 설정이 있다고 알려진 경우 해당 배포 실행·설정 위치를 추가 추적한다. 현재 메일 설정 분리와는 별개로 다룬다.

시험 메일·SMTP 인증 재검증, Firebase 키 설치, 운영 설정 수정 및 컨테이너 재생성은 별도 후속 작업으로 남긴다.
