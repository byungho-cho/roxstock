상태: 개발 및 검증 중. 운영 이관·배포·최초 임시 비밀번호 발송은 아직 실행하지 않았다.

## 구현

- 초대/승인 이메일만 가입하고 이메일 인증 후 사용한다. 인증에는 가입 시 비밀번호도 확인해 사전 가입된 계정의 탈취를 방지한다.
- 비밀번호는 12자 이상, 긴 문장/붙여넣기를 허용하며 임의 salt를 사용하는 scrypt로 단방향 저장한다.
- DB 세션, HttpOnly/Secure/SameSite 쿠키, Origin·CSRF 검사, 해시 기반 갱신 토큰 교체·재사용 탐지, 서버 요청 제한을 구현한다.
- 자동 로그인 기본값은 미선택이다. 선택 시 90일 영속 쿠키와 갱신 가능한 만료일, 미선택 시 세션 쿠키와 12시간 서버 상한을 사용한다.
- 동시 갱신은 조건부 원자 갱신과 짧은 이전 토큰 유예로 처리한다. 유예 이후 폐기된 토큰을 재사용하면 해당 세션을 폐기한다.
- 재설정 링크는 30분·일회용이며 새 링크 발급 시 이전 링크를 폐기한다. 비밀번호 변경/재설정은 모든 기존 세션을 폐기한다.
- 로그인 전과 세션 복원 중에는 개인 화면/하단 메뉴를 렌더링하지 않는다. 계정 전환 시 쿼리·페이지 메모리를 비우고, 계좌 선택/관심 표시의 저장 공간과 서버 설정을 사용자별로 분리한다.
- 개인 계좌와 자식 Lot·매도·예수금·배당·관심종목·계획·이력·스냅샷에 서버 소유권 경계를 적용한다. 요청 userId는 거절하며 타인 ID 직접 조회·변경도 차단한다.
- 공통 종목·시세·재무제표·공시·뉴스 원천은 공유한다. 뉴스의 보유·관심·거래 연관 정보는 소유 계좌별로 계산한다.
- 공개 API는 `/api/version`, 명시된 가입/로그인/메일 링크 API뿐이다. 나머지 API는 인증이 기본이며 운영·수집·관리 API는 ADMIN을 요구한다. `/health` 계열은 개인 정보를 반환하지 않는다. 내부 수집 API의 별도 자격증명 검사는 유지한다.
- 메일 링크는 fragment로 전달하고 최초 렌더 시 주소에서 지운다. Referrer-Policy no-referrer, 요청/응답 쿠키 redaction, 메일 로깅 금지를 적용한다.
- 최초 메일은 서버 시작과 마이그레이션에서 발송하지 않는다. 명시적인 사후 작업만 허용하며, 발송 claim을 먼저 보관해 재배포/불확실한 SMTP 응답으로 같은 임시 비밀번호를 반복 발송하지 않는다. 만료/불확실한 발송은 재설정으로 복구한다.
- SMTP는 지정된 실제 Gmail 계정·587·STARTTLS를 사용한다. 비밀값은 backend 전용 `.env.auth`에만 두고 collector 환경에서 제거한다.

## 현재 검증 기록

- 기존 백엔드 계산·원장 회귀 142/142 통과.
- 실제 로컬 MariaDB의 서로 다른 두 사용자로 인증·CSRF·Origin·조회·수정·삭제·묶음 조회·Lot·분할매도 직접 ID 차단 통과. 자기 계좌의 잔여 수량과 Lot/분할매도 조회도 통과.
- 같은 쿠키의 동시 갱신, 서버 앱 인스턴스 재생성 후 DB 세션 복원, 이전 토큰 재사용 폐기, 재설정 후 기존 세션 폐기·링크 재사용/만료 차단 통과.
- 별도 인증 UI 6/6 및 기존 종목소식 화면 8/8 통과. 실제 Figma 렌더와 화면을 대조했다.
- 지정된 서버 Gmail 설정의 STARTTLS 인증 성공을 비밀값 출력·메일 발송 없이 재확인했다. SMTP 수락과 실제 수신은 구분해 기록한다.
- 로컬 이관 14개 개인 테이블의 건수·원본 내용·연결 키 해시 일치. 첫 연습에서 ORM이 계좌 수정 시각까지 바꾸는 것을 발견해 SQL로 소유권 필드만 변경하도록 수정했다. 운영에는 이 수정된 경로만 사용한다.
- 프론트 실제 프로젝트 타입 검사, 백엔드 빌드 통과.

아직 검증하지 않은 항목: 최종 전체 CI, 브라우저 프로세스 재실행, 실제 USB 앱 재실행·메일 링크, 실제 운영 이관 대조, 운영 가입/인증/재설정 발송, 최초 임시 비밀번호 발송. 완료 전에는 운영 준비 완료로 표시하지 않는다.

## 이관·복구 절차

1. 개인 API를 차단하는 프록시 유지보수 경계를 먼저 설치·검증한다. 이전 무인증 이미지로 돌아가도 경계가 유지되어야 한다.
2. 비공개 SMTP/기존 소유자 이메일 설정을 검증하고, 백업 복제/체크섬·여유 공간·진행 중 쓰기를 확인한다. 비밀값은 명령 출력에 넣지 않는다.
3. 최신 DB 추가 백업 후 추가 방식의 인증 스키마를 적용한다. 이관 도구는 기존 사용자 이메일을 조회/upsert하며 중복 계정을 만들지 않는다. 계좌·이전 관심종목의 미할당 소유권만 연결한다.
4. 이관 전후 14개 개인 테이블 원본 해시와 건수·금액·관계가 같고, 미할당 계좌가 없는지 대조한다. 백업과 대조 파일은 비공개로 보관한다. 기존 Lot/매도 FK와 계산값은 재작성하지 않는다.
5. 새 백엔드 내부 무인증 개인 API가 401인지 확인하고 새 프론트를 배포한다. 프록시 경계를 해제한 뒤 외부에서도 401과 정상 로그인/격리를 확인한다.
6. 가입·인증·메일·재설정을 확인한 후에만 최초 임시 비밀번호를 명시적으로 한 번 발송한다. 임시 비밀번호는 24시간·최초 변경 필수이며 변경 전 일반 API는 금지한다.
7. 코드 복구는 인증을 보존하는 직전 호환 이미지로 한다. 동결된 무인증 이미지가 필요한 경우 프록시 개인 API 차단을 유지한 채 유지보수 모드로만 복귀한다. 자동 DB 다운 마이그레이션은 하지 않는다.
8. 전체 DB 복원이 불가피하면 현재 DB를 먼저 추가 백업하고 동결 이후 거래/수집 차이를 보존한다. 격리 복원·대조·재적용 계획을 확인한 뒤 별도 복원한다. 기준 백업을 운영 DB에 바로 덮어쓰지 않는다.

운영 배포 결과·최초 메일 발송 여부와 APK/PR 링크는 검증 후 갱신한다.
