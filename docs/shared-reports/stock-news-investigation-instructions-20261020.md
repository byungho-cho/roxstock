범위: 운영 로그·DB·배포 코드의 읽기 전용 조사. 이번 요청은 수정·재수집·배포 지시와 구분합니다.

## 1. 사용자 화면에서 확인된 사실

09:30 KST 첨부 화면 기준:
- 10/20 06:00 실행은 ‘일부 실패’, 대상 1·성공 0·실패 1·건너뜀 0으로 표시됩니다.
- HANKYUNG_RSS: 실행시각 10/20 06:02, FEED_FINANCE_WINDOW_LIMIT 및 FEED_ECONOMY_WINDOW_LIMIT.
- 상단은 ‘원천 기준 10/20 06:02’, ‘수집 완료 10/20 06:02’, ‘시도 10/20 06:00’, ‘성공 10/20 06:02’를 표시합니다.
- 종목소식 목록은 전날의 공시 3건·리포트 1건, 총 4건입니다.
- 화면의 DART 오류 CORP_MAPPING_MISSING:3, DART_API_UNAVAILABLE_OR_QUOTA는 10/19 16:06 기록입니다. 오늘 오류로 단정하지 않습니다.

위 내용은 화면 관찰이며 운영 DB·로그로 검증한 결과가 아닙니다. WINDOW_LIMIT의 의미와 ‘대상 1’의 집계 단위도 아직 미확인입니다.

## 2. 조사 목표

아래를 구분해 결론을 내려 주세요.
1. 정상 조회했으나 대상 종목의 신규 소식이 없었음
2. 조회·파싱·수집 범위 제한 등으로 소식을 확인하지 못했음
3. 후보는 있었으나 매칭·중복 제거·선별 단계에서 제외됨
4. 저장은 됐으나 계좌 관계·조회 조건·캐시·화면 반영 문제로 보이지 않음

제공처별로 판단하고, 일부 실패 결과를 전체 ‘신규 없음’으로 해석하지 않습니다. 현재 자료만으로 판단할 수 없으면 미확인 범위와 필요한 증거를 명시합니다.

## 3. 실행과 제공처별 처리 내역 확인

- 당시 운영 버전·커밋·수집기 이미지, 실행 ID, 예약·시작·종료 시각과 재시도 이력을 확인합니다.
- 모든 시각은 KST로 표기합니다.
- 실제 보유·관심·거래 이력 수집 대상 및 계좌 관계 적용 여부를 확인합니다. 공개 문서에는 계좌정보를 제외합니다.
- 한경 RSS·리포트·DART 각각의 실행/미실행/재사용/제외 이유를 확인합니다.
- 제공처별 요청 수, HTTP 상태, 응답 시간·크기, 조회 기간, 피드 최저·최신 게시 시각을 확인합니다.
- 원천 응답 건수 → 파싱 건수 → 기간 통과 → 종목 매칭 → 중복 제외 → 선별 → 신규 저장 → 기존 항목 관계 추가 → 화면 조회 건수를 대조합니다.
- 기존 기록으로 집계할 수 없는 값은 추정하지 말고 ‘기록 없음’으로 표시합니다.
- ‘대상 1’과 ‘성공 0/실패 1’이 제공처·항목·작업 중 어떤 단위인지 확인합니다.

## 4. WINDOW_LIMIT 발생 조건

- 두 오류 코드를 생성하는 실제 코드 위치와 조건을 확인합니다.
- 시간 범위 미충족, 피드 보존 길이, 페이지·항목 상한, 요청·실행 예산, 응답 크기 제한 중 어떤 조건인지 근거로 구분합니다.
- 요청한 수집 구간과 실제 피드가 제공한 구간을 대조합니다.
- 일부 유효 항목을 수집했음에도 실패 처리했는지, 저장 전에 중단했는지 확인합니다.
- 성공·부분 실패 시 watermark/커서가 어디까지 전진했는지 확인하고, 다음 실행에서 미확인 구간이 누락될 가능성을 검토합니다.
- 현재 안전 제한을 단순 해제하거나 전체 피드를 무제한 조회하지 않습니다.

## 5. DART·리포트 및 목록 미추가 확인

- 오늘 DART와 리포트가 실행됐는지, 전날 상태만 노출됐는지 확인합니다.
- 전날 DART 오류는 회사 매핑 누락과 API 실패·쿼터를 가능한 범위에서 각각 구분합니다. 키나 비밀값은 기록하지 않습니다.
- DB에 오늘 신규 저장 또는 기존 소식의 관계 추가가 있었는지 확인합니다.
- 동일 계좌·동일 필터의 목록 API와 DB 결과를 대조합니다.
- 기존 항목 4건 유지가 정상 보존인지, 갱신 누락인지 확인합니다.
- 당시 원천 응답이 보존되지 않았다면 현재 조회만으로 당시 신규 소식 부재를 확정하지 않습니다.

## 6. 성공 시각·상태 표시 의미 확인

- 상단 ‘성공 06:02’, ‘수집 완료’, ‘원천 기준’이 각각 전체 성공·일부 성공·작업 종료 중 무엇을 의미하는지 코드·DB로 확인합니다.
- 일부 실패인데 전체 성공처럼 보이는 표시가 생기는지 확인합니다.
- 신규 없음·일부 실패·전체 실패·미실행을 사용자가 구분할 수 있도록 개선안을 제안합니다.
- 이번 조사에서 표시 상태나 데이터를 임의로 변경하지 않습니다.

## 7. 조사 방법과 운영 보호

- 우선 보존된 로그·DB·배포 코드를 조회합니다.
- 수집기 재시작, 잠금 삭제, 오류 초기화, watermark 변경, 강제 재수집, 코드 수정·배포는 이번 조사 범위에 포함하지 않습니다.
- 추가 외부 요청이 필요하면 대상·목적·최대 횟수를 명시하고 제공처 정책과 기존 호출 제한을 준수합니다. 과거 실행 재현과 현재 원천 조회의 차이를 구분합니다.
- 원본 증거는 접근 제한된 운영 조사 경로에 보관합니다.
- 공유 Git에는 API 키·토큰·쿠키·DB 접속정보·계좌정보·원문 전체·운영 DB 덤프를 올리지 않습니다.
