**이번 운영 DB 보정은 0건이다.** 개발 PR [#288](https://github.com/byungho-cho/roxstock/pull/288)은 아직 초안·미병합이고 운영 v1.2.1에는 새 상태·마이그레이션이 없다. 사용자 지시의 ‘개발 반영 전에는 대상 ID와 보정 계획까지만 준비’ 조건을 적용했다. **정책 제외 24건·미도래 70건·API 자료 미제공 57건, 총 151개 작업 ID**를 확정하고 조건부 계획과 1차 응답 근거를 준비했다. 실행 가능한 apply 파일은 만들지 않았고 새 상태를 DB에 넣지 않았다.

### 개발 반영 후 적용 전제

1. 실제 API·모든 관련 수집기·frontend의 배포 SHA와 마이그레이션 완료를 다시 확인한다. DB enum만 확장됐다고 보정하지 않는다.
2. 보정 직전 대상 행을 다시 읽고 정확한 ID·종목코드 namespace·회사번호·수집 허용·이전 상태/사유·갱신 시각을 비교한다. 같은 기간에 검증된 저장 공시가 있거나 이미 SUCCESS인 작업은 건너뛴다.
3. 실제 변경 전 DB 백업은 서버 `AGENTS.md`에 따라 `/opt/roxstock/backups/roxstock-v0.2-<실제 UTC 백업시각>/`에 비공개로 보존하고 체크섬·압축 무결성·복구 검증을 남긴다. 이번 읽기 전용 스냅샷은 실제 보정 직전 백업을 대신하지 않는다.
4. 공유 financial lease 안에서 ID·상태·updatedAt 및 이전 스냅샷 해시를 CAS로 비교하고, 변경과 `dart_task_decisions` 전후 이력을 같은 트랜잭션에 남긴다. 조건이 달라진 행은 일괄 덮어쓰지 않는다.
5. 같은 계획을 반복 적용하면 이미 새 상태/다른 updatedAt인 행은 건너뛰어 중복 변경을 막는다. 개발 배포 후 자동 보정 job과 별도 웹서버 apply가 동시에 같은 작업을 처리하지 않도록 실행 소유자를 하나로 정한다.
6. apply 직전에 만든 계획만 사용한다. 이 보고서의 시각·nextAttemptAt 제안값을 나중에 그대로 복사하지 않는다. 원문·재무자료·가치지표·개인 자산 데이터는 이 상태 보정의 쓰기 범위에 넣지 않는다.

## 3. 더본코리아 지정 24건 — 사용자 정책 제외

사용자가 확정한 상장일 **2024-11-06**과 정책을 그대로 사용한다. 이것은 공시 부존재나 제출의무 없음 판정이 아니라 **사용자 정책상 ‘상장 전 수집 제외’**다.

대상은 2015–2023 사업보고서 **9건**, 2020–2024 Q1·반기·Q3 **15건**이다. 24개 ID를 1차 스냅샷과 다시 대조했고, 12월 결산 기준 각 대상 보고기간 말일은 모두 상장일 이전이다. 2024년 Q3도 2024-09-30로 확인했다. **2024 사업보고서·기존 저장 자료·상장 이후 작업·다른 신규 상장사로 확대하지 않는다.**

배포 후에는 상태 `EXCLUDED`, 사유 `PRE_LISTING_POLICY_EXCLUDED`, 설명 ‘상장 전 수집 제외’, 정책일·대상 보고기간·정확한 24개 ID 범위를 이력에 남긴다. nextAttemptAt은 NULL이며 일반 작업 큐에서 빠져야 한다. 기본 전체/우선 집계의 대상 수·완료 분자·진행률 분모와 상태 분포 모두에서 제외하고 별도 EXCLUDED 상세로 조회해야 한다. 행 삭제·화면만 숨김·수동 숫자 보정은 하지 않는다.

**이번 실제 제외 0건**이므로 우선종목 계획은 아직 **1,155건**이다. 24건 적용 후의 **1,131건은 검산 목표이며 현재 운영 실측값이 아니다.**

## 4. 미도래 70건 — 보정 계획과 일정 연결 검토

70건 모두 기존 DB·유효 v2 공시 캐시에 같은 기간의 새 보고서 후보나 검증된 저장 공시가 없는지 대조했다. 결산월은 각 회사의 `selection.annualPeriods / fiscalYearEndMonth`와 보고기간을 사용했다. 3S는 3월 결산을 유지해 반기 2026-09-30, Q3 2026-12-31로 대조했다. 현재 캐시 근거가 유효한 70건을 계획에 넣었으며, 전체 70건을 외부 조회·재수집하지 않았다.

| 대상 | 건수 | 보고기간 말일 | 일반 기준일(최종 법적 기한 아님) |
| --- | --- | --- | --- |
| 12월 결산사 2026 Q3 | 34 | 2026-09-30 | 45일 산술 기준 2026-11-14 |
| 3S 2026 반기 | 1 | 2026-09-30 | 45일 산술 기준 2026-11-14 |
| 12월 결산사 2026 사업보고서 | 34 | 2026-12-31 | 90일 산술 기준 2027-03-31 |
| 3S 2026 Q3 | 1 | 2026-12-31 | 45일 산술 기준 2027-02-14 |


정확한 법적 기한은 특례·휴일·제출의무 개별 근거가 부족해 계속 **미확인**이다. 개발 helper는 90/45일을 확정 마감일이 아닌 하한으로 사용하며, 새 공시를 먼저 찾고 없을 때 NOT_DUE를 판단한다. 날짜를 법적 최종기한이라고 확정하지 않는다.

개발 규격의 다음 확인은 **실제 확인/적용 시각 +24시간**이며 DB `nextAttemptAt`에 저장한다. CSV에는 계획 작성 시점의 일일 확인 제안만 넣었고 자동 일정으로 등록하지 않았다. 1차의 11월/내년 운영 재확인 제안일과 **매일 조기 공시를 확인하는 개발 일정**을 구분한다. 조기 공시가 발견되거나 이미 SUCCESS로 바뀐 작업은 NOT_DUE로 되돌리지 않는다. 캐시 만료/새 후보/결산월 모호 상태면 70건을 강제 NOT_DUE로 넣지 말고 다시 판정한다. 전체 70건을 일괄 재수집하는 동작도 하지 않는다.

### 자동 재확인·재시작 지속성 검증 상태

- 개발 소스에는 `reactivateDueTasks`가 `nextAttemptAt <= now`인 NOT_DUE/NO_FILING 등을 인덱스로 최대 100개 읽고, CAS 후 PENDING과 감사 이력을 남긴다. CURRENT 이후에도 실행될 수 있도록 backfill 상태를 재가동하는 경로가 있다.
- 재확인 일정이 JS 메모리가 아닌 DB에 저장되는 구조임은 소스로 확인했다. **운영 DB에는 새 상태가 없어 실제 일정 연결·기한 도래·조기 제출 처리·프로세스 재기동 지속성은 미검증**이다.
- 이번 지시로 서비스 재시작 시험을 하지는 않았다. 개발 담당의 격리 DB/CI 재기동 시험과 실제 배포 후 DB 일정 보존·중복 실행 방지 증거를 연결해야 한다.
- 현대홈쇼핑은 현재 비활성 플래그를 가진 우선종목이다. 재가동 큐는 활성 여부를 직접 제한하지 않지만 실제 수집 대상 조회에는 `isActive=true` 조건이 있어, 해당 2건의 다음 확인이 PENDING에 정체되지 않는지 별도 검증이 필요하다. 임의 활성화는 하지 않았다.

## 5. 금융회사 57건 — 기존 응답 재사용과 개발 차이

삼성증권·기업은행·KB금융 각 19건이다. 1차 비공개 응답 **114개**를 현재 57개 ID·회사번호·요청 연도·보고서·CFS/OFS와 한 건씩 대조했다. 모두 **HTTP 200 / DART 013 / 0행**이며, 당시 공시 목록에서 선택한 보고서 접수번호와 조회 시각을 함께 연결했다. 각 응답 본문의 SHA-256 및 1차 호출 번호도 비공개 보정 근거에 보존했다. **동일 114회 조회를 반복하지 않았다.**

배포 후 계획 상태는 `DATA_UNAVAILABLE`, 코드 `API_ROWS_UNAVAILABLE`, `needsSupplement=true`, `availability=API_DATA_UNAVAILABLE`다. `financialResponses`에 회사·연도·코드·연결/별도·HTTP/DART 상태·행 수·확인 시각·반환 접수번호(없음)·근거 식별자를 보존한다. 공시는 있으므로 미공시로 표시하지 않고, 원문 보완이 남아 있으므로 수집 성공/완료로 합산하지 않는다. 금융업 전체나 이 57건을 정책 제외로 바꾸지 않는다.

**개발 PR #288의 현재 plan 스크립트와 차이가 있다.** `ROWS_NOT_PUBLISHED`는 아직 원응답 근거가 부족하다고 간주하여 `FAILED / REVIEW_REQUIRED / LEGACY_FINANCIAL_RESPONSE_UNVERIFIED`로 전환하도록 작성되어 있다. 1차 완료 후에는 이 전제가 달라졌다. 자동 보정 job을 그대로 실행하면 이번 사용자 지시의 ‘자료 미제공 상태 분리’를 달성하지 못한다. **114개 기존 응답을 검증해 DATA_UNAVAILABLE로 입력하는 경로를 먼저 반영하거나 검토된 증거 입력 계획을 기존 CAS/감사 경로로 적용해야 한다.** 이 문서 작업에서 개발 스크립트를 중복 수정하지 않았다.

성공한 13개 매핑 복구 작업도 개발 문서의 옛 990건 예시와 달리 이미 완료됐다. 배포 후 자동 보정이 이 13건을 다시 대기/재수집으로 돌리지 않는지 확인해야 하며, 이번 계획에는 넣지 않았다.

삼성증권은 BS table 12, 손익 table 16, 현금흐름 table 24의 후보를 연결·별도에서 찾았다. 기업은행은 별도 14/17/23, 연결 11/14/20에서 후보를 찾았다(이 번호는 비공개 오프라인 추출기의 0 시작 table index이며 운영 API 필드가 아니다). 금융회사 자료는 연간 누적이므로 분기 실적으로 치환하거나 다른 연도/분기 자료를 대신 저장하지 않았다.

표지의 회사·2015-01-01–2015-12-31, 감사보고서/연결감사보고서 종류, 당기·전기 머리글, 단위와 BS 합계 관계를 대조했다. 공백 셀·주석 열과 금액 열을 분리했고 기업은행 합계 셀의 `===` 장식을 제한적으로 제거한 뒤 Decimal로 비교했다. 라벨 안에 포함된 대손준비금 반영 후 조정이익 등을 금액 열과 혼합하면 안 된다. 단위는 명시적인 원/천원/백만원만 허용하고 모호한 단위는 원으로 추정하지 않았다.

이 결과는 **동일 회사·기간의 재무표 후보를 추출할 가능성과 일부 항등식 확인**이다. 금융업 영업수익/매출 대응, 지배/비지배 순이익, 손익·현금흐름 전체 열/계정 대응, 비교기 재작성, 통화·단위의 모든 주석까지 검증한 것은 아니다. **금액 검증 전체 완료·운영 수집 성공·가치지표 계산 완료로 표시하지 않았다. 검증되지 않은 금액 저장은 0건**이다.

KB금융의 접수번호 20160330004428 소형 첨부는 2014년 표지를 가지므로 그대로 거부했다. 주본문은 5MB를 초과해 2015년을 정확히 식별할 근거가 아직 부족하다. 상한을 무제한 해제하거나 2014년 첨부를 대신 사용하는 방식을 쓰지 않았다. 추가 외부 조회가 필요하면 이 접수번호의 실제 2015년 최신 원본/정정과 필요한 최소 문서만 목적·예상 호출 수를 다시 산정한 후 조회해야 한다. 이번에는 추가 호출을 요청·실행하지 않았다.

## 7. 현재 집계와 보정 후 검산 목표 — 혼합 금지

동일한 인증 범위에서 선택되는 35개 STOCK·DART 연결·수집 허용 종목에 2015–2026 사업보고서, 2020–2026 Q1/Q2/Q3를 적용했다. 1차 후속과 같은 집합으로 DB와 실제 운영 코드의 API GET 핸들러를 재조회했다. 사용자·계좌·보유/거래 데이터 자체는 내보내지 않았다.

| 분류 | 현재 DB | 운영 API | 개발 반영 및 계획 적용 후 목표(미적용) |
| --- | --- | --- | --- |
| 성공 | 1003 | 1003 | 1003 |
| 미도래 | 지원 상태 없음 — 기존 NO_FILING에 70 포함 | 별도 분리 전 | 70 |
| 미공시 | NO_FILING 151 — 아래 70/57/24 포함 | 151 | 0 |
| API 자료 미제공·보완 필요 | 별도 상태 없음 — NO_FILING에 57 포함 | 별도 분리 전 | 57 |
| 검토 보류 | 1 | 1 | 1 |
| 대기·처리 중·일반 실패 | 0 | 0 | 0 |
| 정책 제외(기본 집계 밖) | 아직 제외 안 됨 | 아직 제외 안 됨 | 24 |
| 기본 전체 계획 | 1155 | 1155 | 1131 |
| 현재 처리 대상 분모 | 구버전 1155 | 1155 | 1061 |


현재의 NO_FILING 151 = **미도래 후보 70 + API 미제공 57 + 사용자 정책 제외 예정 24**다. 논리적 조사 분류와 저장 상태를 같은 표에서 중복 합산하지 않는다. 개발 규격 적용 후라면 기본 계획 1,131 = **성공 1,003 + 미도래 70 + 자료 미제공·보완 57 + 보류 1**, 현재 처리 대상 **1,061 = 1,131 - 70**이다. needsSupplement=true인 57건을 완료에 넣지 않으므로 완료 분자는 **1,003**, 완료율/수집 성공률은 약 **94.5335%**다. 이것은 적용 후 기대치이며 현재 화면 수치가 아니다.

시스템 전체 범위와 우선 35개 범위도 구분했다. 현재 운영 API 전체 과거 작업은 **86,724건**(성공 66,878 / NO_FILING 19,524 / NOT_APPLICABLE 33 / 검토 보류 289), 우선종목은 **1,155건**이다. 같은 24개 정책 작업을 기본 집계에서 제외하면 다른 변동이 없을 때 전체 계획은 **86,700**, 우선 계획은 **1,131**이어야 한다. 새 규격이 기존의 다른 상태를 어떻게 표시하는지도 별도로 검증해야 하며, 우선종목 보류 1건과 전체 보류 289건을 혼합하지 않는다.

### 실제 화면 확인의 한계

공개 운영 `/api/version`은 HTTP 200으로 1.2.1을 확인했다. 인증 없는 실제 모니터링 HTTP 요청은 **401 LOGIN_REQUIRED**였다. 현재 도구에 재사용 가능한 관리자 브라우저 세션이 없어 **실제 관리자 화면의 수치 직접 대조는 미검증**이다. 실제 API 서버 핸들러를 인증 범위 컨텍스트에서 읽기 전용으로 호출한 결과와 DB가 일치한다는 사실만 확인했으며 이를 브라우저 화면 대조 완료로 표현하지 않는다. 배포 후 관리자 세션에서 실제 전체/우선·제외 상세·상태별 표시를 대조하는 증거가 추가로 필요하다.

## 8. 불변·근거 보존 검증

- 전체 DART 작업 행 및 기존 DART 저장 공시·요약 재무자료·가치지표·기간별 가치지표의 전후 SHA-256이 일치했다. 151개 대상의 상태·사유·진단·접수번호·시도 횟수·다음 시각을 변경하지 않았다.
- 계좌·매수·매도·입출금·배당·일별 계좌/포지션 스냅샷·계좌별 목록도 읽은 값을 서버 안에서 해시만 계산해 전후 일치를 확인했다. 개인 원문 행·식별자·수량·거래·자산값은 추출 파일과 공개 문서에 저장하지 않았다.
- 1차 성공한 13건의 현재 SUCCESS 및 저장 공시, 경동나비엔 2025년 사업보고서 `FAILED / REVIEW_REQUIRED`를 확인했다. 경동나비엔을 보정 대상으로 섞거나 강제로 성공 처리하지 않았다.
- 개발 소스/마이그레이션 확인, 원문 오프라인 추출, 계획 작성은 모두 운영 데이터를 쓰지 않는 조사였다. 공유 금융 잠금·DART 호출 예산도 이번에는 사용/갱신하지 않았다.
- 1차 원본 응답·ZIP·XML과 이번 스냅샷·계획·오프라인 후보 금액/로그는 Git 밖 권한 0700 비공개 디렉터리에 보존했다. 공개 산출물은 보고서와 비식별 CSV 두 개뿐이다.

## 9. 개발 담당 인계 — 적용 전 해결·증거 필요

1. **1차 선처리 반영:** 성공 13건은 제외하고 저장 성공 기준을 990이 아닌 현재 **1,003건**으로 검증한다. 매핑 회복 큐가 이를 다시 초기화하지 않게 한다.
2. **금융 57건의 증거 가져오기:** 현재 `LEGACY_FINANCIAL_RESPONSE_UNVERIFIED` 계획 분기를 이번 114개 보존 응답과 대조한다. 검증된 대상만 DATA_UNAVAILABLE/API_ROWS_UNAVAILABLE + needsSupplement=true로 분리한다. 같은 114회 조회나 금융업 전체 정책 제외를 하지 않는다.
3. **정책 제외 정확한 범위:** 더본코리아 24개 ID만 EXCLUDED로 관리한다. 사유·정책일·보고기간·감사 이력은 보존하고 기본 전체/우선/완료/분모에서 제외하며 별도 상세로 확인한다. 2024년 전체나 다른 상장사로 확대하지 않는다.
4. **자동 보정 job과 순서 조율:** 새 스키마뿐 아니라 API·수집기·화면 SHA를 일치시킨 뒤, 하나의 실행자가 새 사전 스냅샷을 이용해 CAS/감사 적용한다. 이번 준비 파일을 무검토 실행하지 않는다.
5. **미도래 일일 재확인:** 조기 공시 우선 확인, 경과 시 큐 재가동, CURRENT 이후 동작, DB 일정 및 실제 재기동 지속성·중복 방지 증거를 남긴다. 현대홈쇼핑 비활성 우선종목의 PENDING 정체 가능성을 따로 검증한다.
6. **원문 파서:** 경로를 추출하지 않고 제한된 메모리에서 선행 슬래시·접수번호_첨부코드 이름을 검증한다. 선언 UTF-8/실제 CP949 불일치, 5MB 상한, 회사·기간·연결/별도·당기/전기·단위를 각각 검증한다. KB금융 2014년 첨부를 2015년으로 대체하지 않는다.
7. **금융업 정규화:** 이번 BS 부분 대조를 저장 성공으로 확대하지 않는다. 손익·현금흐름 전체 및 금융업 계정 대응·지배/비지배 구분·누적/분기를 검증한 뒤 별도 제한 저장 절차를 검토한다. 미검증 금액은 저장하지 않는다.
8. **실제 화면:** 관리자 세션에서 전체/우선 계획·현재 처리 대상·완료 분자·성공/미도래/미공시/자료 미제공/보류/대기/처리/실패/제외 상세를 DB·API와 직접 대조한다. 숫자만 맞추거나 프론트에서만 숨기는 방식은 사용하지 않는다.

이번 보고서는 **개발 반영 대기 상태의 2차 준비·검증 결과**다. 운영 보정 완료 또는 새 상태 적용 완료로 간주하지 않는다. 문서 PR에서 #288·#289를 연결하여 인계하며, 운영 코드 변경·병합·배포·재시작은 별도 개발 작업으로 유지한다.
