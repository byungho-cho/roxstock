# RoxStock 수집기 설계

**버전:** v0.2  
**작성 기준일:** 2026-09-30  
**상태:** 기존 수집 기능 현행화 및 재무제표 수집 신규 설계; 사업연도별 수집 범위 보완  
**연계 문서:** [기본설계서 v0.5](./매매일지%20설계%20v0.5.md), [DB 스키마 v0.3](./매매일지%20스키마%20v0.3.md), [개발현황](./개발현황.md)

이 문서는 RoxStock 수집기에서 처리하는 데이터별 책임과 실행 주기를 모아 관리한다. `현재 구현`은 2026-09-30 `main`의 코드에서 확인한 범위이며, `신규 설계`는 재무제표 수집을 개발할 때 적용할 기준이다. 운영 서버의 실행 성공 여부는 별도의 실행 기록으로 확인한다. 모든 시각은 `Asia/Seoul` 기준이다.

# 1. 수집기 구성

- Fastify API, 일일 배치 수집기(`backend/src/collector/worker.ts`), 장중 실시간 시세 수집기(`backend/src/collector/realtime-worker.ts`)는 독립 프로세스로 운영한다.
- 현재 배치 수집기는 종목 마스터, 전체 활성 종목 시세, 계좌 스냅샷을 처리한다. 실시간 수집기는 선택 종목 시세를 별도로 처리한다.
- 수집 실행 기록과 중복 실행 방지는 `collector_runs`, `collector_run_items`, `collector_locks`를 사용한다. 각 기능의 원천과 호출량은 서로 구분한다.
- 새 재무제표 수집은 기존 배치 수집기의 독립 작업으로 추가한다. 다른 수집 작업의 실패가 재무제표나 API 서버를 중단시키지 않도록 한다.

# 2. 수집 기능별 설계

## 2.1 종목 마스터 수집 — 현재 구현

| 항목 | 기준 |
|---|---|
| 원천 | 공공데이터포털 KRX 상장종목정보 `getItemInfo_V2` |
| 대상 | KOSPI·KOSDAQ의 유효한 6자리 종목코드 |
| 실행 | 매일 07:00, 설정값 `COLLECTOR_SECURITY_MASTER_HOUR` |
| 저장 | 종목코드·종목명·시장구분을 `securities`에 UPSERT |

최근 데이터가 없으면 과거 기준일로 최대 14일 탐색하고 페이지 전체를 조회한다. 결과가 기본 최소 2,000종목보다 적으면 불완전 응답으로 보고 저장하지 않는다. 누락 종목의 자동 비활성화는 기본적으로 꺼져 있다. DART의 `corp_code` 매핑은 이 원천에 포함되지 않으므로 재무제표 수집용으로 별도 관리한다.

## 2.2 장중 실시간 주가 수집 — 현재 구현

| 항목 | 기준 |
|---|---|
| 원천 | 네이버 금융의 브라우저용 polling 응답. 공식 공개 API가 아니므로 응답 변경을 감시한다 |
| 대상 | 보유·관심·추천 종목의 합집합, 중복 제거, 기본 최대 100종목 |
| 실행 | 평일 프리 08:00~08:50, 정규 09:00~15:30, 애프터 15:40~20:00; 기본 60초 간격 |
| 전달·저장 | 수집기 캐시 → 내부 가격 API → SSE; 정상 가격을 기본 60초마다 `market_prices`에 UPSERT |

기본 동시 요청은 5개다. 무효 가격, 거래시각이 오래된 응답과 휴장·미갱신 응답은 기존 정상 값을 덮어쓰지 않는다. API 전달 실패와 DB 저장 실패를 분리해 기록한다. 이 작업은 아래 일일 전체 종목 수집과 별개다.

## 2.3 전체 종목 장 마감 주가 수집 — 현재 구현

| 항목 | 기준 |
|---|---|
| 원천 | 네이버 금융 polling 응답 |
| 대상 | `securities`의 전체 활성 종목 |
| 실행 | 매일 20:00, 설정값 `COLLECTOR_PRICE_COLLECTION_HOUR` |
| 저장 | 유효하고 최신인 가격만 `market_prices`에 UPSERT |

종목별 순차 요청과 기본 1초 간격으로 원천 부하를 제한한다. 개별 실패는 다른 종목의 처리를 막지 않고, 부분 실패 종목은 한 차례 재시도한다. 전체 원천 장애는 설정된 지연 후 한 차례 재시도한다. 전 종목이 휴장·미갱신이면 `SKIPPED`로 기록한다.

## 2.4 계좌 일별 스냅샷 생성 — 현재 구현

| 항목 | 기준 |
|---|---|
| 원천 | 계좌 예수금·보유 Lot·저장된 정상 주가. 외부 크롤링 없음 |
| 대상 | 활성 계좌 |
| 실행 | 기본 매일 23:00, 설정값 `COLLECTOR_SNAPSHOT_HOURS` |
| 저장 | 계좌·날짜별 현금, 주식평가액, 총자산을 `daily_account_snapshots`에 UPSERT |

보유종목 가격이 하나라도 빠지면 그 계좌의 잘못된 0원 스냅샷을 생성하지 않는다. `daily_position_snapshots`는 선택 구현이며 현재 배치 작업에는 포함되지 않는다.

## 2.5 재무제표 수집 — 신규 설계

Open DART의 공시·재무제표를 수집하여 기존 종목 재무 화면에 제공한다. 대상·주기·정규화·수동 입력과의 관계는 다음 장에서 정한다. 기존 `financial_statements` 테이블과 수동 분석 입력이 있으나, 자동 DART 수집 작업은 현재 구현되지 않았다.

# 3. 재무제표 수집기 설계

## 3.1 대상과 주기

| 구분 | 대상 | 실행 및 목표 |
|---|---|---|
| 우선종목 | 보유·추천·관심 종목의 중복 없는 합집합 | 시간 제한 없이 설정한 시각에 하루 1회 공시 변경 여부 확인. 변경된 보고서만 수집 |
| 일반종목 | 우선종목을 포함한 재무제표 수집 가능 전체 종목 | 매일 18:00~다음 날 06:00에 순환 처리. 각 종목을 약 3개월에 한 번 확인 |
| 최초 구축 | 아직 필요한 보고서가 없는 종목 | 올해 제출분과 최근 완료 3개 사업연도를 단계적으로 수집. 기본 하루 최대 100종목으로 시작하며 중단·재개 가능 |

전체 약 3,000종목을 90일에 확인하려면 야간에 하루 약 35종목(3,000 ÷ 90 ≈ 33.4)에 처리 여유를 더한 설정이 적절하다. 실제 대상이 늘거나 줄면 `ceil(대상 종목 수 / 90)`에 여유를 두어 처리량을 조정한다. 개별 종목의 마지막 **확인** 시각과 마지막 **자료 변경** 시각을 따로 저장한다. 우선종목은 전체 대상에서 제외하지 않으며 최근 우선 조회에서 같은 보고서를 확인했다면 중복 재무 API 호출을 건너뛴다. 일반종목의 새 자료 반영은 최대 약 3개월 지연될 수 있다.

우선종목은 DART 공시 목록에서 신규·정정 여부를 확인하고 해당 보고서만 다시 받는다. 일반종목은 야간 차례가 왔을 때 공시 변경 여부를 확인한다. 공시 목록이 지연되거나 누락되는 경우에 대비해 주기적인 최근 보고서 대조와 실패 재시도를 둔다. 신규 종목은 종목 마스터 등록 후 대기열에 넣는다.

## 3.2 올해와 과거 사업연도 수집

**전체 순환 주기(일반종목 약 3개월 1회)**와 **수집할 재무제표의 사업연도 범위**는 별개다. 종목을 확인할 때 매번 과거 모든 보고서를 다시 요청하지 않는다. 사업연도는 회사의 회계연도 기준으로 식별하며 아직 제출되지 않은 보고서를 요청하지 않는다.

| 자료 범위 | 최초 수집 | 이후 갱신 |
|---|---|---|
| 올해 사업연도 | 현재까지 제출된 1분기·반기·3분기 보고서 및 해당 연도의 사업보고서가 제출된 경우 그 자료 | 우선종목은 매일, 일반종목은 야간 순환 차례에 **신규·정정 접수 여부** 확인 후 변경분만 조회 |
| 최근 완료 사업연도 3개 | 기본값 3개 연도의 1분기·반기·3분기·사업보고서 수집. 4분기 계산에 필요한 3분기 누적과 연간 자료 확보 | 원칙적으로 재수집하지 않으며 정정 보고서가 접수되었거나 데이터 결손이 발견된 경우만 해당 보고서 재조회 |
| 그보다 오래된 연도 | 기본 자동 수집 범위 밖. 필요하면 별도 백필 설정으로 과거 연도를 늘림 | 백필 대상과 호출 한도를 따로 지정하고 수집 기록을 유지 |

예를 들어 현재 사업연도가 2026년이라면 제출된 2026년 분기 자료를 우선 채우고, 완료된 2025·2024·2023년의 연간 및 분기 자료를 순차 수집한다. 2026년 사업보고서는 제출되기 전까지 빈 상태로 두며, 2026년 4분기 계산값도 2026년 사업보고서와 3분기 누적 자료가 모두 있을 때만 생성한다. 12월 결산이 아닌 회사도 실제 보고서의 사업연도와 기간을 따른다.

최초 구축의 종목 처리 순서는 **① 올해 제출분과 가장 최근 완료 연도의 사업보고서 → ② 최근 완료 3개 연도의 나머지 분기·연간 자료 → ③ 필요한 경우 추가 과거 연도**로 한다. ①이 끝난 종목은 ②를 기다리지 않고 최신 재무 화면에서 사용할 수 있다. 최초 구축의 하루 100종목은 **해당 종목의 모든 과거 자료 완료 건수**가 아니라 **처리를 시작한 종목 수의 한도**다. 별도의 실제 API 호출 한도를 넘으면 남은 기간별 작업을 대기열에 저장해 다음 날 이어간다.

기본 범위가 올해 4종류와 완료 연도 3개 × 4종류이면 1종목당 **최대 16개 보고서**가 대상이다. 보고서가 모두 제출된 경우 전체 재무제표 API는 CFS 기준 약 16회, 보고서마다 OFS 대체가 필요하면 최대 약 32회이며 공시 목록 조회·재시도는 추가된다. 올해 미제출 보고서, 이미 저장된 보고서, 일부 미공시 회사는 이보다 적다. 따라서 1년치 4~8회를 여러 해 수집량의 상한으로 해석하지 않는다.

## 3.3 식별과 원천

1. `corpCode.xml` ZIP 목록을 주기적으로 내려받아 `stock_code` 6자리와 RoxStock `securities.symbol`을 정확히 매칭해 8자리 `corp_code`를 관리한다. 종목명 유사성만으로 연결하지 않는다.
2. `list.json`의 정기공시 목록에서 보고서와 정정 공시를 찾고, 접수번호(`rcept_no`)를 기록한다. 목록 조회용 호출은 종목별 재무제표 조회와 별도로 집계한다.
3. `fnlttSinglAcntAll.json`을 사업연도·보고서 종류·연결/별도 기준별로 조회한다. 보고서 코드는 1분기 `11013`, 반기 `11012`, 3분기 `11014`, 사업보고서 `11011`이다. 우선 CFS를 조회하고 해당 보고서에 연결 자료가 없을 때 OFS를 조회한다.
4. `corp_code` 매칭 실패, 재무제표가 없는 종목, 해당 연도에 공시가 없는 종목을 구분해 기록한다. ETF·ETN 등 대상 유형의 적합성은 실제 종목별 DART 매칭 결과로 판단하며 임의의 0원 자료를 생성하지 않는다.

정상 최초 수집에서 **한 종목의 한 사업연도**는 보고서 4종의 CFS 조회 4회, 필요한 경우 OFS 추가 최대 4회로 재무제표 API 4~8회가 기준이다. 공시 목록·고유번호 목록·재시도·정정 조회는 별도 호출이며 고정된 상한이 아니다. 이미 처리한 보고서는 변경이 없으면 재조회하지 않는다.

## 3.4 계정 매핑과 기간 값

- `sj_div`와 표준 `account_id`를 우선 사용해 매출액, 영업이익, 순이익, 총자산, 총부채, 총자본, 영업현금흐름을 매핑한다. 비표준 계정명은 검증된 예외 규칙으로만 처리한다.
- 분기·반기 손익계산서의 `thstrm_amount`는 해당 3개월 금액, `thstrm_add_amount`는 누적 금액으로 구분한다. 재무상태표의 시점 값과 현금흐름표의 기간 누적 값도 혼동하지 않는다.
- 4분기 기간 손익·현금흐름은 연간 누적에서 3분기 누적을 뺀 **계산값**으로 제공한다. 원본 값과 파생값의 구분 및 기준 보고서 접수번호를 남긴다. 앞선 분기 자료나 기준이 부족하면 값을 비워 둔다.
- 자본적지출 등 표준 계정 매핑이 불확실한 값은 추정하지 않고 `null`로 둔다. 통화 단위와 음수 값을 원본에 맞춰 파싱하며 연결/별도 자료를 한 계산에 무심코 섞지 않는다.
- 표본 종목의 실제 원문과 정규화 결과를 대조하고, 회계 업종별 계정 차이는 발견된 사례에 한해 매핑 규칙을 확장한다.

## 3.5 저장, 수동 입력, 정정

현재 `financial_statements`의 UNIQUE는 `(security_id, fiscal_year, period_type)`이고 출처·CFS/OFS·접수번호가 없다. 또한 분석 수정 API가 당해 연간 값 일부를 수동 입력한다. 자동 수집 전에 공시 자료와 수동 입력 자료를 구별할 스키마 마이그레이션을 먼저 설계한다.

- 공시 자료는 종목, 사업연도, 보고서 코드, 연결/별도, 접수번호, 수집 시각, 원본/계산 여부를 추적한다. 원본의 핵심 데이터와 선택된 정규화 값은 정정 후에도 변경 이력을 대조할 수 있게 한다.
- 기존 수동 입력값을 마이그레이션에서 보존하고, 자동 수집으로 덮어쓰지 않는다. 조회 API는 필드별 수동 보정이 있으면 이를 우선 표시하고 나머지는 공시 값을 사용하도록 출처를 함께 제공한다. 수동 값 해제 시 공시 값으로 복귀한다.
- 같은 보고서·접수번호를 다시 받으면 중복 저장하지 않는다. 정정 공시의 접수번호 또는 실제 값이 달라진 경우 새 판본을 기록하고 화면에 적용할 최신 유효 판본을 결정한다.
- EPS·PER·PBR·RIM 등의 계산은 재무제표 원문 수집과 별도 단계로 둔다. 분모인 발행주식수·자기주식수 또는 지배주주 귀속값의 근거가 확보되지 않은 계산값은 자동 생성하지 않는다.

## 3.6 호출량, 장애, 재개

- 한국 날짜별 **종목 확인 건수**와 **DART API 실제 호출 수**를 별도로 기록하고 구성 가능한 일일 한도를 둔다. 우선종목 작업을 먼저 처리하며 전체 호출 한도에 도달하면 일반 대기열을 다음 날 이어간다. 개인 키의 실제 허용량은 Open DART 이용현황으로 확인하고, 일반적인 20,000회 안내를 사용자 키의 확정 한도로 간주하지 않는다.
- 야간 작업은 고정 간격·낮은 동시성으로 나눠 처리하고 종목별 처리 완료 시각 및 대기열 진행 위치를 DB에 기록한다. 재시작·프로세스 중복 실행 시 DB 락과 멱등 저장으로 안전하게 이어간다.
- DART의 데이터 없음(013)은 정상 미공시·미대상으로 구분하고, 요청 제한(020)은 당일 추가 호출을 중단한다. 네트워크 장애·일시적 서비스 장애는 제한적으로 재시도한다. 실패하더라도 기존 정상 재무 값은 유지한다.
- `collector_runs`와 `collector_run_items`에 우선/일반/최초 구축 실행 종류, 성공·실패·건너뜀, API 호출 수, 공시 판본과 오류 사유를 남긴다. 로그에는 API 인증키를 출력하지 않는다.

## 3.7 개발 완료 기준

1. 우선종목 하루 1회, 일반종목 야간 순환 및 약 90일 이내 재확인, 최초 수집 중단·재개와 중복 건너뛰기를 확인한다.
2. 올해 제출분과 최근 완료 3개 사업연도의 최초 백필, 미제출 보고서 제외, CFS 우선/OFS 대체, 4종 보고서, 분기·누적·4분기 계산, 보고서 정정과 미공시 사례를 검증한다.
3. 수동 입력값 보존·표시 우선순위와 출처 표기를 기존 분석 API·재무 화면에서 검증한다.
4. 호출 제한, 013·020 오류, 네트워크 장애 및 DB 재시작 후 재개를 확인한다.
5. 완료 보고에 실제 적용 시각, 일일 종목·호출 한도, 첫 구축 진행률, 마지막 성공 시각과 미수집 사유를 포함한다.

# 4. 구현 전 확인 항목

- 수집기의 DART 키는 기존 공공데이터포털 키와 별도로 환경변수로 주입한다. 키 값은 설계서와 로그에 넣지 않는다.
- Open DART 공식 문서: [고유번호](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019018), [공시검색](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019001), [단일회사 전체 재무제표](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS003&apiId=2019020).
- 배포 후 수집 데이터와 화면 결과는 사용자 직접 확인을 전제로 하되, 개발자는 배포 전 자동 검증 및 로그를 확인한다.
