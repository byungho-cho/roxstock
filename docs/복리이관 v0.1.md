# 복리목표 이관 명세

**버전:** v0.1  
**기준:** 매매일지 설계 v0.6

# 1. 목적

기존 `compound_growth_goals` 단일 구조를 `compound_growth_plans` 1:N `compound_growth_goals` 구조로 안전하게 이관합니다. 기존 데이터가 없으면 이관 로직을 실행하지 않고 새 구조로 시작합니다.

# 2. 묶음 기준

다음 값이 모두 같은 기존 행을 계획 한 건으로 묶습니다.

- `account_id`
- `period_name`
- `start_date`, `end_date`
- `initial_asset_value`
- `annual_contribution_amount`

하나라도 다르면 별도 계획입니다. 계획명은 기존 `period_name`을 사용합니다. 같은 계좌에서 계획명이 충돌하면 `period_name + 시작연도`를 후보로 만들고 이관 전에 충돌 목록을 검토합니다.

# 3. 목표 변환

| 기존 값 | 신규 값 |
|---|---|
| 묶음의 공통값 | `compound_growth_plans` |
| `goal_name` | 목표 `goal_name` |
| `annual_target_rate` | 목표 `annual_target_rate` |
| 표시색상 | 목표 `color_key` |
| `is_visible` | 목표 `is_visible` |
| `display_order` | 목표 `display_order` |
| `memo` | 목표 `memo` |

기본 목표는 다음 우선순위로 한 건을 선택합니다.

1. 목표명이 `기준형`인 행
2. `display_order`가 가장 작은 행
3. 기존 `id`가 가장 작은 행

# 4. 대응표

이관 실행기는 다음 대응표를 CSV 또는 JSON으로 남깁니다.

| legacy_goal_id | new_plan_id | new_goal_id | group_key | status |
|---:|---:|---:|---|---|

대응표는 애플리케이션 데이터 테이블이 아니라 배포 산출물로 보관합니다.

# 5. 실행 순서

1. 사전 점검으로 건수, 중복 계획명, 잘못된 날짜·금액을 출력합니다.
2. 새 계획·목표 테이블을 준비합니다.
3. DB 트랜잭션을 시작합니다.
4. 묶음별 계획을 생성하고 기존 목표를 하위 목표로 생성합니다.
5. 계획별 기본 목표를 한 건 지정합니다.
6. 대응표와 검증 결과를 생성합니다.
7. 검증이 모두 통과하면 커밋하고, 실패하면 롤백합니다.
8. 기존 테이블은 즉시 삭제하지 않고 `compound_growth_goals_legacy`로 보존합니다.
9. 운영 확인 후 별도 배포에서 기존 테이블을 삭제합니다.

# 6. 필수 검증

- 기존 목표 수 = 신규 목표 수
- 모든 기존 ID가 대응표에 정확히 한 번 존재
- 모든 신규 목표가 계획 FK를 가짐
- 목표가 있는 계획은 기본 목표가 정확히 한 건
- 계획 공통값과 기존 행 공통값이 일치
- 동일 계좌 계획 기간이 서로 겹치지 않음
- 계획별 목표명 중복 없음

# 7. 개발 전달사항

DDL과 데이터 이관을 분리합니다. 기존 초기 마이그레이션을 수정하지 않고 새 Prisma 마이그레이션과 별도 TypeScript 이관 명령으로 구현합니다. `--dry-run`에서 사전 점검과 예상 건수만 출력할 수 있어야 합니다.
