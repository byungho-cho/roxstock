# 1. 설계 결론

- 매수와 매도는 `buy_trades`, `sell_trades`로 분리합니다.
- 한 매수는 하나의 독립된 Lot이며 여러 매도를 가질 수 있습니다.
- 한 매도는 반드시 하나의 매수 Lot만 참조합니다.
- 여러 매수 Lot을 한 번에 매도하는 기능은 제공하지 않습니다.
- 보유현황은 조회 시 계산하며 `positions` 테이블을 저장하지 않습니다.
- 예수금은 `accounts.cash_balance`에 현재 실제 금액을 유지합니다.
- 거래·배당·예수금 변동은 최초 등록 때만 현재 예수금에 자동 반영합니다.
- 거래·배당·예수금 내역 수정·삭제 시 현재 예수금을 다시 계산하지 않습니다.
- 현재가, 일별 스냅샷, 가치투자 정보와 복리계획별 여러 하위 목표를 관리합니다.
- Figma는 화면 표현 기준이고, 계산·데이터 충돌 시 이 설계서의 업무 규칙을 우선합니다.

# 4. 매수·매도

## 4.1 매수 Lot

`buy_trades` 한 행이 매수 Lot 한 건입니다. 현재 보유수량과 종목 전체 평균단가는 조회 시 계산할 수 있지만, 평균단가는 매도 연결이나 실현손익 원가로 사용하지 않습니다.

## 4.2 매도

`sell_trades.buy_trade_id`는 한 `buy_trades.id`만 참조합니다. 잔여수량보다 많은 매도는 허용하지 않습니다.

```text
잔여수량 = 매수수량 - 연결된 매도수량 합계
실현손익 = 매도수량 × (매도단가 - 연결된 매수단가)
```

실현손익, 잔여수량과 총거래금액은 저장하지 않고 조회 시 계산합니다.

## 4.3 수정과 삭제

- 거래 수정은 매수·매도 기록만 변경하고 현재 예수금을 다시 반영하지 않습니다.
- 연결된 매도가 없는 매수는 바로 삭제할 수 있습니다.
- 연결된 매도가 있는 매수는 연결 매도 건수를 포함한 확인창을 표시합니다.
- 사용자가 확인하면 연결 매도를 먼저 삭제하고 매수를 삭제합니다.
- 연결 매도와 매수 삭제는 하나의 DB 트랜잭션으로 처리합니다.
- DB FK는 `ON DELETE RESTRICT`로 유지합니다.
- 일괄삭제 UI와 소프트 삭제는 제공하지 않습니다.
- 매도 단건 삭제는 연결 매수를 보존하고 삭제 수량만큼 Lot 잔여수량을 복원합니다. 거래내역 카드 삭제는 항상 해당 매도 1건이며 매수 삭제와 구분합니다.
- 거래 삭제로 예수금과 과거 스냅샷을 자동 변경하지 않습니다.

# 5. 예수금과 거래비용

## 5.1 현재 예수금

`accounts.cash_balance`는 현재 증권계좌에서 확인한 실제 예수금입니다. 사용자는 이 값을 직접 수정할 수 있고 보정 이력은 따로 저장하지 않습니다.

## 5.2 예수금 변동

`cash_transactions.transaction_type`은 다음 값을 사용합니다.

```text
BUY, SELL, DEPOSIT, WITHDRAWAL, DIVIDEND
```

| 유형 | 최초 등록 시 현재 예수금 계산 |
|---|---|
| BUY | 이전 예수금 - 매수금액 - 수수료·세금 |
| SELL | 이전 예수금 + 매도금액 - 수수료·세금 |
| DEPOSIT | 이전 예수금 + 입금액 |
| WITHDRAWAL | 이전 예수금 - 출금액 |
| DIVIDEND | 이전 예수금 + 세후 배당금 |

수수료와 세금은 `fee_tax_amount` 하나로 통합합니다. 거래·배당 테이블과 예수금 내역 사이에는 FK를 두지 않습니다.

거래·배당·예수금 변동 내역은 최초 등록할 때만 현재 예수금에 반영합니다. 이후 수정·삭제 시에는 비용 차액을 포함하여 현재 예수금을 자동 변경하지 않습니다. 실제 잔액과 차이가 있으면 사용자가 `accounts.cash_balance`를 직접 수정합니다.

```text
월별 비용 = 해당 월 fee_tax_amount 합계
연도별 비용 = 해당 연도 fee_tax_amount 합계
```

## 5.3 예수금 화면

- 현재 예수금과 마지막 갱신시각을 표시합니다.
- 월간·연간 정보를 하나의 통합 기간 카드에서 전환합니다.
- 최초 진입은 현재 월의 월간 상태입니다.
- 월간과 연간의 마지막 조회 기간을 각각 보존합니다.
- 월간은 출금·입금·배당을, 연간은 연간 합계를 표시합니다.
- 기간은 좌우 버튼과 스와이프로 순환 탐색합니다.
- 최근 변경은 `구분 | 날짜 | 금액` 3열로 최신 10개를 표시합니다.
- `이전 1개월 불러오기`로 과거 내역을 추가합니다.
- 데이터가 없는 기간도 같은 구조의 빈 상태로 표시합니다.
- Figma 삭제 확인창의 “삭제하면 예수금에서 제외” 문구는 사용하지 않습니다.
- 수정·삭제 화면에는 현재 예수금이 자동 변경되지 않는다는 안내를 표시합니다.

# 6. 배당

`dividends`에는 세전 `gross_amount`와 세후 `net_amount`를 함께 저장합니다.

```text
배당소득세 = gross_amount - net_amount
연도별 실수령 배당금 = 해당 연도 net_amount 합계
```

배당 최초 등록과 세후 금액의 예수금 증가는 한 DB 트랜잭션으로 처리합니다. 이후 배당 수정·삭제는 현재 예수금을 자동 변경하지 않습니다.

# 7. 종목목록과 가치투자

## 7.1 통합 목록

표시 탭은 **보유종목→관심종목→거래종목**이다. 종목 추가는 관심/보유 선택을 매수 유무와 관계없이 저장한다. 추천 분류 및 과거 거래 이력에 따른 관심/보유 제한은 폐기한다. 수동 보유 분류는 매수 Lot·수량·자산을 생성하지 않는다.

거래 이후 잔여수량>0이면 보유, 거래 이력 있고 잔여수량0이면 거래종목으로 전환한다. 거래 없는 수동 보유는 선택 분류를 유지한다. 거래종목은 자동 상태이며 추가 선택지에 포함하지 않는다. 실제 자산 집계는 잔여수량>0 기준이다. 계좌별 저장·중복 표시 방지·기존 추천 데이터 보존과 이관 검토는24장을 따른다. 새 enum/API/DB 마이그레이션이 이미 구현됐다고 가정하지 않는다.

## 7.2 보유종목

- 보유수량·매수단가·매입금액·현재가·평가금액·평가손익·수집상태를 표시합니다.
- 종목 상세는 `요약 | 보유 현황 | 거래내역` 탭을 제공합니다.
- 보유 현황은 Lot별 보유일, 잔여수량, 매수금액, 예상 평가와 목표수익률별 단가·총액을 표시합니다.
- 거래내역은 각 매도와 연결 매수를 한 묶음으로 표시하며 카드 수정·삭제는 해당 매도에만 연결합니다. 부분매도 Lot은 잔여수량으로 유지하고 전량 매도 기록은 거래종목에서 조회합니다.
- 매수 후 평균단가는 종목 전체 참고값으로만 표시합니다.

## 7.3 관심종목과 가치분석

- 관심 목록은 현재가, 등락, PER, PBR, ROE, W 값과 메모를 표시합니다.
- 가치분석은 RIM 기준 W별 적정주가와 상승여력을 제공합니다.
- 재무지표는 연간·분기 전환과 수익성·안정성·성장성 항목을 제공합니다.
- 직접 수정 화면에서는 자동 계산 지표와 계산 기초 데이터를 함께 보여줍니다.

# 8. 현재가와 수집

## 8.1 수집 계층

`market_prices`는 종목별 최신 가격 한 행만 유지합니다. 전체 종목의 종가 보정과 사용자가 실제로 보는 선택 종목의 장중 시세를 서로 다른 작업으로 분리합니다.

| 작업 | 대상 | 기본 일정·주기 | 결과 |
|---|---|---|---|
| 종목 마스터 | KOSPI·KOSDAQ 전체 활성 종목 | 매일 07:00 | `securities` UPSERT |
| 장중 실시간 시세 | `HOLDING + WATCHLIST + RECOMMENDED` 합집합, 최대 100종목 | 평일 프리 08:00~08:50, 정규 09:00~15:30, 애프터 15:40~20:00, 60초 | 메모리 캐시 갱신 및 SSE 전송 |
| 실시간 DB 반영 | 위 장중 실시간 대상 | 60초 | `market_prices` UPSERT |
| 장 마감 시세 | 전체 활성 종목 | 매일 20:00, 1회 | `market_prices` 최종 UPSERT |
| 계좌 스냅샷 | 전체 계좌 | 매일 23:00, 1회 | `daily_account_snapshots` UPSERT |

모든 시각은 `Asia/Seoul` 기준입니다. 장중 실시간 수집의 기본 간격은 60초이며 환경변수로 최소 5초까지 조정할 수 있습니다. 공식 호출 한도가 보장되지 않은 외부 원천의 부하와 개인용 화면의 실시간성 요구를 함께 고려해 운영 기본값은 60초로 유지합니다.

NXT 프리마켓 종료 후 정규장 시작 전인 08:50~09:00과, KRX 종가 형성 후 NXT 애프터마켓 시작 전인 15:30~15:40에는 수집을 멈춥니다. NXT 거래 대상이 아닌 종목은 프리·애프터 세션에서 기존 마지막 정상 KRX 가격을 유지하며 0원이나 빈 값으로 덮어쓰지 않습니다.

## 8.2 실행 프로세스

- Fastify API, 일일 배치 수집기, 장중 실시간 수집기는 각각 독립 프로세스와 Docker Compose 서비스로 실행합니다.
- 장중 실시간 수집기의 장애·재시작은 API 서버와 일일 배치 수집기를 중단시키지 않습니다.
- 공통 Prisma 연결, 가격 타입, 공급자 인터페이스와 로깅은 기존 백엔드 코드를 공유합니다.
- 장중 수집 대상의 분류 연계는24장의 추천 폐기·기존 데이터 이관 계약에 맞춰 개발에서 검토합니다. `security_id` 기준 중복 제거는 유지하며 문서 변경만으로 기존 추천 대상 데이터를 삭제하지 않습니다.
- 관심/보유 및 자동 거래 상태 변경 시 수집 대상 정책에 맞춰 다음 대상 갱신 회차에 반영합니다. 실제 수집 대상 전환은 개발 확인 항목입니다.
- 실제 거래에 따른 보유/거래 자동 전환과 사용자의 관심/보유 등록을 구분합니다. 매수 유무로 수동 등록을 차단하지 않습니다.

## 8.3 실시간 전달과 저장

1. 실시간 수집기가 선택 종목 시세를 60초 간격으로 수집합니다.
2. 유효한 가격을 수집기 프로세스 메모리 캐시에 즉시 반영합니다.
3. 수집기는 Bearer 토큰으로 보호된 내부 `POST /internal/realtime-prices`를 호출하여 API 프로세스 캐시로 전달합니다.
4. API는 SSE(Server-Sent Events)로 연결된 React 화면에 변경 가격을 전송합니다.
5. 프론트엔드는 SSE 메시지를 받으면 해당 종목만 갱신합니다.
6. SSE 연결이 끊기면 최신 가격 REST API를 10초 간격으로 조회하는 폴백을 사용합니다.
7. DB 쓰기 부하는 줄이기 위해 수집기 캐시의 최신 정상 가격을 기본 60초마다 `market_prices`에 UPSERT합니다.
8. API 전달 실패와 관계없이 DB 저장은 계속하며, 20시 전체 종목 수집 결과가 당일 최종 마감 가격을 보정합니다.

SSE는 서버에서 브라우저로의 단방향 가격 전달에 적합하며 React에서는 하나의 연결을 공유합니다. 화면·탭별로 별도 외부 시세 요청을 생성하지 않습니다.

## 8.4 외부 원천과 호출 제어

1차 가격 원천은 네이버 금융 브라우저용 polling JSON 응답을 사용합니다. 공식 공개 API가 아니므로 응답 형식과 접근 정책이 바뀔 수 있으며 공급자 코드는 인터페이스 뒤에 격리합니다.

- 종목코드는 `securities.symbol`의 6자리 코드를 사용하고 `A005930` 형식은 `005930`으로 정규화합니다.
- 프리·애프터마켓에서는 `overMarketPriceInfo.overMarketStatus=OPEN`이고 세션이 `PRE_MARKET` 또는 `AFTER_MARKET`일 때 `overPrice`와 해당 `localTradedAt`을 사용합니다.
- 정규장에서는 기본 현재가와 거래시각을 사용합니다. API의 `marketStatus`는 NXT 세션일 때 `NXT_PRE_MARKET` 또는 `NXT_AFTER_MARKET`으로 전달합니다.
- 동시 요청 수는 기본 5개로 제한하고 전체 회차가 끝나기 전에 다음 회차를 겹쳐 실행하지 않습니다.
- 공급자가 다중 종목 응답을 안정적으로 제공하는 것이 확인되면 배치 단위 호출로 교체할 수 있습니다.
- 인증이 필요한 원천을 추가할 때 키는 환경변수로만 관리하고 Git에는 저장하지 않습니다.
- 원천별 응답 변환은 공급자 모듈에서 처리하여 수집·저장 로직과 분리합니다.

## 8.5 정합성·실패 처리

- 가격이 0, 빈 값, 비정상 숫자이면 저장하거나 전송하지 않습니다.
- 수집 실패 시 마지막 정상 가격을 캐시와 DB에 유지합니다.
- 사용자가 수동 수정한 가격은 다음 정상 자동 수집 성공 시 갱신합니다.
- 공급자 응답의 거래시각 `providerTimestamp`가 현재 저장값보다 오래되면 덮어쓰지 않습니다.
- 휴장일, 장 운영상태 종료, 거래시각 미갱신은 성공과 구분하여 `STALE` 또는 `SKIPPED`로 기록합니다.
- 개별 종목 실패는 다른 종목의 수집을 중단시키지 않습니다.
- 동일 실시간 회차의 중복 실행은 프로세스 락으로 차단하고, 여러 인스턴스 운영 시 DB 락을 함께 사용합니다.
- 실행 시작·종료, 대상 수, 성공·실패·STALE 수, 종목별 실패 사유를 구조화 로그에 남깁니다.
- 수집상태는 영구 가격 데이터보다 최신 수집 실행 결과와 응답 상태로 우선 제공합니다.

# 9. 스냅샷

## 9.1 계좌 스냅샷

`daily_account_snapshots`는 `cash_balance`, `stock_value`, `total_asset_value`를 저장합니다. `account_id + snapshot_date`를 UNIQUE로 둡니다.

## 9.2 종목 스냅샷

`daily_position_snapshots`는 종목별 수량, 매입금액, 현재가, 평가금액과 미실현손익을 저장합니다. 종목별 스냅샷은 선택 구현입니다.

## 9.3 실행 규칙

- 현재 운영 기본값은 한국 시간 23시 1회 실행이며 같은 계좌·날짜를 UPSERT합니다.
- 향후 장중 자산 추이가 필요하면 1시간 간격 갱신을 선택적으로 활성화할 수 있습니다.
- 한국 시간 23시 실행을 당일 마지막 예정 갱신으로 사용합니다.
- `is_final`은 두지 않습니다.
- 시세가 없으면 잘못된 0원 스냅샷을 만들지 않습니다.
- 거래나 예수금 변경으로 과거 날짜 스냅샷을 수정하지 않습니다.

# 10. 복리계획과 복리목표

Figma 최종 통합 구조인 `복리계획 1 : 복리목표 N`을 사용합니다. 1차·2차·3차처럼 기간이 다른 차수는 계획이고, 같은 기간의 안정형·기준형·공격형은 하위 목표입니다.

## 10.1 복리계획

`compound_growth_plans`는 계좌, 계획명, 시작일, 종료일, 시작자산, 연간 추가 투자금, 표시순서와 상태를 저장합니다.

## 10.2 하위 목표

`compound_growth_goals`는 `plan_id`, 목표명, 연 목표수익률, 표시색상, 기본 목표 여부, 표시 여부와 표시순서를 저장합니다.

- 계획을 만들면 기준형 목표 한 개를 자동 생성합니다.
- 계획 목록의 올해 목표·최종 목표·진행률은 기본 목표 기준입니다.
- 기본 목표 변경은 확인창을 거칩니다.
- 시작연도 선택 시 5년 범위를 제안하지만 시작·종료연도를 수정할 수 있습니다.
- 같은 연도를 선택한 1년 계획도 허용합니다.
- 화면에는 일반적으로 목표 3개를 우선 표시하지만 저장 개수에는 제한이 없습니다.

## 10.3 계산 기준

연간 추가 투자금은 첫해부터 연초에 기초자산에 더한 뒤 해당 연도의 목표수익률을 적용합니다.

```text
첫해 목표자산
= (시작자산 + 연간추가금) × (1 + 목표수익률)

다음 해 목표자산
= (직전 목표자산 + 연간추가금) × (1 + 목표수익률)
```

Figma에 표시된 연말 추가 방식의 예시 금액과 안내문은 구현 기준으로 사용하지 않습니다. 화면 예시 데이터는 위 공식에 맞춰 교체합니다.

# 12. 화면별 설계

## 12.1 홈과 평가자산

- 기획 페이지명·메뉴명은 홈(C1000/T1000)입니다. 화면 내부 제목은 확정 프레임을 따릅니다.
- 홈 상단 +는 종목 추가로 이동하고 성공 후 1100 종목목록의 해당 탭을 엽니다. 거래등록은 종목 상세·매매일지에서 1101을 공통 호출합니다.
- 평가자산·오늘손익은 적색, 주식평가액은 연두색, 예수금은 노란색을 사용합니다.
- 평가자산·예수금·오늘손익·자산추이 카드는 각각 관련 상세 화면으로 이동합니다.
- 보유종목 제목은 목록으로, 개별 행은 해당 종목 상세로 이동합니다.
- 평가자산 화면은 `매입금액 | 평가손익 | 주식평가액`과 전일 대비를 제공합니다.
- 자산구성은 주식·예수금 금액과 비율을 표시합니다.

## 12.2 매매일지 (1200)와 하위 일별손익

- 매매일지 기본 화면은 월간 달력입니다.
- 날짜별 매수·매도 건수와 선택 날짜의 거래 요약을 표시합니다.

- 날짜 선택 영역은 세로 스크롤 시 상단에 고정합니다.

# 14. 자산과 손익 계산

```text
Lot 평가금액 = 잔여수량 × 현재가
Lot 평가손익 = 잔여수량 × (현재가 - 매수단가)
주식 평가금액 = 모든 보유 Lot 평가금액 합계
총 평가자산 = 주식 평가금액 + 현재 예수금
현금 비중 = 현재 예수금 ÷ 총 평가자산 × 100
기간 투자손익 = 평가손익 + 실현손익 + 배당수익 - 수수료·세금
현재 총자산 = 기간 시작자산 + 순입출금 + 기간 투자손익
```

일별손익·기간성과·투자손익은 기존 거래·배당·예수금·스냅샷에서 계산하는 조회모델로 제공하며 별도 집계 테이블은 두지 않습니다.

## 2026-10-01 목표가 도래 정의 교체

이 기능은 종목별 매도 목표가 비교가 아니라 **선택 계좌 매수 Lot의 보유기간별 목표수익률 달성**이다. 기본 독립 조건은 7일/5%, 30일/10%, 90일/15%, 180일/20%, 365일/30%이며 각 조건은 기간 AND 수익률, 조건 간 OR다. 매수 당일0일, KST 달력일, 잔여수량>0, 개별 Lot 단가 기준이며 평균단가를 사용하지 않는다. 경계 포함·반올림 이전 판정·대표 최단 기간·중복 Lot 제거를 적용한다.

2100 설정은 계좌별 조건 추가·수정·삭제(최대5개)를 저장한다. 명시적 빈 조건은 비활성이다. 홈은 전체 도달 Lot 수를 표시하고 최대5건을 요약한다. C1003/T1003 전체 목록에서 모든 결과를 볼 수 있다. 최근 매수 카드 요구는 유지한다. 홈 본문 단일 스크롤·최하단80px·공통헤더/하단44px을 적용한다.

계산·검증·API·이동·오류·설정 계약은 [목표가 도래 설계 v0.2](./RoxStock%20목표가%20도래%20설계%20v0.2.md)를 개발 정본으로 사용한다. 이전 방식과 충돌하는 정의는 본 명세를 우선한다. 과거 버전 문서는 작성 당시 기록으로 보존한다.


# 20. 홈 목표가 도래 설계 (2026-10-01 추가)

사용자 확정 요구사항으로 추가한 항목이며 구현·QA·배포 완료를 의미하지 않는다. 이전의 종목별 매도 목표가 비교 해석을 대체한다. 적용 화면은 C1000/T1000 홈, 2100 설정, 홈 하위 전체 목록과 Lot 상세다. 최근 매수 카드의 기존 요구사항은 유지한다.

## 20.1 목적과 범위

선택된 계좌의 잔여 보유 Lot 중 보유기간별 목표수익률을 달성한 항목을 조회한다. 자동 매도·주문·알림 발송 기능은 포함하지 않는다. 목록은 현재 상태를 계산하는 것이며, 과거에 한 번 도달한 항목을 영구 보존하는 이력이 아니다.

## 20.2 기본 조건과 설정

| 보유기간 상한(달력일) | 최소 평가수익률 |
| --- | --- |
| 7 | 5% |
| 30 | 10% |
| 90 | 15% |
| 180 | 20% |
| 365 | 30% |

각 조건은 독립적인 OR 조건이다. 각 조건 안에서는 보유일수 상한과 최소 수익률을 모두 만족해야 한다. 기간 구간을 서로 배타적으로 나누지 않는다. 경계값은 포함한다.

설정에서 조건 추가·수정·삭제를 제공한다. 조건은 최대 5개이며 보유기간 오름차순으로 표시한다. 보유기간은 1 이상의 정수, 수익률은 0보다 큰 유한한 수치다. 같은 기간 상한은 중복 저장하지 않는다. 5개이면 추가 버튼을 비활성화하고 이유를 안내한다.

초기 조건은 위 5개다. 사용자가 명시적으로 전부 삭제한 빈 설정은 기능 비활성 상태이며, 기본값을 다시 자동 삽입하지 않는다. 최초 설정 미생성과 명시적 빈 설정을 구분한다. 저장 성공 후 홈 조회를 갱신하고 실패하면 입력을 보존한다. 프론트와 백엔드 모두 개수·중복·입력값을 검증한다.

설정 저장 범위(사용자 공통/계좌별), 수익률 입력 소수 자릿수 및 최대 입력 범위는 기존 설정 구조를 확인해 개발 확정 기준은 아래 개발 명세를 따른다. 이 항목은 이를 사용자 확정사항으로 임의 지정하지 않는다.

## 20.3 Lot별 계산

같은 종목의 분할매수도 독립 Lot으로 처리한다. 종목 평균 매수단가를 사용하지 않는다.

- 보유일수: 오늘의 Asia/Seoul 달력 날짜 − 매수일의 Asia/Seoul 달력 날짜
- 매수 당일: 0일
- 날짜형 매수일은 그대로 날짜로 취급하고, 시각형 값은 한국시간 날짜로 변환한다.
- 달력 날짜 차이로 계산하며, 시각 차이를 24시간으로 나눈 값은 사용하지 않는다.
- 잔여수량: 매수수량 − 해당 Lot에 연결된 매도수량 합계
- 평가수익률(%): (현재가 ÷ 해당 Lot 매수단가 − 1) × 100
- 평가이익액(원): (현재가 − 해당 Lot 매수단가) × 잔여수량
- 수수료·세금은 위 평가 계산에 별도로 차감하지 않는다.
- 잔여수량이 0인 전량 매도 Lot은 제외한다.
- 미래 매수일, 잘못된 수량·단가·시세는 임의 보정하지 않고 판정 불가로 구분한다.

조건 일수 D, 최소수익률 R에 대해 다음을 모두 만족하면 해당 조건을 충족한다.

1. 잔여수량 > 0
2. 0 ≤ 보유일수 ≤ D
3. 평가수익률 ≥ R

표시를 위해 반올림하기 전의 값으로 판단한다. 금액·수익률 비교는 기존 Decimal 계산 정책을 사용하며 부동소수점 오차로 경계값이 달라지지 않게 한다. 나눗셈 없이 비교하는 경우 현재가 × 100 ≥ 매수단가 × (100 + R)로 판정할 수 있다.

현재가 미수집 또는 유효하지 않은 매수단가는 0으로 채우지 않는다. 기존 시세 유효성 정책과 수집 기준 시각을 함께 사용한다.

## 20.4 중복 충족·정렬·조회

하나의 Lot이 여러 조건을 충족해도 한 번만 표시한다. 대표 조건은 충족 조건 중 기간 상한이 가장 짧은 조건이다. 대표 조건은 Lot 상세에서 확인하고 홈 두 줄 행에는 추가하지 않는다.

정렬:
1. 평가수익률 내림차순
2. 동률이면 매수일이 오래된 순
3. 동일 날짜이면 Lot ID 기준으로 안정적인 순서 유지

홈은 최대 5건만 표시하고 전체 충족 Lot 건수를 제공한다. 전체가 5건 초과이면 “더보기”를 표시한다. 정확히 5건이면 표시하지 않는다. 설정 조건 5개 제한과 홈 표시 5건 제한은 별개이며 전체 조회 결과 수에는 5건 제한을 두지 않는다.

전체 목록은 동일한 계좌·조건·판정·정렬을 사용한다. 많은 결과는 페이지 단위 추가 조회를 사용하며 한 조회의 계산시각·시세·설정 기준을 유지해 중복/누락을 방지한다. 설정 또는 계좌 변경 시 기존 페이지와 캐시를 초기화한다. 구체적인 API 경로·커서 구조는 기존 API와 맞춰 개발 시 확정한다.

목록 행은 해당 Lot의 기존 상세로 이동한다. 전체 목록은 홈 하위 화면으로 번호를 지정하며 대메뉴를 새로 만들지 않는다. 번호는 현행 화면번호표에서 중복 여부를 확인해 배정한다.

## 20.5 두 줄 행 표시

| 줄 | 표시 순서 | 정렬·색상 |
| --- | --- | --- |
| 첫째 | 종목명 / 현재가 | 종목명 왼쪽, 현재가 빨간색·오른쪽 |
| 둘째 | 매수일(보유일수) / 잔여수량 × 매수단가 / 평가수익률 / 평가이익액 | 수익률 빨간색, 평가이익액 빨간색·오른쪽 |

- 날짜: YY.MM.DD, 예: 26.02.10 (10일)
- 수량: 해당 Lot 잔여수량. 분할매도 전의 최초 수량과 혼동하지 않는다.
- 금액: 원 단위, 천 단위 쉼표. 이 행은 프로젝트의 일반 만원 축약보다 본 표시 명세를 우선한다.
- 수익률: 소수점 한 자리
- 같은 종목의 다른 Lot은 각각 별도 두 줄 행
- 현재가 빨간색은 이 목록의 지정 규칙으로 전일 등락 색상과 별개다.
- 큰 금액·긴 종목명·커버 370px에서 겹침과 잘림 없이 검수한다.

계산 예시: 현재가 200,000원, 매수단가 180,000원, 잔여 10주이면 수익률 11.1%, 평가이익액 200,000원이다. 매수일 2026-02-10에 보유 10일인 예시는 기준일 2026-02-20이다. 화면의 실제 오늘 날짜에서 보유일수를 고정하지 않는다.

## 20.6 카드·상태·갱신

홈 순서: 기존 보유종목 → 목표가 도래 → 최근 매수.

제목은 “목표가 도래”, 설명은 “보유기간별 목표수익률 달성”이다. 제목 오른쪽은 전체 충족 Lot 건수이며 종목 수와 구분한다. 설정 아이콘은 조건 편집 영역으로 연결한다.

| 상태 | 표시 |
| --- | --- |
| 정상 판정 완료, 충족 0건 | 현재 목표가 도래 항목이 없습니다. |
| 설정 조건 0개 | 조건 미설정 안내와 설정 진입 |
| 일부 Lot 판정 불가 | 확인된 결과와 일부 판정 불가 안내 |
| 전체 판정 불가 | 시세 등 판정 불가 이유 표시 |
| 조회 실패 | 오류 안내와 재시도 |

전체 목록에도 동일한 빈 상태 문구를 사용한다. 조회 실패 또는 일부/전체 판정 불가를 정상 0건으로 표시하지 않는다. 판정 불가가 있으면 건수는 확인 가능한 Lot 기준임을 안내한다.

현재가 수집 기준 시각과 목록 계산시각을 구분한다. 갱신 중 기존 목록을 유지하고 전체 카드 로딩 문구로 교체하지 않는다. 오류 시 기존 결과가 마지막 성공 시점의 자료임을 알린다. 갱신 완료 후 현재 조건을 재평가하고 미충족 Lot은 제거한다. 계좌 변경 시 다른 계좌 결과를 유지해 보여주지 않는다.

## 20.7 개발 데이터 계약

다음은 필요한 정보의 논리적 목록이며 기존 DB 필드명이나 신규 API 완료 선언이 아니다.

- 설정: 조건 식별자, 기간 상한, 최소수익률, 저장 범위, 설정 변경 버전
- 항목: 계좌 ID, Lot ID, 종목 ID/명, 매수일, 보유일수, 잔여수량, Lot 매수단가, 현재가, 평가수익률, 평가이익액, 대표 충족 조건, 시세 기준시각
- 목록 메타: 계산시각, 전체 충족 Lot 수, 판정 불가 수/상태, 적용 설정 버전, 추가 조회 정보
- 기존 API 정책에 맞춰 Decimal 직렬화 형식을 유지하고 표시용 값을 판정 입력으로 재사용하지 않는다.
- 단일 판정 로직을 요약·전체 목록에서 공유한다. 프론트가 다른 공식으로 재판정하지 않는다.
- 기존 사용자/계좌 권한과 조회 범위를 유지한다. 목표 판정은 거래·예수금·스냅샷 데이터를 변경하지 않는다.

기존 구현 계약과 사용자 확정 요구를 통합한다. 21.1은 현재 반영된 API·화면 현황이고, 21.2~21.7은 확정 요구 및 후속 검증 기준이다. 두 범위의 구현 완료를 혼동하지 않는다.

## 21.1 현재 반영된 구현 계약 (#49)

- 화면 진입과 연도·범위 선택은 저장 데이터 조회만 수행한다. 업데이트 버튼만 수집 POST를 호출한다.
- POST `/api/securities/:id/financial-refresh`: `{ fiscalYear: 정수(2015~현재), period: Q1|Q2|Q3|ANNUAL|ALL }`. ALL은 1분기·반기·3분기·사업보고서이다. Q4 단독은 받지 않는다(기존 조회에서 연간-3분기 누적으로 계산).
- 202 응답의 requestId로 GET `/api/securities/:id/financial-refresh/:requestId`를 조회한다. QUEUED→PROCESSING→FINISHED, 기간별 SUCCESS/NO_DATA/FAILED 결과를 반환한다.
- 기존 collector_runs metadata.phase=MANUAL에 요청을 보존하고 기존 DART 작업자가 순차 처리한다. 재시작 후 미완료 요청 재처리, 동일 접수번호 중복 저장 방지. 별도 DB 마이그레이션 없음.
- 자동 수집과 DB 잠금·일일 3000회 한도·최소 5초 호출 간격·CFS 우선/OFS 대체·접수번호 검증·정정 판본 저장을 공유한다. 수동 요청은 야간 시간 제한 없이 처리한다.
- 동일 종목의 진행 중 요청은 409, 전체 미완료 요청은 최대 20건. 미설정 503, 대상 외 종목 422. 요청 상태 GET은 수집을 실행하지 않는다.
- 기업코드 연결이 없으면 공식 기업코드 목록을 갱신한 뒤 정확한 종목코드로 연결한다. 매핑 실패·공시 없음·API 한도·인증 오류를 구분한다.
- 실패/미공시는 기존 데이터를 보존한다. 화면은 진행 중 기존 데이터를 유지하고 완료 후 해당 종목 분석 캐시를 재조회한다.
- 기존 판본을 다시 확인한 시각(업데이트 완료 시각)과 DB 저장 데이터의 수집 시각을 구분한다.
- 현재 UI에는 갱신 범위 선택이 있고 기본값은 ANNUAL이다. 아래 확정 요구의 ‘선택 연도 전체 업데이트’ UI는 아직 미반영이다. 버튼과 상태 UI의 시각 교정 및 확장 요구는 후속 개발로 처리한다.

 종목별 저장 데이터를 조회하는 기존 재무제표를 재사용한다. 분기/전체 갱신 범위 선택은 취소하고 **전체 업데이트 한 버튼**만 제공한다. 전체는 현재 종목의 선택 사업연도 네 보고서를 뜻하며 모든 종목·모든 연도가 아니다.

## 21.3 조회와 갱신 범위

화면 진입, 연도/분기 변경, 재조회, 포커스 복귀는 저장 데이터 GET만 수행한다. GET에서 DART 호출을 발생시키지 않는다. 수동 버튼 클릭만 외부 공시 확인 작업을 시작한다. 버튼 옆/아래에 종목·사업연도 및 네 보고서를 상시 표시하므로 범위 선택이나 별도 확인 팝업은 두지 않는다.

| 화면 기간 | 대응 수집 보고서 | 현재 저장 periodType |
|---|---|---|
| 1분기 | 1분기보고서 | Q1 |
| 2분기 | 반기보고서 | Q2 |
| 3분기 | 3분기보고서 | Q3 |
| 연간 | 사업보고서 | ANNUAL |
| 4분기* | 독립 보고서 없음: 사업보고서와 3분기 누적 차이 | Q4, 파생 |

4분기는 신규 수집 보고서로 요청하지 않는다. 연결/별도가 동일한 누적 자료끼리 파생하고 원천 미수집은 —로 표시한다. 현재 backend `securities.ts`의 연간−3분기 누적 로직을 재사용한다. 항목별 누적/단일분기와 재무상태표 시점값 의미를 유지한다.

## 21.4 최신 확인과 데이터 보존

버튼은 네 보고서를 확인하되 이미 최신이면 재무 본문 수집·UPSERT를 생략한다. 최근 수집시각만으로 최신을 단정하지 않는다. 현재 주가는 판단 입력이 아니다.

서버가 최신 유효 공시(정정·철회 포함), 저장 접수번호/버전, 사업연도·보고서·연결/별도 및 정상 저장 여부를 비교한다. 동일 공시라도 직전 수집 실패/불완전이면 재수집 대상이다. 공시 확인 실패는 UP_TO_DATE가 아니다. 확인을 위한 DART 조회 자체는 필요할 수 있으므로 호출 0회를 보장하지 않는다. 비교·정정 처리의 실제 지원은 개발 확인 항목이다.

보고서별 성공 수집과 유효성 검증 뒤 해당 보고서만 원자적으로 반영한다. 실패/공시 없음/미공개를 기존 값 삭제 또는 0으로 바꾸지 않는다. 정정 공시 정상 수집 후에만 대체한다. 수동 입력 우선 정책(`MANUAL_WITH_DART_FALLBACK`)을 유지하고 사용자가 입력한 자료를 강제로 덮어쓰지 않는다. 원천 수집 성공과 화면 수동값 유지가 다르면 출처/안내로 설명한다.

## 21.5 상태와 문구

| 상태 | 안내와 행동 |
|---|---|
| 기본 | 최종 수집 시각과 선택 범위; 전체 업데이트 |
| 진행 | 보고서 확인 중 · 완료/전체(4); 기존 데이터·위치 유지, 버튼 비활성 |
| 성공 | 전체 업데이트 완료 · 갱신 N · 최신 N |
| 이미 최신 | 이미 최신입니다. · 4개 보고서 변경 없음 |
| 일부 성공 | 갱신/최신/공시 없음/실패 개수; 결과 상세와 재시도 |
| 공시 없음 | 해당 연도의 공시가 없습니다.; 기존 데이터 유지 |
| 인증 오류 | DART 인증을 확인해 주세요.; 인증 수정 후 재시도 |
| 호출 한도 | 호출 한도 초과; 서버 제공 재시도 가능 시각 표시 |
| 일시 장애 | 일시적으로 업데이트할 수 없습니다.; 재시도 |
| 미수집 | 저장된 재무 데이터가 없습니다.; 전체 업데이트 진입 |
| 저장 데이터 조회 실패 | 저장 데이터 조회 실패; 저장 데이터 GET 재시도, DART 요청 없음 |

공시 없음은 정상적으로 조회하여 확인한 결과에만 사용한다. 업데이트 오류와 저장 데이터 조회 오류를 분리한다. 갱신 0/최신4는 이미 최신, 일부 보고서 정상이고 나머지 공시 없음/실패이면 일부 결과로 표시한다. 네 보고서 모두 정상 조회·공시 없음일 때만 연도 전체 공시 없음이다. 전체 작업 실패는 해당 오류를 표시한다. 진행률 API가 없으면 숫자 진행률을 만들어내지 않고 ‘보고서 확인 중…’으로 표시한다.

‘저장 데이터 최종 수집’은 실제 정상 저장시각, ‘이번 확인’은 이번 작업 종료시각이다. 최신/오류/공시 없음일 때 마지막 수집시각을 이번 시각으로 덮어쓰지 않는다. 보고서별 수집시각이 다르면 현재 표시 자료의 기준과 결과 상세의 개별 시각을 제공한다. 시간대 Asia/Seoul.

## 21.6 요청·응답 개발 계약

기존 API 경로와 필드는 21.1의 구현 계약을 재사용한다. 화면 버튼의 POST 요청은 `{ fiscalYear, period: 'ALL' }`로 고정하며 조회 분기를 수집 범위에 사용하지 않는다. 기존 202 응답의 requestId와 상태 GET을 사용한다. 서버의 기간별 API 지원은 제거하지 않는다.

이하 항목은 디자인 요구를 지원하기 위한 후속 확장 요구이며 현재 응답에 존재한다고 가정하지 않는다: 보고서별 UPDATED/UP_TO_DATE 구분, receiptNo, collectedAt/checkedAt, completedCount/totalCount, retryAfter 및 요청 중복 식별자. 기존 SUCCESS/NO_DATA/FAILED와 QUEUED/PROCESSING/FINISHED의 매핑을 개발 담당이 검증·명세한 뒤 확장한다. SUCCESS만으로 ‘새로 갱신’과 ‘이미 최신’을 임의 구분하지 않는다.
인증키·원천 요청 URL의 민감정보는 브라우저에 보내지 않는다.

React에서는 저장 조회 useQuery와 업데이트 useMutation을 분리한다. 요청 시작 때 종목·연도를 고정하고 서버도 같은 키로 중복 요청을 합치거나 거절한다. 진행 중 버튼 및 기간 변경을 잠그고 본문 스크롤은 허용한다. 화면 이탈이 서버 작업 취소를 의미하지 않는다. 돌아올 때 작업 상태를 재조회하고 이탈 전 위치를 복원한다.

성공한 보고서만 관련 저장 조회 캐시를 무효화한다. 종목·연도 키가 달라진 이전 작업 결과를 현재 화면에 덮어쓰지 않는다. 새 자료 적용에도 조회 연도·분기·본문 scrollTop을 유지한다. 기존 자료가 있는 refresh는 전체 Skeleton으로 바꾸지 않는다. 최초 조회 로딩도 재무 영역 안에서만 표시한다.

재시도 버튼도 선택 연도 전체 확인 계약을 사용한다. 이미 성공한 보고서는 최신 비교로 생략한다. 인증 오류는 설정 수정 전 자동 반복하지 않고, 한도 초과는 retryAfter 이전에 요청을 반복하지 않는다. 일시 장애는 사용자가 재시도한다. 네트워크 타임아웃 때 requestId로 확인하여 동일 작업을 다시 생성하지 않는다.

## 21.7 UI·검증·인계

Inter 및 A0000~A0003 토큰·기존 하단 아이콘을 재사용한다. 카드8px, 헤더/하단44px, 커버·태블릿 좌우8px 외곽 여백·2열 간격8px. 커버는 세로, 태블릿은 재무 항목2열. 본문만 스크롤하고 끝에80px. 금액은 기존 단위 규칙(만원, 억도 만원)과 천 단위 구분을 유지한다. 긴 종목명은 줄바꿈하며 금액은 오른쪽 정렬한다. 버튼/기간 선택 터치 영역44px. 진행/오류는 문구도 함께 표시하여 색에만 의존하지 않는다.

디자인 기준: 370×465·400×640·725×396·816×616. 기본/진행/결과와 최하단의 겹침·잘림·수평 넘침을 확인한다. Figma 예시 수치는 실제 공시 데이터가 아니다.

개발 검증:
1. 진입·연도/분기 변경의 외부 DART 요청0건.
2. 버튼 한 번에 선택 종목·사업연도4보고서만 확인, Q4 요청 없음.
3. 동일/정정/미완료 공시 최신 비교와 재수집 생략.
4. 일부 성공·공시 없음·인증·한도·장애 각각 기존 DB값과 화면 유지.
5. 중복 클릭·타임아웃·이탈 복귀·종목 전환에서 중복 작업/응답 혼입 없음.
6. 수집시각과 확인시각 분리, 진행 API 없는 경우 허위진행률 없음.
7. 수동 입력 우선·연결/별도·Q4 파생 기준 유지.
8. 구현 후 네 크기 캡처를 Figma와 대조.

### 거래종목 화면과 진입

- 거래종목 카드/행의 최종 구성은 보류한다. 종목명·코드, 마지막 매도일, 누적 실현손익·거래 건수는 검토 제안이며 확정 표시 항목이 아니다. 누적 실현손익은 해당 계좌의 유효한 매도 전체를 연결 Lot 단가로 계산하며 평균단가를 원가로 사용하지 않는다. 건수는 매도 거래 건수임을 명시한다.

### 부분매도와 매도 수정·삭제

- 부분매도한 Lot은 잔여수량으로 보유현황에 남는다. 잔여수량=0인 Lot만 보유현황에서 제외하며 원본 매수와 연결 매도 기록은 유지한다.
- 매수·매도 한 묶음인 **거래내역 카드의 수정·삭제 아이콘은 항상 해당 매도 거래에 연결**한다. 분할매도 N건은 각 매도별 카드로 표시하며 원가에는 그 매도수량에 해당하는 매수단가를 사용한다.
- 매도 삭제 확인은 대상 종목·매도일·매도수량·연결 매수 Lot·복원 후 잔여수량을 안내한다. 예: “이 매도 20주를 삭제하면 연결된 매수의 잔여수량이 50주에서 70주로 복원됩니다. 예수금은 자동으로 변경되지 않습니다.”
- 삭제 대상은 매도 1건이며 연결된 매수 기록은 삭제하지 않는다. 삭제한 매도수량만큼 해당 Lot 잔여수량이 증가한다. 70주 매수→20주 매도→잔여50주에서 매도 삭제 시 잔여70주다.
- 수량을 별도 덧셈 저장하여 이중 복원하지 않는다. 잔여수량=매수수량−유효 연결 매도수량 합계로 재산출한다. 반복 삭제/중복 요청으로 수량이 늘어나지 않도록 한다.

- 매수 자체 수정·삭제는 별도 매수 Lot 경로를 유지하며 기존 연결 매도 보호 규칙을 적용한다. 거래내역 카드 아이콘을 매수 편집·삭제로 연결하지 않는다.

투자손익 종목 상세의 좌우 이전/다음 종목명은 한 줄 말줄임으로 표시한다. 폭이 부족한 경우 최대 5글자와 …로 축약하고 중앙 종목명을 침범하지 않는다. 전체 이름은 접근성 이름으로 제공한다.

### 5. 투자손익 종목 상세 스와이프
본문 좌우 스와이프로 종목을 전환한다. 왼쪽은 다음, 오른쪽은 이전이며 진입 목록의 현재 정렬 순서와 좌우 버튼 순서를 따른다. 처음·마지막 종목에서는 멈춘다. 인접 종목을 선조회하되 다른 종목 데이터를 새 제목 아래 표시하지 않는다. 세로 스크롤·버튼·입력·차트·뒤로가기 제스처와 충돌하지 않게 한다.

### 6. 연도별 투자손익의 투자금 기준
지난 연도는 해당 연말 스냅샷의 투자금을, 진행 중인 올해는 해당 연도의 가장 마지막 유효 스냅샷 투자금을 사용한다. 올해를 무조건 어제 날짜로 고정하지 않는다. 기준일을 함께 확인할 수 있게 한다. 누적 매수금·실시간 평가금액으로 대체하지 않는다. 연말 스냅샷 누락 시 대체일 정책은 별도 확정 전까지 미수집으로 구분하며 임의 날짜로 조용히 치환하지 않는다.

### 7. 종목별 손익 정렬·총계 위치
연도 상세 ‘종목별 손익’과 투자손익 종목별 탭 ‘종목별 누적 수익’은 **부호를 포함한 손익액 내림차순**을 기본으로 한다. 절댓값·수익률 정렬이 아니다. 제목 오른쪽에 내림/오름 토글을 두며 재정렬 시 종목·수익률·금액을 함께 이동한다. ‘총 N개’는 제목 옆으로 옮긴다. 선택 종목 상세의 이웃 이동도 현재 목록 정렬을 따른다.

### 8. 월별 매매·배당 텍스트 색상
투자손익 종목 상세 ‘월별 손익·배당 내역’의 유형 텍스트는 매매=해당 행 손익색(이익 적색/손실 청색/0 중립), 배당=노란색으로 표시한다. 금액 색상은 기존 정책을 유지한다.

### 9. 홈 로딩 성능 개선
첫 진입과 재진입의 API 응답 시간·중복 요청·직렬 의존·렌더링 대기를 측정하고 병목을 튜닝한다. 캐시가 있으면 즉시 표시하고 필요한 갱신은 뒤에서 수행한다. 캐시가 없는 첫 진입은 준비된 카드부터 표시하고 미완료 카드에만 로딩 상태를 둔다. 전체 API가 끝날 때까지 화면 전체를 막지 않는다. 임시 0원이나 다른 계좌의 자료를 표시하지 않는다. 동일 조건의 수정 전후 첫 유효 카드 표시 시간·전체 로딩 시간·요청 수를 보고한다.

### 10. 매매일지 거래현황 스와이프 개선
날짜·요약·거래 목록·빈 상태를 포함한 거래현황 카드 전체에서 날짜 스와이프가 동작하도록 영역을 넓힌다. 거리·속도·가로/세로 방향 판정을 조정하여 짧은 의도적 가로 움직임도 자연스럽게 인식한다. 세로 스크롤을 우선 보호하고 버튼 클릭을 오인하지 않으며 한 제스처당 한 날짜만 전환한다. 왼쪽 다음 날/오른쪽 이전 날, 날짜 버튼과 동일한 경계 규칙을 사용한다. 인접 날짜 선조회와 요청 중복 방지를 적용한다. 거래 없는 날짜도 동일하게 동작한다.

### 11. 일별손익 스와이프 추가
날짜 선택부·전체손익·실현손익·거래현황 등 본문 전체에서 좌우 스와이프로 날짜를 전환한다. 방향·감도·축 판정은 거래현황과 공통으로 관리한다. 세로 스크롤·행 상세 진입·버튼 동작을 보존한다. 헤더·하단 메뉴는 고정하고 인접 날짜 캐시를 재사용한다.

### 12. 투자금 화면의 누적 매매손익 표시
현재 평가금액 카드 아래 ‘투자금 대비 차액’을 **선택 연도의 누적 매매거래 실현손익**으로 변경한다. 올해는 ‘올해 누적 매매손익’, 과거는 ‘YYYY년 누적 매매손익’으로 표시한다.
- 금액 = 해당 연도 매도 거래의 실현손익 합계. 배당·미실현 평가손익 제외.
- 비율 = 해당 연도 누적 매매손익 ÷ 해당 화면의 누적투자금 × 100. 분모 0은 —.
- 색상은 손익 금액의 양/음/0을 따른다. 상단 평가금액의 값은 변경하지 않는다.
- 분기 선택은 기존대로 차트·투자내역에 적용하며 이 요약은 연간 값이다.
- 사용자 확인용 예시: 평가금액 81,845,732원 / 누적투자금 107,317,732원 / 올해 누적 매매손익 +39,720,500원 / +37.0%. 화면 예시이며 운영 API 검증값으로 간주하거나 코드에 고정하지 않는다.

### 개발 순서·검증·인계
손익·스냅샷 기준(2/6/12)을 먼저 구현하고 정렬·표시(1/4/7/8), 캐시·로딩(3/9), 공통 스와이프(5/10/11)를 진행한다. 소스 변경은 별도 브랜치와 PR로 제출하며 v0.1 복귀 기준을 유지한다. 이번 개선으로 기존 매수·매도·배당·예수금 원본이나 과거 스냅샷을 임의 수정하지 않는다.

**웹서버 담당:** 필요한 API·집계·캐시 계약 변경 및 API 검증만 수행한다. 브라우저 검증은 요구하지 않는다. 정상 응답뿐 아니라 집계 대조·빈 결과·실패·계좌/연도/종목 경계·배당 제외·분모 0을 검증하고 응답 예시와 결과를 남긴다.

**프런트 담당:** 화면 연결·캐시 무효화·정렬·색상·스와이프·홈 성능을 구현하고 브라우저/실기기 검증을 맡는다. 작은 화면·태블릿, 가로/세로/대각선 제스처, 빈 날짜, 빠른 전환, 뒤로가기·스크롤 복원, 포커스 복귀 시 불필요한 요청 제거를 확인한다.

완료 보고에는 변경 파일·PR·API 검증 결과·프런트 검증 결과·홈 전후 측정치·미해결 사항을 구분한다. 문서/Figma 현행화는 구현·배포 완료 선언이 아니다.
