기준 main `70d04c1fba806d0e5cc7b1bc26cc69e104785593`와 실제 분석 이미지 `f16cd801236d5247358ee45c4bc7341de90dab1e`의 수집 로직을 대조했다. 화면 개선 PR #192/#193은 유지한다. PR #137은 참조용이며 병합하지 않는다.

[원인 분석](https://github.com/byungho-cho/roxstock/blob/docs/collector-feedback-20261008-152215/docs/collector-feedback/20261012-073828-KST-dart-receipt-mismatch-analysis.md)의 대표 공시 식별값을 격리 fixture에 사용했다. 이 fixture에 재무 금액이나 인증정보는 없다. 검사 금액은 합성값이며 실제 재무 수치의 동일성을 주장하지 않는다.

DART [공시검색](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019001)은 원/정정 목록과 기업·공시명을 제공한다. [전체 재무제표](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS003&apiId=2019020)는 사업연도·보고서·연결/별도를 입력받으며 임의로 선택한 접수번호를 입력받지 않는다. 따라서 최신 목록 번호와 재무 API 번호의 절대 동일성 대신 반환 번호의 역검증을 사용한다.

## 기간 계약

- 작업 `fiscalYear`와 API `bsns_year`는 별도 메타데이터로 기록한다. 현재 둘은 동일하며 요청 연도에 일괄 ±1년 보정을 하지 않는다.
- 연간은 해당 연도의 실제 사업보고서 제목 기간에서 결산일을 구한다. 인접 연도 사업보고서들의 결산월을 함께 보존한다.
- 분기는 해당 기업의 결산월로 각 보고서의 실제 월을 구하고, API 요청 연도 안의 공시와 연결한다. Q1/Q2 이후에 Q3를 무조건 다음 연도로 이월하지 않는다. GRT 실제 응답 대조는 2024 연간 2024.06 / Q1 2024.09 / 반기 2024.12 / Q3 2024.03이다. 작업/API 사업연도가 하나의 12개월 회계 주기를 의미한다고 가정하지 않는다. 이 후보 계약에 맞는 실제 API 반환 공시가 있어야만 저장한다. 다른 기업의 반환 기간이 다르면 차단되며 GRT 결과를 근거로 강제로 허용하지 않는다.
- 인접 연도에 결산월이 달라지거나 같은 연도 연간 기간이 복수이면 분기는 검토 대상이다. 과거 연간 근거가 없으면 12월을 기본값으로 추정하지 않는다. 미확인 기간은 재무 API 호출 전에 거절한다.
- `periodEndDate`는 검증된 출처 공시의 실제 제목 월 말일이다. 12/3/6/9월 고정 함수는 수집 경로에서 제거했다. 공시명에 월만 있으므로 변경기의 짧은 회계기간 시작일/길이는 추정하지 않는다.

## 원공시·정정·출처

`DartReport.selection`은 동일 기업·실제 기간의 모든 원/정정 후보, 정정 유형, 결산월 근거를 보존한다. v1 캐시는 사용하지 않고 정상 요청 한도·간격 아래서 v2를 생성한다. 불일치 때 캐시를 삭제해 반복 목록 호출을 유도하던 동작은 제거했다.

`validateDartFiling`은 기업·API 연도·보고서·단일 접수번호·통화·공시 기간을 검증한다. 응답에 잘못된 식별 행이 하나라도 있으면 공급자에서 거절하며 해당 행을 버리고 CFS→OFS로 우회하지 않는다.

반환 번호가 선택 번호와 다르면 동일 기업/기간/제목 그룹에 단일 원공시와 공개 정정 표기가 있고, 실제 API 출처 이후의 공시가 첨부정정/첨부추가만인 경우에만 허용한다. 최신 기재정정이 있는데 API가 이전 자료를 주면 접수번호 지정 원문 검증 필요 상태로 남긴다. 철회·모호한 원공시·알 수 없는 정정·혼합 접수번호는 차단한다. 재무 수치가 동일하다고 가정하지 않는다.

저장 `receiptNo`, `reportName`, `receiptDate`는 API가 실제 반환한 출처의 값이다. 별도 nullable JSON `source_validation`에 선택/반환 번호, 정정 관계, 실제 기간, 작업/API 연도, CFS/OFS, 통화·단위를 기록한다. 기존 KRW 전용 금액/계산 경로에 CNY/USD를 원화처럼 저장하지 않도록 비KRW는 `NON_KRW_STORAGE_UNSUPPORTED` 검토 사유로 차단한다. 환산/외화 지원은 이번 범위 밖이다.

자동 과거/현재 수집, 기존 수동 갱신, 독립 수동 작업, 수동 연간 보완에 공통 검증을 적용했다. 저장값 보완은 기존 저장 접수번호의 동일 출처만 허용하며 다른 재무 응답을 기존 출처로 이름 바꾸지 않는다. DART와 독립 PER/PBR의 병렬/분리 동작은 유지한다.

## 보존과 진단

기존 SUCCESS/PENDING/NO_FILING/FAILED 작업을 삭제/일괄 초기화하지 않는다. 자료 기간·기업·연결/별도·작업 연도가 기존 receipt 행과 충돌하면 `STORED_FILING_CONFLICT`로 중단하고 기존 행을 보존한다. 동일 receipt는 하나만 저장하며 기존 금액은 자동 중복 저장 시 덮어쓰지 않는다. 경쟁 insert도 기존 행을 같은 식별 검증으로 다시 확인한다. 검증된 선택 번호는 출처 행의 별도 alias로 인식해 현재 연도 경로에서 첨부정정을 매 주기 반복 요청하지 않는다. 출처 번호는 바꾸지 않으며 이전 선택 번호도 메타데이터에 보존한다.

작업·실행 항목의 nullable `diagnostics`에 공개 식별자·원래 코드·검증 하위 사유·단계·시도·runId를 기록한다. REVIEW_REQUIRED는 원래 오류와 하위 사유를 잃지 않는다. 근거 부족·원문 검증 필요·외화(`DART_SOURCE_REVIEW`)·기존 저장 충돌은 첫 시도부터 검토 대기로 두며 자동 반복 재요청하지 않는다. 실제 접수번호 불일치의 기존 3회 정책과 통신 재시도 정책은 유지한다. 공시 제목 기간을 파싱할 수 없을 때도 NO_FILING으로 단정하지 않는다. 로그·필터는 allowlist만 직렬화하고 인증키·URL·헤더·SQL·원문 예외·cause를 출력하지 않는다.

수집 시간/휴일 규칙/호출 한도/응답 후 지연/CFS→OFS 순서/스케줄/RAM/DB pool/프로세스 종료 처리는 변경하지 않는다. PROCESS_RESTARTED로 과거 종료 시각이나 원인을 단정하지 않는다.

## 읽기 전용 목록과 제한 검증

```sh
# SELECT-only: API 호출·캐시 변경·작업 변경 없음
node backend/dist/scripts/verify-dart-receipts.js audit
```

출력은 실패 작업 원인 목록, 대표 후보, 저장 공시 제목 대비 기간 불일치 목록, 상태/사용량/실행 기준선, receipt 중복 수다. 과거 하위 원인 증거가 없는 실패는 `LEGACY_EVIDENCE_INCOMPLETE`로 보존한다. 번호가 없는 147건을 두 원인으로 임의 분류하지 않는다.

배포 후 전용 workflow는 먼저 위 dry-run을 기록한다. 대표 모드는 v2당 한 번만 실행하며 앱 일일 잔여량을 확인한 뒤 최대 12회, 기존 최소 지연 이상으로 제한한다. GRT 2024 연간/Q1/Q2/Q3, CJ대한통운·삼성전자 2024 연간을 조회한다. 실제 반환으로 검증된 GRT 2024 반기·CJ 2024 연간 FAILED 작업 두 개만 저장/성공 전환 후보다. 삼성 SUCCESS 및 다른 작업은 검증만 하며 갱신하지 않는다. 후보는 검증 및 기존 자료 충돌이 없어야만 transaction 안에서 저장·작업 전환한다. 과거 오류/시도는 append-only 실행 항목에 먼저 보존한다. 검증이 차단된 대표 후보는 재무자료를 쓰지 않고 원래 오류 이벤트를 보존한 뒤 이번 시도의 안전한 하위 사유/시도만 기록한다. 근거 부족/단위/저장 충돌은 검토 대기로 남긴다. 나머지 작업 재개/초기화는 하지 않는다.

사용량은 앱 counter에 원자적으로 예약한다. 같은 키의 외부 서비스 사용량은 미확인으로 기록한다. 인증/한도/통신 실패는 안전한 코드로 중단/기록하며 대표 검사 재실행으로 무한 요청하지 않는다.

## 기존 기간 오기재의 별도 복구안

`periodInventory`는 종목·receipt·작업 연도·보고서·저장 일자·제목의 실제 일자로 별도 목록을 만든다. 현재는 읽기만 한다. 일괄 복구 전에 다음을 별도 승인된 작업으로 수행해야 한다.

1. 목록의 각 공시·기업·원/정정·API 기간 및 원문을 확인한다. 제목과 불일치만으로 자동 수정하지 않는다.
2. server-local dump와 대상 행 원본/메타데이터/연결 가치지표의 제한 export를 보관한다.
3. 검증된 대상별 before/after 계획과 역복구 SQL을 작성한다. 접수번호·사업연도·연결/별도 unique 관계가 변하면 단순 날짜 UPDATE로 처리하지 않는다.
4. 격리 DB에서 기간/가치지표/단위 재계산을 대조한 뒤 제한 transaction으로 반영한다. 미검증/이미 정상 자료는 그대로 둔다.
5. 역복구는 보존한 기존 일자·금액·지표로 대상 receipt만 되돌린다. 전체 DB restore/전량 재수집은 기본 복구안이 아니다.

배포는 기존 SHA 고정·백업·헬스 체크 경로를 사용한다. nullable 컬럼 추가 외 기존 자료를 수정하는 migration은 없다. 구 이미지 rollback은 새 nullable 컬럼을 무시하며 기존 데이터 삭제가 필요하지 않다.
