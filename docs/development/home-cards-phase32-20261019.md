# 32차 홈 카드 — 1.1.17

최근 매수는 매수 Lot의 수량에서 해당 Lot의 매도 수량 합계를 뺀 잔여량이 양수인 경우만 표시한다. 직접 API는 DB에서 잔여 Lot을 먼저 선별한 뒤 매수일·ID 내림차순의 최신 5건과 전체 건수를 조회한다. 홈 통합 API는 이미 읽은 포트폴리오와 공통 잔여 Lot 선별·평가 함수를 재사용한다. 월별 더보기에서도 같은 정책을 적용한다.

부분 매도 Lot의 수량·매입금액·평가금액·손익은 잔여량 기준이다. DTO의 원 매수 수량과 거래 이력 API는 보존한다. 더보기 응답은 확장 구간의 최신 스냅샷으로 교체하여 조회 중 발생한 전량·부분 매도를 반영한다.

목표가 도래가 있으면 목표가 카드를 보유종목 바로 위로 이동한다. 0건이면 기존 마지막 위치를 유지한다. 커버에서는 DOM 순서, 태블릿에서는 동일 DOM 순서와 기존 두 열의 그리드를 함께 변경한다. 컴포넌트 key는 유지한다. 같은 계좌 재조회와 목표가 보조 조회 실패에는 마지막 정상 결과·위치를 유지하고, 계좌가 바뀌면 이전 계좌 결과를 즉시 제외한다. 정상 0건 응답은 이전 양수 결과를 대체한다. 기존 계산 조건, 색상, 간격, 버튼과 이동 경로는 재사용한다.

## 검증

- 백엔드 단위 테스트: 전량/부분/미매도, 동일 종목의 서로 다른 Lot, 잔여 소수 수량의 비용·평가·손익, 시세 미수집을 검증한다.
- 격리 MariaDB API 통합 테스트: 최신 5개가 전량 매도된 경우에도 보유 Lot 5건을 반환하고 전체 7건·확장 7건이 일치하는지, 추가 전량 매도 후 캐시 갱신과 거래 이력 보존을 검증한다.
- Playwright: 370×465와 725×396에서 0/1/여러 목표가, 0↔1 전환, 지연·실패 재조회, 계좌 전환, 카드 중복·순서·간격·가로 넘침, 스크롤, 더보기 중 매도 반영, 초기화와 클릭 경로를 검증한다. 화면 증거는 Frontend Check 아티팩트에 저장한다.
- 실제 실행 결과는 PR 검사 및 최종 보고를 기준으로 한다. 운영 실계좌의 거래 변경은 검증에 사용하지 않는다.

## 운영 반영과 복구

DB 스키마·마이그레이션 변경은 없다. 거래·과거 매매·현금 원장은 읽기만 한다. 기존 Production Deploy의 운영 DB 백업과 검증 절차를 유지한다. backend와 frontend를 배포하고 collector 및 네이티브/APK는 배포하지 않는다.

복구 시 직전 backend/frontend 이미지를 기존 배포 절차로 복원한다. 스키마가 동일하므로 역마이그레이션이나 거래 데이터 복원은 필요하지 않다. 이전 최근 매수 표시 정책으로 돌아갈 수 있다.
