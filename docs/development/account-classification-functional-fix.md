# 종목 분류·거래 정합성 교정 (2026-10-03)

기준: main 기본설계서 v0.7 22·23장, PR #67. 시각 디자인 변경은 다음 인계 후 진행한다.

## 운영 API에서 재현한 문제

- 수동 HOLDING 등록이 INVALID_LIST_TYPE 400으로 거부되었다.
- accountId가 다른 관심종목 조회가 같은 전역 등록을 반환했다. 기존 테이블은 계좌 키가 없었다.
- 이미 등록된 관심·추천의 검색 결과 버튼이 비활성화되어 분류 변경을 막았다.
- 거래 저장이 전역 분류를 바꾸어 다른 계좌와 원래 수동 분류에 영향을 주었다.
- 부분 매도 Lot 조회의 평가손익이 원래 매수수량 기준이었다.

## 변경 및 데이터 보존

- AccountWatchlistItem을 계좌+종목 고유 키로 추가한다. 직접 보유 분류는 등록만 하며 매수·자산을 생성하지 않는다.
- 매수 이력과 연결 매도의 잔여수량으로 HOLDING/TRADED를 계좌별 계산한다. 모든 유효 거래가 삭제되면 원래 수동 분류로 돌아간다. 수동 분류가 없는 종목에는 관심 분류를 임의 생성하지 않는다.
- 거래 이력이 있는 보유종목의 관심·추천 이동/삭제와 거래종목의 직접 분류 변경을 서버에서 제한하고 사유를 반환한다.
- 이전 전역 watchlist_items는 원본 그대로 보존한다. 소유 계좌 정보가 없는 관심·추천은 기본 활성 계좌(없으면 첫 활성 계좌)에만 이관한다. 전역 HOLDING은 해당 매수의 계좌별로 이관한다. 거래·예수금·스냅샷은 이관으로 변경하지 않는다.
- 거래 등록 요청 ID와 결과를 같은 DB 트랜잭션으로 기록한다. 같은 계좌/ID/입력의 재요청은 기존 결과를 반환한다. 다른 입력으로 ID를 재사용하면 제한한다. 구버전 클라이언트는 요청 ID 없이 기존 검증 경로를 사용하지만 현재 화면은 요청 ID를 항상 전송한다.
- 수정·삭제는 현재 연결 매도 합계에서 잔여수량을 재계산한다. 원래 Lot 원가를 유지하고 예수금/현금 이력/과거 스냅샷을 자동 수정하지 않는다.
- 수집 대상은 활성 계좌의 등록과 실제 보유를 합쳐 중복 제거한다. 계좌별 수동 보유도 시세 수집은 가능하지만 자산 집계에는 거래 수량만 반영한다.
- 목록/상세/자산/현금 관련 쿼리를 저장 후 갱신한다. 계좌별 쿼리 키와 폼 재생성으로 이전 계좌 응답이 현재 폼이나 이동을 바꾸지 않는다. 실패 시 입력을 유지한다.

## 검사

- 기존 백엔드 테스트, TypeScript와 빌드.
- stockMath의 Lot 원가·평가·평균단가 교체 계산.
- 실제 MariaDB + 실제 Fastify/Prisma API: 구 데이터 이관, 두 계좌의 독립 분류, 수동 보유의 자산 미생성, 분류 제한, 거래 요청 재실행/동시 요청, 부분/전량 매도, 수정 수량 제한, 매도 삭제, 현금/스냅샷 보존, 원래 분류 복귀, 새 API 연결 후 분류 유지.
- 370×465/725×396의 분류 저장·실패·새로고침·계좌 전환 기능 검사. Figma 비교/전체 회귀 QA는 미실시.

## QA 담당 인계 / 후속 디자인 범위

- 이전 QA의 C2100 조건 수정 기대값(수정 버튼/별도 Dialog)은 최신 행 클릭/인라인 편집과 달라 검사 명세를 갱신해야 한다.
- 더보기 이동 시간 초과는 전체 25초 제한과 제품 동작을 분리해 재현해야 한다.
- 구 자산구성 내부 스크롤 기대값, CSS mask 아이콘 탐색, tablet 프로젝트 이름에 따른 잘못된 분기는 QA 검사 수정 대상이다.
- 현대차 등락률의 정상 반올림 차이를 계산 오류로 분류하지 않는다.
- 종목 검색의 시장명, 버튼 크기, 공통 여백·행 간격·아이콘 및 화면 Figma 대조는 디자인 교정 인계 후 작업한다. 이번 변경에서는 시각 교정을 하지 않았다.
