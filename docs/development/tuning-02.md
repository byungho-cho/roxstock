# 튜닝 2차: 나머지 화면 공통 조회

홈·종목목록의 전용 bootstrap은 유지하고, 예수금·평가자산·자산분석·매매일지·투자내역/손익·종목 상세·복리계획·재무제표·가치분석·수집 모니터링·설정의 조회에 공통 전송 계층을 적용한다.

## 요청 병합
- 같은 microtask 전의 독립적인 GET을 `/api/pages/read` POST 한 번에 최대 8개로 묶는다. 같은 경로는 중복 제거한다. API의 data/summary/meta 구조 및 개별 오류 상태는 그대로 전달한다.
- 서버는 읽기 전용 경로 allowlist만 허용하며 Fastify의 in-process injection으로 기존 검증/오류 처리를 재사용한다. 내부 HTTP 연결은 만들지 않는다.
- 계좌 목록을 먼저 알아야 하는 최초 진입, 다음 페이지 커서를 알아야 하는 조회, 뒤늦게 마운트되는 영역은 별도의 요청 묶음이다. 모든 화면이 무조건 한 요청이라고 해석하지 않는다.
- 각 묶음은 병렬 처리하되 가장 느린 조회가 완료돼야 반환된다. 진행 중 작업 상태/실시간 스트림 및 신설 미등록 경로는 원래 직접 요청을 유지한다.
- 취소된 호출은 결과를 전달하지 않으며, 묶음 내 다른 호출은 계속 처리한다. 전부 취소되면 전송도 취소한다. 404에서만 구버전 API로 전환하고, 서버/네트워크 오류는 감추지 않는다.

## 서버 캐시와 중복 집계
- 계좌·조건·KST 날짜·호출자 인증/쿠키 범위를 캐시 키에 포함한다. 일반 조회 10초/96개, 모니터링 2초/32개이며 512 KiB 초과 및 오류 응답은 보존하지 않는다.
- 동일한 진행 중 조회는 Promise를 공유한다. 쓰기 응답 및 실시간 주가 반영 시 캐시를 비운다. 무효화 전 시작한 조회가 새 캐시를 덮어쓰지 못한다.
- 별도 수집기의 직접 DB 쓰기는 TTL로 반영된다. 서버 재시작 직후/캐시 미적중은 원래 DB 읽기가 필요하다.
- AsyncLocalStorage로 한 묶음 내 동일 계좌의 loadPortfolio 결과를 공유한다. 서로 다른 묶음/계좌는 공유하지 않으며 트랜잭션 전용 reader는 제외한다.
- HTTP 캐시는 private/no-store. 각 응답 항목의 cache 필드로 HIT/MISS/COALESCED 확인 가능.

## 목록과 호환성
- 기존 infinite query/선조회 후 붙이기를 유지한다. 종목 관리의 기존 행은 memo와 안정된 선택 callback으로 더보기 시 불필요한 렌더를 줄인다.
- 26차 UI/계산 기준 변경과 분리한다. DB migration 없음. 백엔드 → 프론트 배포이며 롤백 중 404 호환 제공.
- 1차 홈/종목 API 캐시는 조회용 POST 때문에 무효화되지 않는다. 실제 저장 요청은 계속 무효화한다.

## 검증
- 단위/서버 검사: 병합, 중복 제거, 호출별 취소/오류, 404 호환, 허용 경로, 계좌/조건/호출자 격리, 쓰기·시세 무효화, 요청 범위 집계 공유.
- Tuning 02 Check: 커버 370×465 / 펼침 725×396에서 화면별 묶음 응답, 계좌 전환, 부분 실패 및 종목 관리 더보기 DOM 유지.
- 기존 화면 회귀 fixture는 404 호환 경로를 유지하며 튜닝 전용 fixture가 묶음 경로를 검증한다.
- 실제 휴대폰 첫 진입 1초 달성 여부 및 운영 화면별 전후 성능 수치는 별도 실측 대상이다.
