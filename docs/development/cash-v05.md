# 예수금 v0.5 · 12차 개선 · 2026.10.08

수집 개선 PR #138~#140의 main `c7413c830793f7b40faaabbd27af302fb1387733` 및 Production Deploy #37747475130 성공을 확인한 뒤 별도 작업 브랜치에서 진행한다. 기준 Figma는 [커버 예수금 명세](https://www.figma.com/design/HFguP6QYb6xnO9FRsjYlc2?node-id=3674-2), [태블릿 예수금 명세](https://www.figma.com/design/HFguP6QYb6xnO9FRsjYlc2?node-id=3674-331)이며 FINAL 3674:3 / 3674:332와 대조했다. 이번 현재예수금 기준은 이전의 ‘내역 수정·삭제 시 계좌 현재 잔액은 변경하지 않는다’ 규칙을 대체한다. 다음 일반 개선은 13차, 수집 데이터 개선은 별도로 관리한다. 임시 소통 PR #137과 해당 브랜치는 병합하지 않는다.

## 현재예수금 기준

- 선택 계좌 전체 예수금 내역에서 `createdAt DESC, id DESC`로 조회한 최신 1건의 `balanceAfter`가 유일한 현재예수금 기준이다. 목록 기간·거래일자·화면 정렬·다른 계좌와 무관하다. 수정은 `createdAt`을 바꾸지 않는다.
- `Account.cashBalance` 컬럼은 호환 캐시다. 등록 및 최신 내역 수정·삭제 시 동기화하지만 조회·신규 거래 계산의 기준으로 읽지 않는다. 과거 내역 수정 시 캐시도 변경하지 않는다. 내역이 없거나 세후값이 누락됐으면 남아 있는 캐시를 사용하지 않는다.
- 계좌 목록/수정 응답, cash-overview, 홈 dashboard, holdings가 사용하는 공통 portfolio, 평가자산의 당일 계산점, 복리 현재자산 및 신규 일별 스냅샷의 현재예수금 기준을 통일한다. 과거 스냅샷은 당시 저장값을 그대로 유지한다.
- **내역 없음:** API 금액 `null`, 상태 `NO_TRANSACTIONS`, 화면 `—`와 입금 등록 안내. 첫 입금의 입력 금액 자체가 세후예수금이 된다. 첫 입금 계산에서만 0을 시작점으로 사용하며 조회값을 0으로 표시하지 않는다. 출금·배당·매수·매도는 기준이 없으면 `409 CASH_BALANCE_UNAVAILABLE`로 거절한다.
- **최신 세후값 누락:** API 금액 `null`, 상태 `BALANCE_MISSING`, 화면 `—`와 누락 안내. 이전 내역이나 별도 잔액을 대신 쓰지 않는다. 최신 내역에 명시적인 세후예수금을 입력해 정정할 수 있다. 현재 DB 스키마의 세후 컬럼은 NOT NULL이므로 누락 상태는 레거시/스키마 드리프트 응답을 방어하며 테스트 대역으로 검증한다.
- 기준금액이 없으면 총자산·관련 수익도 `null`로 유지한다. 신규 스냅샷은 `CURRENT_CASH_MISSING`을 기록하고 해당 계좌 저장을 건너뛴다. 조회 실패는 오류/재시도를 표시하고 다른 내역을 대신 편집하지 않는다.

## 카드와 공통 편집

- 현재예수금 카드 전체 및 편집 아이콘은 카드 조회 응답의 `recentTransactions[0]`을 공통 수정 화면으로 연다. 카드 표시 금액과 편집 대상이 같은 응답·내역을 사용한다. 목록 조회 기간 밖의 최신 내역도 편집할 수 있다.
- 기존 별도 현재 잔액 편집은 제거한다. 설정의 예수금 수정 진입은 예수금 내역 편집으로 연결한다. 이전 PATCH `/accounts/:id/cash-balance`는 `409 LATEST_CASH_EDIT_REQUIRED`를 반환한다.
- 모든 내역 유형을 편집할 수 있다. 입금·출금·배당 수정에도 명시적인 세후예수금 입력을 제공한다. 변경내역의 네 열(구분 / KST 날짜·시간 / 제세금 / 세후 잔액), 빨간 삭제 버튼, 최신 1건만 삭제 활성화, 커버 일반 입력 및 태블릿 중앙 팝업은 유지한다.
- 매수·매도 수정의 세전예수금은 `balanceAfter + feeTaxAmount`로 초기화하며 편집 가능하다. 세전 변경 시 세후·제세금을 빈 문자열로 초기화한다. 마지막 입력인 세후 또는 제세금에서 상대 항목을 Decimal 문자열 연산으로 계산한다. 음수 제세금을 임의로 0으로 보정하지 않는다.
- 저장 후 카드·목록·계좌·홈·평가자산·복리 등 portfolio 캐시를 무효화하여 갱신한다. 취소는 쓰기 요청을 보내지 않는다. 수정 중 계좌가 변경되면 저장을 거절한다.

## 등록·수정·삭제와 동시 변경

- 입출금·배당·매수·매도 신규 등록은 최신 내역의 세후예수금에서 계산한다. 과거 거래일자로 등록해도 신규 등록 순서대로 현재예수금에 반영한다.
- PATCH `/cash-transactions/:id`: 선택한 내역의 입력값만 수정한다. `balanceAfter`는 0 이상 Decimal 문자열, `feeTaxAmount`는 부호 있는 Decimal 문자열이다. 생략한 잔액은 유지한다. 최신 내역 수정은 변경된 세후예수금을 현재예수금으로 반영하며 `cashBalanceAdjusted:true`, 과거 내역은 `false`를 반환한다. 원본 BuyTrade/SellTrade/Lot, 이후 내역, 과거 스냅샷을 연쇄 수정하지 않는다.
- 카드 편집은 `accountId`와 `expectedLatestId`를 보낸다. 잠금 후 최신 내역이 달라졌으면 `409 LATEST_CASH_CHANGED`로 거절하고 다시 열도록 안내한다. 목록에서 과거 내역을 명시적으로 편집하는 것은 계속 허용한다.
- DELETE `/cash-transactions/:id?accountId`: API에서 선택 계좌를 검사하고 최신 1건만 삭제한다. 삭제 뒤 남은 최신 내역의 세후예수금을 사용하며, 마지막 내역 삭제는 `null/NO_TRANSACTIONS`가 된다. 역산하거나 다른 내역을 재계산하지 않는다.
- 등록·수정·삭제는 Serializable 트랜잭션 및 계좌 행 `SELECT ... FOR UPDATE` 잠금을 공통 사용한다. 수정·삭제 대상과 최신 판정은 잠금 뒤 재조회한다. 데드락/충돌 P2034, P2002 및 MariaDB 잠금 충돌 P2010(SQL 1020/1213/1205)은 트랜잭션 콜백 실패로 롤백된 경우에만 최대 3회 전체 트랜잭션을 다시 실행한다. 거래 등록의 기존 요청 ID 중복 방지도 유지한다.

## 올해 제세금과 추이 유지

- `currentYearTax`는 현재 KST 연도 1월 1일~조회 시점으로 계좌별 집계하며 목록 기간과 독립적이다. 배당 gross/net 차액을 포함하고 이중 합산하지 않는다. 카드의 올해 제세금은 공통 파란색, 계좌 갱신 정보와 동일 10px/15px 기준이다.
- 추이는 기존 저장 일별 스냅샷과 공통 차트의 축·가이드·터치/마우스 툴팁을 유지한다. 날짜·잔액 누락은 선을 끊고 0으로 채우지 않는다. 빈 결과와 조회 실패를 구분한다.

## 검증 및 데이터 처리

- 백엔드 전체 테스트와 Fastify 요청 검사: 5개 유형 최신/과거 수정, 최신 삭제와 기준 전환, 계좌 분리, 기간 없는 정렬, 동일 createdAt의 id 순서, 과거 날짜 신규 등록, 빈 내역/누락 세후/조회 실패, 카드 최신 가드, 잠금 후 재검증, 충돌 재시도, 원본 거래·스냅샷 미변경, 계좌/카드/홈 API 일치.
- 실제 MariaDB: `backend/tests/cash-latest.integration.ts`를 Backend Check 필수 검사에서 실행한다. 두 동시 입금과 등록·카드 수정·삭제 경쟁 이후 최신 내역·계좌 호환 캐시·카드 API·홈 총자산이 일치하는지 검증한다. 다른 통합검사도 별도 잔액 대신 명시적 초기 예수금 내역을 시드한다.
- TypeScript 및 프론트/백엔드 빌드. Playwright 예수금 기존·신규 검사에서 커버 370×465, 태블릿 725×396, 큰 화면 1280×800의 카드/편집/금액 정렬/포커스/취소/오류/빈 내역/누락 금액과 차트를 검증한다. 설정 진입도 확인한다.
- 운영 데이터 백필·원본 수정·스키마 변경은 없다. 조회 기준 변경으로 불일치를 해결하므로 별도 정정/백업 대상은 없다. 이후 운영 정정이 필요하면 대상과 변경 내용을 기록하고 관련 데이터 백업 후 최소 범위만 처리한다.
- 배포 후 실제 운영의 선택 계좌 최신 세후예수금, 카드 및 accounts/dashboard를 읽기로 비교한다. 운영 쓰기 시나리오는 일회용 MariaDB 검사로 구분하고 실제 기기 QA는 별도다.
