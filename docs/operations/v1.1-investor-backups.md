# V1.1.0 실행·운영 전환·롤백

## 현재 실행 범위

개발 앱 `http://127.0.0.1:3000/detail/investor-trends`, 백엔드 3300, DB `roxstock_dev`. 새 투자동향 테이블은 로컬과 격리 시험 DB에만 적용했다. 운영 앱/DB 스키마는 변경하지 않았다.

투자동향 시험 컨테이너 `roxstock-investor-crawler-preview`는 `roxstock-investor-db-preview`만 사용한다. 전용 네트워크 `roxstock-investor-preview`, 볼륨 `roxstock-investor-preview-db`, 비공개 설정 `/opt/roxstock/.deploy/investor-preview/`다. 외부 DB 포트를 노출하지 않는다. 운영 계좌 대신 시험 계좌와 삼성전자·SK하이닉스 관심 2개만 사용한다. 기존 프론트·API·수집기·운영 DB 컨테이너와 구분한다.

소스는 `investor-crawler/`, 별도 Dockerfile, 배포 구성 `infra/docker/compose.investor-crawler.yml`이다. 이미지 워크플로는 수동 실행이며 main의 전체 SHA를 요구한다. 기본은 이미지 발행만 하고 `deploy=true`일 때 별도 수집기만 배포한다. 앱 배포 워크플로에 자동 결합하지 않는다. `preview-setup.mjs`는 같은 이름의 리소스가 자체 시험 라벨을 가진 경우만 재사용하며 새 이미지일 때 수집기만 정상 종료 후 교체한다. DB 볼륨은 지우지 않는다.

## 운영 전환 순서

모니터링은 API가 연결한 DB의 `investor-trends` 실행을 조회한다. 원격 격리 시험 DB를 자동으로 합치지 않는다. 같은 DB의 자동 수집기 연결을 확인한 뒤 API에 `INVESTOR_MONITOR_SCHEDULE_ENABLED=true`를 지정한다. 시간표를 변경하면 API와 수집기의 `INVESTOR_COLLECTION_HOURS`를 같이 맞춘다. 미설정 시 실제 실행 결과는 표시하지만 예정 회차 누락을 임의 지연으로 판정하지 않는다.

1. Draft 검토에서 공급 범위·이용 조건과 미완료 항목을 확인한다. 확인되지 않은 시장 숫자는 계속 미표시한다. 앱 PR 병합과 수집 경로 검증은 별개다.
2. 기존 배포 전 백업 절차를 수행하고 백엔드 배포에서 additive 마이그레이션을 먼저 적용한다. 수집기 배포 스크립트는 테이블 존재를 확인하며 마이그레이션하지 않는다.
3. 백업 호스트 경로 `/opt/roxstock/backups/managed`를 비공개 0700으로 만들고 실행 사용자 UID 1000이 접근하도록 설정한다. 공개 정적 디렉터리나 Git 경로에 두지 않는다.
4. 서버 비공개 환경설정에 `BACKUP_ADMIN_PASSWORD_HASH`(scrypt salt/hash), `BACKUP_PUBLIC_ORIGIN=https://newrox.cafe24.com`, `BACKUP_ENABLED=true`를 준비한다. 비밀번호·해시는 채팅/PR/로그에 출력하지 않는다. 첫 수동 백업·다운로드·격리 복원 후 `BACKUP_AUTO_ENABLED=true`로 월초 04:30 KST 작업을 활성화한다. 현재 월 보충이 1회 발생할 수 있다.
5. 별도 투자 이미지 `newrox/roxstock-investor-crawler:sha-<40자리 SHA>`를 발행한다. 환경변수 `INVESTOR_START_DATE=2026-10-16`, `INVESTOR_REQUEST_DELAY_MS=2000`, `INVESTOR_COLLECTION_HOURS=18,21`과 운영 DB 연결을 비공개 설정에 준비한다. 시험 시간표이며 최종 제공 시각 확인 후 조정한다.
6. `.github/workflows/investor-crawler-image.yml`의 수동 배포 또는 `scripts/deploy-investor-crawler.sh <SHA>`로 해당 서비스만 전환한다. 잠금 충돌 시 기존 실행을 강제 해제하지 않는다. 헬스 실패 시 이전 투자 수집기 이미지로 복구하거나 신규 서비스만 중지한다.

## DB 복원 절차

앱 복원 버튼은 제공하지 않는다. 비공개 운영 절차로만 수행한다.

1. 복원 대상·파일 생성 시각·체크섬·감사 이력을 확인한다. `.sql.gz`는 gzip 무결성을 먼저 검사한다. 파일은 권한을 제한한 경로에서 처리한다.
2. 외부 수집·API 쓰기를 중단하고 현재 상태를 별도 백업한다. 운영 DB에 덤프를 바로 밀어 넣기 전에 신규 격리 DB에서 복원을 시험한다.
3. SQL의 DATABASE/USE 목적지가 원본 운영 DB를 가리키는지 점검한다. 격리 복원에는 해당 지시문을 검증하여 시험 DB로 변환한 사본을 사용한다. 계좌·거래·예수금·스냅샷·신규 자료 건수와 제약을 대조한다.
4. 승인된 유지보수 시간에 검증된 파일로 운영 복원하고 API 읽기·핵심 계산을 확인한 뒤 서비스를 재개한다. 원본 파일·복원 시각·실행자·이유를 비공개 감사 기록에 남긴다. SQL 내용·자격증명은 일반 로그에 남기지 않는다.

## 코드 롤백

기준 태그 `v1.0` / `5316e99ee21d9089cbd9d9cd94f1a1fb4d688147`의 기존 이미지로 프론트·백엔드를 복구한다. 추가 테이블은 옛 코드에 영향이 없으므로 DROP하지 않고 보존한다. 새 수집기는 별도로 정상 종료한다. 백업 영구 볼륨·목록·감사 이력을 삭제하지 않으며 기존 원본 데이터와 운영 스냅샷을 되돌리지 않는다. 관리 기능만 문제면 백업 enable 설정을 꺼 추가 생성을 중지하고 파일을 보존한다.

로컬 관리자 정보·덤프는 저장소 밖 `work/production-backups-private/backup-management-development/`에 있다. 운영 설정으로 복사하지 않는다. 기존 배포 전 백업은 이번 관리 목록에 자동 편입하지 않는다.
