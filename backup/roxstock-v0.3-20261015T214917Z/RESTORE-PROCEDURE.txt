RoxStock v0.3 encrypted production backup

1. Retrieve the password file from its separately managed location. It is not in Git.
2. Verify the encrypted archive against the adjacent .sha256 file.
3. With Node.js, decrypt to a path OUTSIDE the repository:
   node decrypt-backup.cjs ARCHIVE.sql.gz.enc PASSWORD_FILE /safe/path/restored.sql.gz
   AES-256-GCM authentication rejects an incorrect password or modified ciphertext.
4. Verify the decrypted gzip's SHA-256 against manifest.json plaintextSha256 and test gzip integrity.
5. For validation, use an isolated MariaDB 11.8.9 instance with networking and event_scheduler disabled.
   Configure server max_allowed_packet and the import client's --max-allowed-packet to 1G:
   the analysis read-cache contains large rows which exceed the default 16 MiB packet limit.
6. Import the decrypted gzip into the explicitly selected validation instance only, then execute verify.sql.
   Compare COUNT rows with validation.json tableCounts. Review restored triggers/routines/events separately.
7. For a future production restore, obtain explicit authorization, stop all database writers,
   make a fresh pre-restore backup, and verify the intended target before importing.
   This dump contains CREATE DATABASE/USE roxstock and DROP/CREATE TABLE statements.
   Restore does not happen automatically and must never be pointed at a running production database.
8. Do not start collectors from restored collector locks/running-job records without reviewing recovery state.

Archive format: ROXDB003 (8 bytes), scrypt salt (16), GCM IV (12), ciphertext, GCM authentication tag (16).
KDF: Node.js scrypt defaults (N=16384, r=8, p=1), 32-byte key; cipher AES-256-GCM.
The random password must be kept separately. There is no recovery mechanism if it is lost.
